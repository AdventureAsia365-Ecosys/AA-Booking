# AA-1092 — pre-PII hardening: row level security on `booking.b2b_partners` (Booking part)

S278 system audit M24. Other parts: AA-TripPlanner-Web (tenant assertion key), AA-Partner (public CRM routes),
AA-CIS-Infra (the key secret, web ACL coverage).

## Threat note

- **Asset:** the agency registry (`agency_name`, tier, commercial terms, the M2M client binding). No traveller data.
- **Threat:** a partner-facing code path that reads or changes another agency's row (a missing `WHERE`, a join that
  fans out), or a future reader role that gets a grant without a tenant filter.
- **Control (bk-049):** ENABLE + FORCE RLS. Any transaction that binds `app.tenant_id` sees its own row only and
  writes none; the owner is under the policies too (FORCE). The catalogue guard (rule a) now passes for the table.
- **Residual:** tracked in Linear AA-1092.

## Readers checked (before writing the policy)

| Reader | Role | Tenant bound? | After bk-049 |
|---|---|---|---|
| Staff admin: partners, tiers, rate cards, allotments, departure board / fees, desk bookings, billing, manifest | `booking` | no | every row, as before |
| Jobs: `bk_tenant_pull` (writes the projection), settlement drafts, reminders, retention | `booking` | no | every row, read and write, as before |
| B2B API partner lookup (`app/b2b/access.py`, by the tenant id the M2M client is bound to) | `booking` | no | the row it asks for, as before |
| Migrations (DB Migrate / Migration Apply) | `bk_owner` (`aa_cis_admin`, `db_migrator` via membership) | no | every row |
| FKs from `agency_invoice`, `billing_terms`, `b2b_*`, `departure_*`, `partner_rate_cards` | RI checks | n/a | unaffected (RI bypasses RLS) |
| Other owners (`cis_app`, `crm_*`, `tripplanner`) | none | n/a | no grant (pinned by the migration's own check) |

## Decisions

- **Two permissive policies, not a fail-closed scope GUC.** Every reader today is AA's back office and none binds a
  tenant. A fail-closed design (an explicit `app.scope` on every staff and job transaction) would touch ~30 call sites
  and risk the staff admin for no gain on a table with no personal data. The chosen shape changes nothing for them and
  gives any partner-facing path that binds its caller a database fence.
- **Bound = read-only.** Partners never edit their own registry row through the B2B API; a bound transaction that
  tries is refused (UPDATE 0 / INSERT 42501).
- **Contract, migration-only.** It alters an existing table and adds policies (ADR 0017 d3). No readiness raise: no
  code depends on it.

## Residual: bind the caller's tenant in the B2B API (S278, lane l20)

Two PRs, MIG-4 order: the migration-only PR (bk-058, this file, `CONTEXT.md`) and then the code PR
(`backend/app/b2b/access.py`, tests). This file and `CONTEXT.md` describe both, so the code PR touches neither.

### Decisions

- **One bound pool per request, not a `set_config` in each handler.** `app.b2b.access.TenantBoundPool` wraps the
  asyncpg pool the B2B dependency hands out (`B2BContext.pool`); every `acquire()` (and `fetch` / `fetchrow` /
  `fetchval` / `execute`) binds `app.tenant_id` first. Every B2B handler and service function already reaches the
  database through `ctx.pool`, so all of them are covered by one change, and a new handler cannot forget it. It has no
  other pool method on purpose (no side door to the plain pool).
- **Session level while held, not `set_config(..., true)`.** Most B2B reads run single statements outside an explicit
  transaction; a transaction-local setting would end with the first one. The binding is set right after acquire and
  cleared in a `finally`; if clearing fails the connection is terminated, and asyncpg's release reset (`RESET ALL`,
  checked: it clears a custom setting) clears it again. A pooled connection never carries a tenant into a staff request
  (integration test with a one-connection pool).
- **The lookup binds too.** It binds the `X-AA-Tenant-Id` it was given (it reads that row only anyway); the handlers
  bind the tenant of the row the token was proven to act for (the same value).
- **bk-058 before the code (found by the integration tests).** A view is read with its owner's row level security.
  `v_tenant_billing_status` (owner `bk_owner`) matched neither bk-049 policy under a bound session and answered no
  row: the credit stop on holds, `GET /billing-status` and `GET /terms` lost the status (3 integration tests went red
  with the binding alone). bk-058 adds `bk_owner` to `b2b_partners_tenant` (SELECT, same USING). Rejected: making the
  view `security_invoker` (changes every staff read of it) or skipping the binding on those routes (leaves a gap).
