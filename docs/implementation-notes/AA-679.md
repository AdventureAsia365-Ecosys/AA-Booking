# AA-679 — Booking half: sellable trip plans over the CIS catalog (S237, decision D4)

Scope (Linear AA-679 comment of 14/10, S237 D4): Booking **live-reads** the CIS catalog views (`catalog.v_tour`,
`v_tour_day`, `v_tour_photo`; CIS migration 225, SELECT granted to role `booking`) and keeps only a
**commercial-only** `booking.trip_plans` row per tour. No CIS `catalog.outbox`, no template copy job (CIS number 232
stays reserved, unused). The reworded Done-when: staff list sellable trip plans over `catalog.v_tour` with their
commercial fields, and a trip case (version) can start from one.

Two branches (migration flow D8):

1. `feat/aa-679-bk-009` — migration file `migrations/009_trip_plans.sql` + its integration test only. Merged to
   `main` first, byte-copied to AA-CIS-Infra, then DB Migrate check → apply.
2. `feat/aa-679-trip-plans` (stacked on 1) — API, staff pages, `REQUIRED_SCHEMA_VERSIONS` += `bk-009`. Merged only
   after bk-009 is applied on Dev, otherwise `/booking/health/ready` goes `not_ready`.

## Decisions

- **Key = `(source_system, source_id)`**, the catalog.tour.v1 key (`source_id` = `raw_tours.source_group_id`,
  stable across re-uploads). `tour_id` is never stored in `trip_plans`. `source_system` is CHECKed to `'cis'`.
- **No supplier column in bk-009.** The lane plan had `supplier_id → booking.suppliers`, but bk-008 (AA-822) is on
  an unmerged parallel branch and this slice must not depend on it. The supplier link comes with a later key
  (together with the price matrix), as a nullable FK once bk-008 is applied.
- **Commercial columns:** `sellable` (UI "Sellable / Not for sale"; the lane's `is_published`, renamed because it
  is not CIS publication), `trip_style` (free text ≤ 60, Q16 open; same limit as `trip_cases.trip_style`),
  `default_channel` (pricing_rules channels), a **price hint** (`price_hint_amount` + `price_hint_currency` +
  `price_hint_basis` per_person|per_group, all or nothing) and `commercial_notes` (≤ 5000), plus
  `created_by/updated_by` (FK `staff_users`) and timestamps. The price hint is "base pricing hints" from the task
  spec: an indicative from-amount for sales, explicitly not a quote and not the `trip_plan_prices` matrix /
  `v_from_prices` (follow-up slice).
- **Never deleted:** role `booking` has SELECT, INSERT, UPDATE; DELETE and TRUNCATE are revoked. "Not for sale" is
  `sellable = false`. A tour that leaves the catalog simply disappears from every list (the join is live), which
  also covers the original Done-when "a trashed tour unpublishes its template" without any sync job.
- **`conf:commercial` comment tags** on the commercial columns (data standards DM-6.1). No personal data.
- Migration numbers: the unit test `test_migration_numbers_are_unique_and_contiguous` gets
  `RESERVED_ON_OTHER_BRANCHES = {8: …}` for the bk-008 gap; remove the entry once AA-822 merges.

## Changed (vs the lane plan / original issue)

- Original AA-679 (outbox events + sync job copying templates, `trip_plan_itinerary`, `activities`) replaced by D4
  (live reads + commercial row). No `trip_plan_itinerary` / `trip_plan_destinations` tables (UI spec §8, O7).
- `supplier_id` dropped from this key (see Decisions).
- Price matrix / `v_from_prices` (AA-812's "from $X") stay out, as the lane plan said.

## Tradeoffs

- A CHECK on nullable columns passes when it evaluates to NULL: the first draft of the price-hint CHECK let an
  amount without currency through. The constraint now tests `IS NOT NULL` explicitly; the integration test has a
  `partial_hint` case for it.
- No cross-schema FK to the catalog (role `booking` has SELECT, not REFERENCES, and the catalog is a view): the API
  validates `source_id` against `catalog.v_tour` before writing. A row can therefore outlive its tour (kept as
  history, invisible in lists).

## Should know

- Apply order on Dev: bk-009 is independent of bk-008; it can apply before or after it.
- After apply: regenerate `AA-Ecosys/docs/architecture/db-schema-reference.md`.

## Code branch `feat/aa-679-trip-plans` (stacked on bk-009)

### Decisions

- **Live join, no copy.** `GET /booking/catalog/trip-plans` = `catalog.v_tour LEFT JOIN booking.trip_plans` on the
  catalog key; every tour is listed (Done-when "total = 892 = catalog.v_tour"), `sellable` defaults to false for a
  tour without a row. Filters `q` (title / SKU ILIKE, or the exact `source_id`), `country` and `trip_style`
  (case-insensitive), `sellable`; sorts `title` (default), `country`, `duration_days`, `updated_at` (`-` = desc).
- **Offset pagination with `total`**, not keyset (the lane plan said keyset): every other list page uses the kit
  DataTable with `serverPagination` + `total`, and the Done-when reads the total. 892 rows; `limit` ≤ 100.
- **`/facets`** gives the country options + counts, trip styles and the sellable count from the server (lesson
  "filter options from the server, not from the current page").
- **Commercial edit is a PUT** of every field (a field left out is cleared), upsert on the unique key under
  `SELECT … FOR UPDATE`, so re-saving never creates a second row. One audit row per real change
  (`trip_plan.created` / `trip_plan.updated`, `before` / `after` of the changed fields); an identical PUT writes
  nothing and answers `changed: []`. The tour must be in `catalog.v_tour` (404 `tour_not_in_catalog`).
- **Permissions:** `catalog.read` (all four roles), `trip_plan.write` (admin, contracting, like pricing.write).
  The price hint, default channel and commercial notes are hidden (null) for staff without `pricing.read`
  (content creators). "Use for trip case" needs `trip_case.write` + `version.write` (admin, sales).
- **"Use for trip case"** (`POST …/{source_id}/trip-cases`), one endpoint, two modes:
  - body with a customer (`customer_id` | `new_customer` + the `POST /booking/trip-cases` fields) → a new case with
    `source_system = 'cis'`, `source_id` = the plan (the bk-002 CHECK already allows `cis`), trip style from the
    plan unless given, countries = the ISO-2 of the CIS country name when `booking.countries` knows it, then V1;
  - body `{trip_case: "TC-…"}` → a new version on that case (task spec "create a trip case version from a plan").
  The version gets one item per `v_tour_day` row (title = CIS day title, else "Day N"; `day_from = day_to =
  day_number`), its title = the tour title, its channel = the plan's default channel, **no price** (ADR 0005: priced
  from cost lines). A tour without canonical days gives one item over its duration. Only **sellable** plans (409
  `trip_plan_not_sellable`).
- Version items from a plan store the plan's **`source_id`** in `source_tour_id` (the stable key), whereas legs from
  TripPlanner carry whatever TripPlanner sends (Q11 still open). The audit row of the version records
  `trip_plan_source_id`.
- `versions.create_version` gained an optional `seed` (items + title + channel) and `service.create_case` an optional
  `source`; both default to the old behaviour, so existing callers are unchanged.
- Catalog read errors (`UndefinedTable`, `InvalidSchemaName`, `InsufficientPrivilege`: CIS 225 missing or grant
  revoked) → 503 `catalog_unavailable` instead of a 500.
- `REQUIRED_SCHEMA_VERSIONS` += `bk-009` (only here, D8), after `bk-008` (AA-822 merged first, #9 / #10).
- **Frontend:** `/catalog/trip-plans` (KPI tiles, server filters, DataTable), `/catalog/trip-plans/[sourceId]`
  (overview / day by day / photos tagged "From CIS", "Edit in CIS" deep link `/admin/master-content?tour=<tour_id>`
  for admin + content creators, commercial side panel), the commercial `FormDrawer`, and the "Use for trip case"
  `Modal` (reuses the case `CustomerPicker`). `/…/commercial` renders the detail with the drawer open. Nav entry
  `shipped: true`. Trip cases list gets a "CIS trip plan" source filter; the case Overview links the plan.
- **CIS photos**: `<img>` from `CIS_MEDIA_URL` (= the Dev CIS API constant) + `?size=small|large`, one component
  (`ui/booking/CisPhoto.tsx`). No new environment variable: the base becomes configurable with the production
  hostnames (AA-818).

### Changed

- The lane plan's `supplier_id` and keyset paging are out (see above). The price matrix / `v_from_prices` stay in the
  follow-up slice.

### Tradeoffs

- One POST with two modes instead of a second route under `/trip-cases/{ref}/versions`: the modal is one form, and
  the plan-specific checks (in catalog, sellable) live in one place.
- `count(*)` over the live view on every list call. 892 tours on Dev; if it gets slow (the view is a security_barrier
  view over CIS tables, and the pool's command timeout is 5 s), cache the facets client-side (already 60 s) and
  consider a CIS-side index, not a Booking copy.
- A case created from a plan has no `trip_case_legs` row (legs are the TripPlanner chain), so its list row shows no
  trip title until the case list resolves CIS titles (Q11 follow-up). The version title carries the tour title.

### Review (S237, adversarial pass)

- Merged `main` after bk-008 (#9, #10) and bk-009 (#11) landed. AA-822 had added `app/catalog.py` (the
  `catalog.v_destination` reads of the supplier place picker), which clashed with the `app/catalog/` package: it is now
  `app/catalog/destinations.py`, re-exported from `app/catalog/__init__.py` (callers unchanged). One router, prefix
  `/booking/catalog`, serves `/destinations` and `/trip-plans*`. One catalog stub holds `v_destination` and the three
  `v_tour*` tables. `REQUIRED_SCHEMA_VERSIONS` lists `bk-008` and `bk-009`.
- `/facets` `total` / `sellable` summed only the country groups, so a tour without a country was missing from the
  "CIS tours" KPI while the list counted it. They now count every tour; only the options skip the NULL group.
- A catalog read past the pool command timeout (or `statement_timeout`) answers 503 `catalog_unavailable` instead of
  a 500.
- `use_for_trip_case` ignores customer / pax fields when `trip_case` is given (only `notes` is used): accepted as is.
