# AA-993 Phase E, slice M4a (Booking) — `registered_keys` on `/booking/health/ready`

Design: root `docs/audits/2026-10-26-S252-aa993-delivery-pipeline/design.md` §2 M4a; critic point 23; root ADR 0017
decision 7 (Proposed).

## Decisions

- `registered_keys` = every `bk-NNN` row of `booking.v_schema_versions` (the view already filters `bk-%`), sorted,
  the same list the probe already read to compute `missing_schema_versions`. No extra query.
- It is in the body whenever the schema read succeeded: on 200 and on the "schema behind" 503. Not on the
  `db: error` / `not_configured` 503s (nothing was read).
- `REQUIRED_SCHEMA_VERSIONS` is unchanged: M4a only exposes what is registered; raising the requirement stays with the
  code that needs a key.

## Changed

- Nothing against the design. The readiness model (`app/routers/health.py`) documents the field, so the exported
  OpenAPI (`docs/api/openapi.json`, fastapi 0.142.2) gains one optional field.

## Tradeoffs

- The list grows by one key per migration (33 today, ~10 bytes each): fine for a cached readiness body, and the
  `schema-gate` needs the full set to see a gap below the required key.

## Should know

- Ships before M4b so the first `schema-gate` run reads a task that has the field; M4b falls back to
  `missing_schema_versions` for an older task.
- Live proof (orchestrator, after deploy): `curl -s https://api-booking.lumiguides.it.com/booking/health/ready` lists
  `registered_keys` ending in `bk-033`.
- Rollback: revert; the field disappears, nothing reads it until M4b.
