# AA-911: staff sign-in on Booking Vercel Previews, then retire the CIS to Booking bridge

Root ADR 0006a A11 holds the design. Two Booking PRs: B1 (Preview sign-in, branch `feat/aa-911-preview-signin`)
and B2 (retire the bridge, branch `refactor/aa-911-retire-bridge`, stacked on B1; push only after B1 is merged
and Done-when line 1 accept is evidenced).

## Decisions

- **One fixed Preview host, `booking-preview.lumiguides.it.com`** (owner decision S246, option a). It is added to
  the allowlist in `frontend/lib/cognito.ts` as a constant (`PREVIEW_ORIGIN`). The redirect URI is still never built
  from the Host header; the host is only compared with the allowlist.
- **The allowlist follows the build's Vercel environment** (`VERCEL_ENV`): a production build accepts only the two
  production hosts, a preview build only the Preview host, `next dev` all of them plus `localhost:3001`. Outside
  Vercel (no `VERCEL_ENV`) a production build keeps the production hosts, as before. A preview build can therefore
  never run the production callback and vice versa. If `VERCEL_ENV` were ever missing at runtime, a preview build
  falls back to the production hosts, which means "no company sign-in on the Preview host": safe, and visible.
- **No legacy password form on the Preview host** (`isPreviewSignInHost`): `/login` on
  `booking-preview.lumiguides.it.com` shows only the company button (or a short "not set up on this build" notice),
  and `POST /api/auth/login` answers 404 there. Raw `*.vercel.app` preview URLs keep the legacy form until B2. The
  host may turn out to be public (Vercel protection check V1), and a stable URL must not expose a password form.
- **Opt-in alias.** Job `preview-alias` in `vercel-deploy.yml` runs only when the PR has the label `preview-signin`
  at event time, or on a dispatch from `main` with `alias_only_url`. `labeled` IS a trigger, so adding the label
  deploys and aliases in one run (one deployment against the Hobby cap); a run for any other label is skipped by the
  deploy job `if:` and gets a throw-away concurrency group, so it never cancels an in-flight preview deploy.
- **Dispatch only from main.** The alias step refuses `alias_only_url` unless `github.ref == refs/heads/main`
  (lesson S241: a dispatch on an old branch runs that branch's workflow copy with the repo secrets).
- **The deployment is checked with the Vercel REST API** (`GET /v13/deployments/<host>?teamId=…`): `projectId`
  must equal `VERCEL_PROJECT_ID`, `target` must not be `production`, `readyState` must be `READY`. A strict regex on
  the URL comes first (`^https://aa-booking-admin-[a-z0-9-]+\.vercel\.app$`), so a custom domain or another project
  is refused before any call. JSON is read with `jq`, not by parsing `vercel inspect` text.
- **The PR comment moved into its own job `comment`** (needs `deploy` and `preview-alias`), so it can say whether
  the Preview host now serves the commit, or how to opt in. The `deploy` job no longer needs `pull-requests: write`.
- **Concurrency:** the alias job has the global group `vercel-alias-booking-preview` (no cancel), so two PRs never
  race on the alias; an alias-only dispatch gets its own workflow group (`…-alias`) so it never cancels a manual
  preview deploy on the same ref.
- **`X-Robots-Tag: noindex, nofollow`** on every response of a Preview build (`VERCEL_ENV === "preview"` at build
  time, `next.config.ts` headers). It is set whether or not the host turns out to be behind Vercel Authentication.

- **Decision D-1 (Nghiệp, 21/10/2026): option 2, the Preview-only client now.** A preview build signs in with the
  new `booking-staff-preview` client (only callback: the Preview host), a production build with `booking-staff`.
  Each build reads only its own secret env var (`COGNITO_BOOKING_STAFF_PREVIEW_CLIENT_SECRET` on the Preview target,
  `COGNITO_BOOKING_STAFF_CLIENT_SECRET` on Production only), so a preview build never holds the production secret.
- **The API caps the preview client (backend, same PR).** `app.auth.identity_config` accepts
  `booking-staff-preview` next to `booking-staff` / `breakglass` (code constant `DEV_BOOKING_STAFF_PREVIEW_CLIENT_ID`,
  env override `COGNITO_BOOKING_STAFF_PREVIEW_CLIENT_ID`, must differ from the production clients). `app.auth.staff`
  `current_staff`: a preview-client token on any method other than GET / HEAD / OPTIONS is 403 `preview_read_only`
  **before** the role check and before any DB access; on a read the session gets `Staff.preview = True`, and
  `Staff.can` grants only `PREVIEW_PERMISSIONS` (the `*.read` permissions + `staff.directory`, intersected with the
  role; never `staff.admin`, `audit.read`, `retention.admin`). `/booking/staff/me` adds `preview_viewer`.
  - Why a method rule and not only permissions: two self-service writes (`PUT /staff/me/preferences`,
    `POST /notifications/read`) are guarded by the session alone; the method rule refuses every write whatever a
    route checks, including routes added later. Side effect: `POST /pricing/quote-preview` (a calculation, needs
    `pricing.read`) is refused on Preview too.
  - The stored role is not touched: a preview read still provisions / syncs the row from the Cognito groups exactly
    like production (the groups come from Cognito, not from preview code). Only the session is capped.
- **The client ids ship empty.** The preview client exists only after the AA-CIS-Infra apply, so both constants are
  `""` here: the API then refuses a preview token (401, the verifier does not list it) and a preview build offers no
  company sign-in. After the apply, one commit fills both constants (same pattern as the existing Dev client ids:
  public values, no task-definition variable).

## Tradeoffs

- **Vercel Standard Protection.** `ssoProtection` is `all_except_custom_domains`, but Vercel's docs say Standard
  Protection covers every domain except production domains, so the Preview host is most likely behind Vercel
  Authentication (Hobby: one member, so only the owner passes; E2E needs the project's protection-bypass value).
  Checked live after the first alias with `curl -s -o /dev/null -w '%{http_code} %{redirect_url}'
  https://booking-preview.lumiguides.it.com/login` (V1).
- **Token exposure.** Unmerged same-repo PR code served on the Preview host sees the access and refresh tokens of
  whoever signs in there (12 h session). Since D-1 those are `booking-staff-preview` tokens: read-only against the
  API, so the worst case is reading Dev data with the person's read permissions. The opt-in label still applies.
- **Preview reads include customer and pricing reads** (role-intersected). Dev holds test data only; narrowing the
  set further would make the Preview host useless for checking those pages. Revisit before prod.
- **Shared host.** Only one preview at a time can be signed in to. Fine for Dev; the PR comment says which commit
  the host serves after each opt-in run.

## B2: retire the bridge (branch `refactor/aa-911-retire-bridge`, stacked on B1)

### Decisions

- **Backend:** `identity_config` keeps one issuer (WORKFORCE); `BRIDGE`, `BRIDGE_ENABLED`, `BRIDGE_AUDIENCE` and
  `bridge_config` are gone. `staff.py` loses `BridgeClaims`, `provision`, `_bridge_claims`, `ROLE_FROM_CIS`,
  `AUTO_ACTIVE_CIS_ROLES` and the BRIDGE branch; any issuer other than WORKFORCE is 401 `invalid_token` (it never
  reaches `current_staff`'s row code: the verifier has no config for it, so no JWKS fetch and no DB call).
  `settings.py` drops `cis_jwks_url` / `staff_jwt_issuer` and their https checks; a value still set in the
  environment is ignored (no task-definition change needed). `identity_verifier.py` is untouched (byte copy of CIS).
- **Tests:** `tests/staff_tokens.py` now has `LocalStaff` (WORKFORCE pool + production verifier profile; `token(sub,
  role)` mints a `booking-<role>` access token), `LocalRsaIssuer` (generic foreign RS256 signer; default claims = the
  old bridge token, so refusal tests use a correctly signed bridge-shaped token) and `seed_linked_staff()` (a staff
  row keyed by `sub` and linked to the local WORKFORCE identity `sub`, replacing the retired `provision()` in DB-level
  tests). Integration fixtures insert their rows linked (`cognito_iss`, `cognito_sub = key`), so the row keys and every
  assertion on them stay as they were; the token's group carries the row's role (WORKFORCE re-reads the role from the
  group on every request).
- **Removed tests** (bridge semantics only): provisioning of CIS roles (active admin / inactive others), unknown
  `cis_role`, "bridge token still works on a linked row", "bridge `sub` starting with `cog:`", `provision()` claims,
  `BRIDGE_ENABLED` switch, CIS JWKS settings. **New:** a correctly signed bridge-shaped token (CIS issuer, `aud =
  booking`, `cis_role = admin|reviewer`, JWKS reachable) is 401 `invalid_token` with no DB call and no key fetch
  (`test_staff_auth.py`, `test_staff_tokens.py`, `test_bk016_staff_identity.py`); the issuer set == {WORKFORCE}
  (`test_identity_config.py`); retired settings are ignored (`test_settings.py`).
- **Frontend:** `app/api/auth/login/route.ts` and `app/login/LoginForm.tsx` deleted; `lib/session.ts` loses the mint
  and `CIS_SESSION_MAX_AGE_S` but keeps `CIS_SESSION_COOKIE` so sign-in / sign-out still clear a leftover cookie;
  `proxy.ts` sends a request with a leftover bridge cookie to `/login?reason=expired` and clears it; the BFF proxy
  needs the Cognito refresh cookie (401 otherwise); `cisApiUrl` / `CIS_API_URL` removed (`CIS_MEDIA_URL` stays).
  `/login` on a per-deployment preview URL says "Staff sign-in on previews: booking-preview.lumiguides.it.com"; on a
  registered host without the client secret it says the build has no sign-in settings. The staff detail page shows
  "Not linked" instead of "CIS password (legacy)". `isPreviewSignInHost` (B1) is gone with the legacy form.

### Should know

- **Agents can no longer sign in to the Booking UI** (Preview or Production): the E2E Cognito user may not hold a
  `booking-*` group (ADR 0006a A10). Booking UI checks are Nghiệp's until a preview machine principal is decided.
- Integration tests were edited without a local Postgres run (no local test DSN); CI runs them. Unit tests run
  locally: `test_staff_auth.py`, `test_identity_config.py`, `test_settings.py`, `test_staff_tokens.py`,
  `test_deploy_gate.py`, `test_identity_verifier.py`, `test_health.py`, `test_lifespan_worker.py`,
  `test_trip_case_routes.py`, `test_w1_routes.py`, `test_pricing_api.py`, `test_db_readiness.py`; ruff check + format.
  Frontend: `tsc --noEmit` and eslint on touched files.
- Deploy order (ADR A11): B1 merged and the Preview accept evidenced → mint a real bridge token while CIS still
  mints, replay it (control 200, or 403 `staff_inactive`) → merge + ECS Deploy Dev of this branch with `booking.job`
  idle → mint a fresh real token and replay it: 401 → only then CIS C1.
