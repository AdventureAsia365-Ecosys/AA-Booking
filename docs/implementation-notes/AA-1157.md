# AA-1157 — View as a lower role (Booking side)

The owner's read-only "view as a lower role" in Booking: logged start and end, every write refused before the route,
the company sign-in untouched. The CIS side is its own PR in AA-CIS-App.

## Decisions

- **No migration, no new table.** The start and end rows are `booking.audit_logs` rows (entity `staff_view_as`, id =
  the session id); the entity index `(entity_type, entity_id, created_at)` serves the per-request read and role
  `booking` already has INSERT / SELECT.
- **Opaque session id instead of a "signed" cookie (deviation from the issue's wording, tech-lead-visible).** Booking
  has no signing secret today (only the database URL and Sentry DSN). The cookie holds a uuid4 checked on every request
  against its start / end rows and bound to the viewer (`actor_ref`). It is revocable at once and needs no secret, no
  Infra change and no new table; integrity of the rights is not at stake because a view can only narrow them. A signed
  token would need a new Secrets Manager secret (Infra PR + MFA apply + CI / secret risk class). Recorded in the root
  ADR amendment too.
- **Who may start.** The CIS `is_owner` marker, read uncached at the start and through the 60 s grant cache on each
  request. The business-owner marker alone does not qualify.
- **Downward (Q6).** Read permissions = every permission a GET route checks (a recursive walk of each route's
  dependency tree, from `app.routes`, so routes added later count) plus every `*.read` permission (the ones services
  check themselves). Downward = target ∩ reads ⊆ viewer's permissions. Refusals name no capability (the log lists
  them).
- **Write block in `current_staff`.** A WORKFORCE request with the header and a method other than GET / HEAD / OPTIONS
  is 403 `view_as_read_only` right after the Preview and E2E checks, before `get_pool` or any read. Any route that
  depends on `current_staff` (directly or through `require()`) is covered, including routes added later (AA-1149,
  AA-1158). The unit test walks every such route with a pool that raises if touched.
- **Owner markers during a view.** `custom_roles.VIEWING` (a context variable set by `current_staff` on every
  WORKFORCE request) makes `is_owner` and `is_business_owner` read False; `custom_roles.markers(conn, staff)` returns
  `(False, False)` for a staff with `view_as`. The role editor uses `markers`. `is_business_owner(conn, cognito_sub)`
  is created here with the contract's name and signature (AA-1158 creates the same helper; keep one at merge).
- **Effective rights.** The narrowed staff has `role` = the target code, `custom_permissions` = target ∩ viewer, no E2E
  grant, `role_label` = the target's label, `view_as` set.
- **Lifecycle.** One view at a time: a new start ends the viewer's open views (`superseded`) under a per-staff advisory
  lock; sign-out ends them (`end-all`, called by the BFF before the refresh token is revoked); the per-request check
  ends a dead view (expired, start row erased, owner lost, role archived, no longer downward) with an end row written
  as `system`, once (lock + "no end row yet" check). The start row's `after.expires_at` is the expiry of an abandoned
  view whose end row has not been written yet; a start row whose `after` was erased fails closed.
- **Settings.** No new policy parameter. `MAX_MINUTES` (60) is the root ADR 0019 d5 ceiling, a security bound;
  `MIN_MINUTES` and `DEFAULT_MINUTES` follow the CIS view; the length is the owner's choice per start (15 / 30 / 60 in
  the UI). All three are marked `# technical-constant:`.

## Changed (vs. the plan)

- Routes are under `/booking/view-as` (critique: `GET /booking/staff/{cis_user_id}` would capture
  `/booking/staff/view-as`), plus `POST /booking/view-as/end-all` for the sign-out.
- The BFF has its own small token helper (`lib/bffAccess.ts`) instead of refactoring the proxy's refresh code.
- The Roles page shows one "View as a role" section (role picker) rather than a button per row.

## Tradeoffs

- Write buttons stay visible during a view where a page decides by `useCan` of a write the target holds; clicks get
  403 "View-as is read-only" from the BFF. The banner says read-only on every page.
- Reads are not written to the audit log one by one (the log would flood); refused writes are logged as
  `booking_view_as_write_refused` lines (no database access happens before the refusal by design).

## Should know

- The live owner path needs the tech lead's own session: no E2E identity is an owner. The E2E identities cannot write
  at all (`e2e_read_only`), so the non-owner refusal is proven by the unit and integration tests.
- `GET /booking/staff/me` adds `view_as` and `read_only`; the staff layout passes the view cookie and clears it through
  `/api/view-as/clear` when the API answers 409 `view_as_ended`.
- Owner-path evidence role pair: the Done-when names "Content + Product & operations". Preset `content_ops` is CIS
  `content_lead` with no Booking role, so the evidence uses CIS `custom_content` and Booking
  `custom_product_ops_accounting` (per CIS 462). The tech lead's Booking screenshots view as
  `custom_product_ops_accounting`.
- Refused writes during a view are a log line only (`booking_view_as_write_refused`), not a `booking.audit_logs` row
  (no DB access before the 403); CIS logs them as `staff.request` rows. Name this asymmetry in the PR body.
- The session id is an opaque uuid4 checked against the `booking.audit_logs` rows, not the issue's "signed cookie"
  (ADR 0019 d5 amendment); the tech lead acknowledges this deviation at review.
