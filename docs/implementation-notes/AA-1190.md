# AA-1190 — My work slice 1 (Booking part)

Slice 1 of the S295 My work proposal: the dashboard (the landing page of every staff member) leads with My work, more
approval tiles, a price setup progress card, zero tiles folded. Read-only, no migration. The CIS part is in AA-CIS-App
`docs/implementation-notes/AA-1190.md`.

## Decisions

- **Same contract, more tiles.** `GET /booking/my-work/summary` keeps its shape (`group` already existed). New tiles:
  `trip_checks_unassigned` (`ops.write`), `price_versions_to_approve` (`price_version.approve`), `addons_to_publish`
  (`addon.approve`), `season_changes_to_approve` and `holiday_events_to_approve` (`season.approve`).
- **Trip checks split.** `trip_checks_overdue` now counts the caller's own overdue checks (`owner=me`) and
  `trip_checks_unassigned` the unowned ones (`owner=none`); both are the Overdue tab's badge under the page's owner
  filter. Checks owned by somebody else are no longer in anyone else's tile.
- **Price versions** count `PENDING_WHERE` (pending, not made by the caller unless the business owner may self-approve,
  `self_approval.may_self_approve`). The list endpoint gained `approvable=me` with the same WHERE. There was no page
  listing pending versions, so the price setup page shows a "Price versions waiting for your approval" list when opened
  with `?pending_versions=me` (`?versions=` already opens one tour's drawer); a row opens that tour's Versions tab.
- **Add-ons** count the list's `approvable=me` view through the list's own WHERE builder (`addons._offer_where`).
- **Seasons and holidays** count only the waiting changes the viewer may approve (review fix, same slice): the approve
  paths' own maker-checker in SQL (`seasons_admin.RANGE_APPROVABLE`, `DEFAULT_APPROVABLE`, `EVENT_APPROVABLE`):
  never the viewer's own proposal or removal request; the business owner's own proposal stays in while she may
  self-approve (`self_approval.may_self_approve`; a season range, a default season, a holiday event, never a stop-sale
  range nor a removal); a stop-sale range (and its removal) only for a `stop_sale.approve` holder. Both pages gained an
  `approvable=me` view that equals the tile: the Seasons list returns each calendar's `approvable` count (0 without
  `season.approve`) and `?approvable=me` keeps the calendars with one; `GET /booking/pricing/holiday-events` takes
  `approvable=me` (server filter, same WHERE). The Holiday events page also keeps its `?state=waiting` filter.
- **Price setup progress** is its own endpoint, `GET /booking/my-work/price-setup` (`price_version.write` +
  `pricing.read`), loaded separately by the card so the tiles never wait for the workbench build. It returns the price
  workbench's own `by_next_step` summary (`price_workbench.rows` + `summary`), so the card equals the workbench. The
  card shows only the steps with plans and "N of M tours ready to buy" (M leaves out the not-served tours).
- **Dashboard.** Approvals first, then work; tiles with nothing waiting fold into "Nothing waiting in N queues"
  (opens on click). The sales block stays open for `trip_case.write` holders and folds under "Sales overview" for the
  others; the Inactive staff tile follows `staff.admin` instead of the role name. The stale "catalog pages open in
  wave 2" line is gone. `contract.expiring` notifications have a label ("Contract ending soon").

## Tradeoffs

- The price setup card costs one workbench build per dashboard open for the makers (two people today). It reuses the
  workbench's code instead of a second SQL count so the two never disagree; it is loaded separately and never blocks
  the tiles.
- A season calendar's stop-sale range counts in "Season changes to approve" only for a `stop_sale.approve` holder
  (its approve path needs both capabilities); every built-in role with `season.approve` has it today, a custom role
  might not.
- The approvable filters restate the approve paths' rules in SQL (no shared predicate object between a Python check and
  a WHERE); the integration test proves the tile equals the page for maker, checker and finance, and the unit test pins
  each rule's fragment.
- No threshold was added; the age limits per tile stay for slice 3 (settings, not literals).
