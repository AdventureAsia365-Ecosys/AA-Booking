# AA-825 — Booking retention kinds (S238 scope addition)

Scope (S238 addition to AA-825; data standards Part B DM-6.6 / DM-7, Part C C5.4; ADR 0003a decision 5; windows approved
in E3): AA-Booking runs its own TTL job kinds on `booking.job`:

- `bk_retention_job` — `succeeded` jobs deleted 30 days after `finished_at`; `failed` / `cancelled` archived to S3 and
  deleted after 90 days; `queued` / `running` never.
- `bk_retention_inbox_redact` — PII in `booking.inbox_events.payload` redacted 90 days after `received_at`; row,
  `idempotency_key` and `contract_version` kept.

Both DRY RUN by default, counts in the job result and in `booking.audit_logs`. The CIS half (5 kinds, migration 233) is
in AA-CIS-App `services/retention/` + `services/jobs/retention_job.py`; this follows its design. The TripPlanner outbox
redaction waits for `tripplanner.job` (X6 / AA-751) and is split into its own issue.

## Decisions

- **Migration `bk-012`** (owned here, `migrations/012_retention.sql`): `inbox_events.redacted_at` (explicit, queryable
  marker; the verification query is `redacted_at IS NULL AND received_at < cutoff`), the `pii:contact` comment on
  `payload` (DM-6.1), `inbox_events_redact_due_idx (received_at, id) WHERE redacted_at IS NULL`, and
  `job_finished_idx (finished_at, id) WHERE finished_at IS NOT NULL` on `booking.job` — the same name and shape as CIS
  `shared.job` (migration 233) and the "finished_at index" ADR 0003a decision 6 (X6) asks for, so X6 finds it present.
  No grant change (role `booking` already has UPDATE on `inbox_events`, DELETE on `job`). Readiness requires `bk-012`.
- **Same mode rules as CIS** (`decide_mode`): manual = DRY RUN unless `dry_run: false` + `max_rows`; scheduled = DRY
  RUN until a live run of the same windows succeeded, then live within 2x the last live count (floor 1,000), else held.
- **Last live run read from `booking.audit_logs`, not `booking.job`.** CIS reads it from `shared.job`, but
  `bk_retention_job` deletes succeeded jobs after 30 days, which would make the scheduled run fall back to DRY RUN if a
  month passed without a live run. The audit log is append-only and kept.
- **One audit row per run** (`entity_type = 'retention'`, `entity_id` = job id, `entity_label` = kind, action
  `retention.dry_run|live|held|failed`, `after` = the result, `summary` = one line), plus `retention.requested` (staff
  actor) when an admin queues a run through the API. A live run that fails half-way writes `retention.failed` with what
  the committed batches did, then fails the job.
- **`max_attempts = 1`** for every retention job. `booking.job` has no `progress` column yet (X6), so a retry could not
  know what an earlier attempt deleted and could exceed the approved `max_rows`. A failed run is visible (job error +
  audit row); the next run recounts.
- **Advisory lock per kind** (`pg_try_advisory_lock(hashtextextended(kind, 0))`, session level on the job's
  connection): a rolling deploy runs two workers; the second run of the same kind fails at once and does nothing.
- **Batches**: at most 1,000 rows (CIS: 5,000; Booking tables are small and share the instance), at most 50,000 per
  run, keyset on `(ts, id)`, `FOR UPDATE OF t SKIP LOCKED` (CIS: plain `FOR UPDATE`; skipping a locked row leaves it
  for the next run instead of waiting), `SET LOCAL statement_timeout = '30s'`, 200 ms pause. The DELETE / UPDATE must
  touch exactly the locked rows or the batch rolls back.
- **FK guard** ported from CIS: any single-column FK onto `booking.job.id` becomes a `NOT EXISTS`; any other shape
  stops the run. None exists today; X6 adds `parent_job_id`.
- **Archive format: gzipped JSON Lines, not Parquet** — same as CIS (pyarrow is not in either image; DM-7.3 / C5.4a
  say Parquet, an Athena CTAS can convert the prefix in L6). `to_jsonb(row)` per line, one object per batch and UTC
  month, key `archive/booking/job/<yyyy>/<mm>/<job_id>-<run>-<part>-b<NNNNN>.jsonl.gz`, SSE AES256.
- **Archive location**: CIS bucket `aa-cis-bronze-<acc2>` (the AA-825 archive bucket), under a Booking-only prefix
  `archive/booking/` (CIS uses `archive/job/` for `shared.job`, so `archive/booking/job/` cannot collide), so Infra can
  grant the Booking task role `s3:PutObject` on `archive/booking/*` only. A constant, like CIS — no new environment
  variable. Until Infra grants it, a live `bk_retention_job` run with failed / cancelled candidates fails before it
  deletes them (archive put precedes the DELETE in the same transaction); the succeeded part needs no S3.
- **Inbox redaction is an allowlist** (`app/retention/redact.py`, pure; changed after review): the payload is rebuilt
  from the contract's known non-PII keys and every other key is dropped. A denylist (null four known fields) left PII
  in `failed` rows for good, because a failed payload by definition did not keep the contract's shape (extra keys,
  a string `customer`, unknown contact fields of a future version) while `redacted_at` marked it clean. Kept keys:
  envelope `contract` / `version` / `idempotency_key` / `source` / `trip_id` / `handoff_id` / `submitted_at`;
  `customer` limited to `customer_id` / `consent` / `consent_at` / `verified` plus `name` / `email` / `phone` = null;
  `itinerary.legs[]` / `days[]` with their v1.2 contract keys; `custom_days[]` limited to `day_id` / `kind` /
  `after_component_id` plus `note` = null. An allowed key holding an object or array becomes null (the contract has
  only scalars there); a non-object `customer` / `itinerary` / list item / whole payload becomes null. Dropped keys
  are reported as `*` (`customer.*`, `itinerary.days[].*`, `$` for a non-object payload) so a key name taken from an
  untrusted payload never reaches the job result or audit log. A conforming payload keeps its shape (`name` /
  `email` / `phone` / `note` keys stay, null). Limit: a string in an allowed slot (e.g. a free-text `days[].name` in
  a failed row) is kept as is; the contract types those slots as ids, dates and place names. Why these stay:
  `customer_id` is the link an erasure follows, `consent` / `consent_at` / `verified` are the DM-6.5 consent record.
  A `failed` row's `error` (a jsonschema message that can quote values) is
  replaced by a fixed text; `parked` reasons are fixed strings and stay.
- **Rows still `received` are never redacted**, only counted (`skipped_unprocessed`): their process job may still run
  and needs the contact. A non-zero count after 90 days means a stuck intake, worth a look.
- **No archive for the inbox redaction.** Nothing is deleted, so DM-7.3's "archive after redaction" (retention table:
  `booking.inbox_events` "After redaction") applies only once a delete window exists; archiving a copy of a row that
  stays in the table would add a second store to erase (DM-6.7) for no restore value.
- **Daily schedule in-process** (`DailySchedule`, a new `Worker(hooks=…)` maintenance hook): the first maintenance pass
  at or after 19:00 UTC (02:00 ICT) queues one `trigger: schedule` job per kind with idempotency key
  `<kind>:schedule:<yyyy-mm-dd>`, so two workers or a restart never queue twice. CIS has no caller for its schedule
  endpoint yet; Booking needs none (no EventBridge, no Infra change). A failing hook is logged and never stops the
  queue.
- **Held notification** goes to each active Booking admin (`recipient_ref`), not the shared staff queue (sales would see
  it otherwise).
- **Admin API** (permission `retention.admin` = admin): `GET /booking/retention`, `POST /booking/retention/runs`
  `{kind, dry_run = true, max_rows}` (202, live needs `max_rows`, 422 otherwise), `GET /booking/retention/runs/{id}`.
  This is how the DRY RUN / live evidence is produced on Dev (CIS staff JWT with `aud=booking`, admin role).

## Changed vs. the issue

- The S238 text says "archive to S3 Parquet": JSON Lines gz instead (as CIS). Inbox redaction archives nothing (above).
- `queue.prune` (bk-002) still deletes finished `bk_inquiry_pull` history after 7 days including `cancelled`, without an
  archive. Left as is: it is a recurring heartbeat kind, a cancelled pull has never happened, and its rows carry no
  business data. Noted as a known gap against "failed / cancelled archived".

## Tradeoffs

- Allowlist vs denylist for inbox redaction: the allowlist must be extended when a contract version adds a non-PII
  key (until then that key is dropped from 90-day-old rows, which loses nothing the intake still needs: rows are
  redacted only after processing). A denylist would silently keep any new or unexpected contact field.
- In-process schedule vs an external trigger: no Infra change and it works on Dev today; the cost is that nothing runs
  while the service is scaled to 0 (acceptable on Dev; prod runs one task).
- `max_attempts = 1` vs a resumable retry: simpler and safe for the approved count; a transient error costs one day.
- Audit-log lookup of the last live run is a filtered scan of `booking.audit_logs` (`entity_type`, `action`,
  `entity_label`); the table is small. An index can follow if it grows.

## Should know

- Order: apply `bk-012` on Dev (byte copy to AA-CIS-Infra `db/migrations/booking/012_retention.sql`, DB Migrate check
  then apply) **before** merging the code, which requires it for readiness.
- Infra follow-up (AA-CIS-Infra `accounts/aa365/booking.tf`, task role policy): `s3:PutObject` on
  `arn:aws:s3:::aa-cis-bronze-<acc2>/archive/booking/*`. Not needed for DRY RUNs or for the succeeded part.
- Evidence on Dev (Nghiệp's rule: no waiting for data to age): DRY RUN of both kinds through the admin API, counts
  posted; then one approved live run each. Dev rows are young (Booking intake started S235), so the honest live result
  today is 0 rows unless aged rows are seeded.
- Tests: `tests/unit/test_retention.py` (policy, redaction, modes, archive key, SQL shape, schedule hook, request model),
  `tests/integration/test_bk012_schema.py`, `tests/integration/test_bk012_retention.py` (dry run then live with
  archive, max_rows, archive failure deletes nothing, scheduled dry → live → held + admin notification, inbox redaction
  with dedupe re-scan, admin API). All 733 tests pass locally against PostgreSQL 16 (CI uses 15).

## S251 — Dev manual override (reopened Done-when: one real Booking run)

The S244 audit reopened AA-825: its Done-when asks for one real Booking retention run, and the S239 evidence was a DRY
RUN with 0 candidates (Dev rows date from S235, 14/10/2026, so none are 30 / 90 days old). CIS solved the same gap in
S239 with a `manual_override` trigger (`services/jobs/retention_job.py`); this ports it.

### Decisions

- **`trigger: manual_override` + `older_than` (UTC date)**: the date's UTC midnight replaces every part's cutoff (both
  kinds). The result carries `override` (`older_than`, `cutoff`, the `policy_cutoffs` it replaced, floor, cap,
  environment). The part predicates are unchanged: `queued` / `running` jobs, rows still `received`, FK-referenced
  jobs stay out exactly as under the policy windows.
- **Guards** (same shape as CIS): only `ENVIRONMENT` in dev / test / local (any other value, e.g. a future prod,
  refuses); cutoff at least **7 days** old (`OVERRIDE_MIN_AGE_DAYS`); DRY RUN unless `dry_run` is the literal false;
  a live override needs `1 <= max_rows <= 1,000` (`OVERRIDE_MAX_ROWS`), refused — not capped — outside it. The job
  makes every check (with the database's UTC date) and fails at once with nothing touched; the API makes the same
  checks first and answers 422 `retention_override_refused`, so an admin does not wait for a failed job.
- **7 days, not CIS's 21**: CIS needed 21 to stay outside the 7-day raw readers of `llm_call_log`; Booking's Dev rows
  are at most ~11 days old, so 21 would select nothing and the proof would again be "0 rows". A week is far past any
  in-flight work (an intake job finishes in seconds, redaction skips rows still `received`) and matches
  `queue.prune`'s 7-day history for the recurring pull kind.
- **Never "the last live run"**: `_LAST_LIVE_SQL` skips audit rows whose `after ->> 'trigger'` is `manual_override`,
  so the scheduled run stays a DRY RUN until a policy-window live run is approved, and the 2x growth rule is not
  anchored on an override count. The audit action stays `retention.live` (it really deleted / redacted rows; the
  audit page lists it as such) with the summary prefixed `override older_than <date>:`. The status endpoint shows
  override runs in their own `override` bucket, plus `override_allowed` per kind and the override settings.
- **Environment source**: `build_handlers(environment=settings.environment)` in `app.main` (the process settings);
  without it the handler reads `ENVIRONMENT` at run time (default dev), as `load_settings` does.

### Changed

- `app/retention/jobs.py`: `OverrideRefused`, `override_cutoff`, `override_max_rows`, override branch in
  `decide_mode`, cutoffs + `override` block in `_run_locked`, `_LAST_LIVE_SQL` filter, summary prefix, status bucket
  and settings, `enqueue_manual(older_than=…)`, `build_handlers(environment=…)`.
- `app/routers/retention.py`: `RunRequest.older_than` (optional date; additive in `docs/api/openapi.json`),
  `_check_override` (422), the request audit row and response carry `older_than`.
- `app/main.py`: passes `settings.environment`.
- Tests: unit (`test_retention.py`: cutoff, every refusal, mode, cap, summary, request model, API check) and
  integration (`test_bk012_retention.py`: dry → live override on 8-20-day-old jobs with archive, scheduled run stays
  DRY RUN, status bucket; override redaction of 10-day-old processed rows only; refused shapes fail and touch
  nothing; refused outside dev/test/local; admin API queue + 422s).
- AA-CIS-Infra (branch `feat/aa-825-booking-archive-grant`): the `archive/booking/*` PutObject grant this file's
  "Should know" asked for — still missing on `main` before S251.

### Tradeoffs

- One trigger value with an explicit date vs a "shrink the windows" knob: the date is visible in the job, audit row
  and S3 object months, and cannot leak into the scheduled runs.
- The audit action stays `retention.live` instead of a new `retention.override`: the frontend audit view and any
  reader that counts live deletions keep working; the trigger and summary tell the two apart.

### Should know

- Order on Dev: apply the Infra grant (1 IAM policy, $0) before a live `bk_retention_job` override run that has
  failed / cancelled candidates (the DRY RUN result's `parts[failed].candidates` says); the succeeded part and the
  inbox redaction need no S3. Then deploy this, and run per kind: `POST /booking/retention/runs`
  `{"kind": …, "older_than": "<today - 7 d or older>"}` (DRY RUN, read the counts) → the same with
  `"dry_run": false, "max_rows": <approved count, ≤ 1000>` → `GET /booking/retention/runs/{id}` (counts, object keys)
  → `aws s3 ls s3://<bronze>/archive/booking/job/ --recursive` for the failed part.
- Redaction on Dev nulls the contact fields of the inbox copies of test inquiries older than the cutoff; the trip
  cases and `booking.customers` are untouched (the master record). Nothing is deleted by the redaction.
- No migration (bk-025 not needed), no new environment variable, no frontend change.

### Review spec gaps (S251)

The independent review raised no code findings. It listed four spec gaps; each is answered here.

1. **Parquet vs gzipped JSON Lines.** Not changed in this PR. Neither the CIS nor the Booking image ships pyarrow, and
   both apps already archive gzipped JSON Lines (decision recorded above and in the CIS AA-825 notes). Conversion to
   Parquet with Athena CTAS is planned for L6. Until then, the DM-7.3 "Parquet" wording is an open, recorded standards
   deviation. Adding pyarrow (a large native dependency) to the Booking image only for a few KB of archive a month does
   not pay off before the L6 conversion exists.
2. **The reopened Done-when is still open.** This PR plus the Infra grant are the code half. The proof run (Terraform
   apply, deploy, DRY RUN then live override for both kinds, counts on AA-825) is orchestrator work; the steps are in
   "Should know" above. To match the S238 "Additional Done when" wording, the run also posts these checks:
   - Inbox rows older than the override cutoff hold no contact data:
     `SELECT count(*) FROM booking.inbox_events WHERE received_at < '<cutoff>' AND status <> 'received' AND (redacted_at IS NULL OR payload #>> '{customer,name}' IS NOT NULL OR payload #>> '{customer,email}' IS NOT NULL OR payload #>> '{customer,phone}' IS NOT NULL)`
     must return 0. Run it through DB Migrate `mode=run-script` (master), because the CIS container role cannot read
     `booking.*`.
   - Dedupe still works: `test_inbox_redaction_removes_pii_keeps_dedupe_and_skips_unprocessed_rows` (integration) passes,
     and live, `idempotency_key` is unchanged on the redacted rows (the redaction rewrites only `payload`, `error` and
     `redacted_at`).
   - `booking.job` rows past the override cutoff in the succeeded / failed / cancelled parts are gone, up to `max_rows`.
3. **CIS Done-when evidence.** Checked on Linear (25/10): the S239 closing comment on AA-825 (16/10) holds the CIS
   evidence. It covers the same numbers for 9 tenants with EXPLAIN index use (`tenant_api_usage_tenant_called_idx`),
   the live override runs of `retention_llm_call_log` (200 deleted / archived, rollup equal to the raw total) and
   `retention_tenant_api_usage` (200, rollup equal row for row), the S3 objects under `archive/<table>/2026/09/`, and
   the daily schedule. The S244 reopen comment names only the Booking run as missing. Nothing CIS-side is re-run here.
4. **TripPlanner outbox PII.** Out of scope: it was split into AA-861, blocked on `tripplanner.job` (X6 / AA-751), as the
   S238 scope comment allowed. `booking.outbox` has no payload column, so Booking has no outbox PII to redact.
