# AA-1091 — Price setup workbench (Booking part)

Linear AA-1091 items 1-4 and the Booking side of the customer-service guide. The CIS items (5 structured reference
price, 6 staff grant) are a separate lane; this side reads their result when it lands.

## Decisions

- **No migration.** Everything is built on tables that exist: the workbench reads trip plans, components, prices,
  departures and the reference; the import writes through the single forms' services; the provisional price is the
  existing price hint (bk-009 `price_hint_*`). No bk-049 is taken (AA-1061 can use it).
- **The workbench is the readiness report plus three facts**, never a second classifier: `price_workbench.rows` calls
  `price_readiness.load` / `resolve` and adds departures, valid b2b rows, reference and hint in one set query. The two
  pages cannot disagree on a status.
- **Next step order** follows the cost sheet's reasons (`no_components` → `inactive_component` → `missing_rates` →
  `missing_fx` → `no_rule`), then `recompute` (priced by the probe but not stored), `make_sellable`, `done`. A plan
  priced only by hand still shows `add_components`: an agency quote prices components (`app.b2b.components`), so hand
  prices alone are never quotable. Departures are a check, never a step (tailor-made tours have none).
- **Provisional price = the price hint.** The hint is already a display-only price: `price_parity` (the public RRP an
  agency must not undercut) falls back to it when no b2b row exists; quotes, holds, the tariff and
  `booking.v_from_prices` never read it. So "shown as RRP only, never quoted to agencies as a contract price" holds by
  construction. A hint is "provisional" whenever it is shown without a b2b row (`supplier_price` false);
  `from_reference` says whether it still equals the CIS reference. The bulk action never overwrites a hint typed by
  staff and marks the reference reviewed (staff looked at it to use it).
- **Structured reference** (fix pass, review finding): the CIS lane ships it as a **new view**,
  `catalog.v_tour_price_reference_v2` (CIS 402; v1 is left as it is), columns `reference_amount`, `reference_currency`,
  `reference_basis` (`per_person` | `per_group` | `from`) and `reference_status` (`confirmed` | `needs_review` |
  `parsed`). Booking feature-detects v2 (`trip_plan_sync.STRUCTURED_VIEW`) and reads it **instead of** v1 (v2 lists
  every live tour, v1 only those with a text); without v2 it parses the v1 text as before. The first cut detected
  `amount` / `currency` / `basis` on v1, names CIS never shipped, so it would never have switched on.
  - `confirmed` and `parsed` are taken as they are; `needs_review` (CIS parser doubts, or the text changed since the
    value was set) is not trusted: Booking's own parse of the text decides, the same as before CIS had a value. Once
    CIS confirms, the value switches and the Booking review clears (an amount change alone counts). Rejected
    alternative: take the needs-review value and clear the Booking review on every run, which would undo a Booking
    review every 15 minutes while CIS is unresolved.
  - `per_person` and `from` (the lowest per-person price) are per-person references. `per_group` gives **no
    per-person amount** (the plan keeps the text only); the first cut parsed the text then, which would show a group
    total as a per-person price.
  - The run result reports `references_source` (`structured` | `text`) and `references_structured` (plans holding a
    trusted CIS value), so it is visible which path ran.
- **Suggestions are rules, not a model** (root ADR 0009 d13: Booking makes no AI call). Explained additive score,
  thresholds 0.2 (0.05 for a guide: country-level guide services are the norm). Breakfast is never a need (it is in the
  room rate). The hotel's default room type is its double / twin (the cost sheet's default room mix is doubles).
- **Accept / reject live in the drawer state only**; nothing is stored until Save, which sends the whole set to the
  existing `PUT …/components` (its checks and audit). A rejected suggestion comes back on the next open; storing
  rejections would need a table and is not needed for the pilot.
- **Bulk workbook = replace semantics per listed tour** (components and plain hand prices), additive for departures,
  a switch for sellable. This makes the prefilled export → edit → import loop idempotent and easy to reason about.
- **Rows priced from a cost are not in the workbook** (fix pass, review finding): a row typed with a net cost on the
  single price form (`computed` false, `net_amount` set, maybe `overridden`) carries a net cost, margin and override
  the sheet has no columns for. The first cut exported it as a plain hand row, so an unchanged re-import dropped its
  net cost (audit row, matrix rewritten). Now the export lists plain hand rows only (`net_amount IS NULL`) and the
  merge keeps net-cost rows like computed rows unless a file hand row overlaps them; the dry run counts those it
  replaces (`net_rows_replaced`, next to `computed_rows_replaced`) and the Read me says so. Rejected alternative: Net
  cost / Net currency columns priced through `replace_prices` (pricing rule, override, below-floor reason per row):
  more columns and a reason field for the bulk path, for a case the single form already covers.
- **Formula-safe export** (fix pass, review finding): the workbook is the first .xlsx export with database text (CIS
  title and country, room type names, seasons). openpyxl stores a str starting with "=" as a formula, so a text cell
  that starts with one of `tariff.FORMULA_START` is set to a string cell with the quote prefix, value unchanged (not
  prefixed with "'" as the CSV exports do: the round trip must still match room type names and seasons).
- **Maker-checker**: the single forms the workbook replaces (components, price matrix, departures, commercial) have
  none; supplier contracts (rate sheets) and pricing rules / FX keep theirs. The import needs `trip_plan.write`.
- **Language**: the page wraps itself in the kit `I18nProvider` with a Booking `langStore` (cookie `bk_lang`) and shows
  the kit `LangSwitch`; only this page (and the drawer when opened from it) follows the choice. The trip plan's
  "Hotels & services" tab reuses the drawer outside a provider, so it stays English like the rest of that page.

## Tradeoffs

- Candidate pool = the tour's country (item, else supplier country) or its overnight destinations, capped at 3000 rows
  each. A hotel named in the text but registered in another country is missed; cross-border tours are rare and the
  unmatched list makes the gap visible.
- The dry run's "status after" applies the readiness rules to the new component set; the one case only the full cost
  sheet catches (rates that do not share a start window) can show `priced` in the preview and `missing_rates` after.
  The real import recomputes and returns the true status.
- The import recomputes at most 50 plans inline; a bigger file leaves the rest to `bk_price_recompute` (its watermark
  moves with the components and plans).
- The workbench returns every plan (about 900) in one response, like the readiness page; client-side paging and the
  filters are server side. Fine at this size; paging would be the next step past a few thousand.

## Should know

- No migration, no new job kind, no new grant. Ships as one code PR. It does not need CIS 401 / 402 first: without
  v2 the sync keeps parsing the v1 text, and it switches to v2 by itself within a minute of CIS 402 being applied
  (feature detection cache).
- The provisional price does not reach TripPlanner "From $X" (`booking.v_from_prices` reads b2b rows only). Showing
  it there would change contract `price.from.v1` (TripPlanner and CIS readers): a follow-up if the business wants it.
- Live data today: only a handful of hotels and services exist in Booking, so most suggestions will be `unmatched`
  until supply is entered; the unmatched list is the to-do list for creating suppliers.

## Guide draft (Booking part) — for the root docs page

Target: `docs/guides/customer-service/price-setup.md` (EN) + `price-setup.vi.md`; front-matter per `docs/STYLE.md`.
Role names only.

### Set up tour prices in Booking

Who: the customer-service team (Booking role **contracting**, granted by the tech lead in CIS → Platform → Staff;
sales can look but not change). Where: Booking staff app → Supply → **Price setup**.

**What "ready to sell" means.** A tour can be quoted to agencies when it has (1) its hotels and services per day,
(2) a published supplier rate for each of them, (3) an approved exchange rate for each rate currency, (4) an approved
agency pricing rule, and (5) the sellable switch on. Departures are needed only for fixed-departure tours. Price setup
shows these checks for every tour and the **next step**.

**1. Find the tours to work on.** Use the *Next step* filter (for example "Add hotels & services") and *Country*.
The tiles at the top count every tour. Switch the page to Vietnamese with the EN | VI switch at the top right.

**2. Add hotels and services from the itinerary.** Click a tour (or "Hotels & services"). For each day Booking
suggests the hotel of the night and the services the CIS itinerary mentions (transfer, guide, entrance ticket,
activity, lunch or dinner), with the reasons of the match and how strong it is. For each suggestion: **Accept**, pick
another match or room type, or **Reject**. Remove items that are wrong. Nothing changes until you click **Save**.
"No match" means Booking has no such hotel or service yet: use *Create supplier*, *Hotels* or *Services* to add it,
then open the tour again.

**3. Load supplier rates.** Supply → Suppliers → the supplier → *Import rate sheet*: download the template, fill it,
*Check*, then *Import as draft*. A second person publishes the draft contract (maker-checker). Prices of every tour
using those hotels and services then compute by themselves.

**4. Many tours at once: the workbook.** On Price setup, filter the tours, then *Download workbook* (prefilled with
those tours) or *Import workbook* → *Blank workbook*. Sheets:
- *Tours*: Sellable yes / no.
- *Components*: one row per hotel room type (Hotel code + Room type) or service (Service code) per day. A tour listed
  here gets exactly these items.
- *Prices*: hand prices per person per pax band and season (Valid from / to, Pax min / max, Currency, Price per
  person, Child, Infant, Single supplement). A tour listed here gets exactly these hand prices; prices worked out
  from a cost (from supplier rates, or a price typed with a net cost on the tour's price form) are not in the file and
  stay unless a hand price covers the same dates and group size.
- *Departures*: new fixed departures (Start date, Capacity, Min to operate, Sales cutoff days…). A date already there
  is skipped.
Upload it, click **Check** (nothing is written; every problem is listed by sheet, row and column, and each tour shows
what changes and its price status after), fix the file if needed, then **Import**. Importing the same file twice
changes nothing.

**5. Provisional price (optional).** For tours with no supplier price yet, select them and click *Show CIS price as
provisional*: the CIS reference price is shown as the suggested retail price, marked "Provisional: no supplier price
yet". It is never quoted to agencies; their quotes and tariff use supplier rates only. *Clear provisional price*
removes it.

**6. Make them sellable.** Select the tours whose next step is "Make sellable" and click *Make sellable* (a tour
without hotels and services is skipped). Check Pricing → Price readiness and an agency's tariff (Pricing → Agency
tiers → Agencies → View tariff).

The Vietnamese translation for the `.vi.md` sibling is drafted outside this repo (everything in this repo is
English); the root docs PR carries both.
