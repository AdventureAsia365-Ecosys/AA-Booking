# AA-1159 — Booking My work band (W2a)

Lane l7 of S286. The Booking half of My work; the CIS half (AA-1156, CIS `/admin/my-work`) shipped in CIS #1615 and
this mirrors its approach: one summary endpoint, tiles by capability, each count taken with the target list's own WHERE.

## Decisions

- **One endpoint, `GET /booking/my-work/summary`** (`app/my_work.py`, `app/routers/my_work.py`). The route needs any
  staff session and refuses (403 `forbidden`) a caller with none of the tile capabilities; each tile is in the answer
  only when `Staff.can(capability)` is true, so preview / E2E caps and a later custom role work without changes.
- **Tiles of this slice (W2a)**, only queues whose list page already exists (or needed one filter value):
  my open cases, overdue trip checks, open on-request lines, supplier bills overdue, supplier bills due soon, agency
  invoices overdue; approvals group: supplier bills to approve (`bill.approve`), to pay (`payout.write`), agency payments
  to approve (`agency_payment.approve`), stop-sales to review (`stop_sale.approve`, review fix).
- **Approval tiles count only what the viewer may act on** (review fix): maker-checker refuses a bill the viewer entered
  or last changed (approve and payout), a payment they recorded, a stop-sale they entered or asked to end. Each list
  gained the same option so the tile still equals its page: `approvable=me` on `GET /supplier-bills`
  (`bill_filter(actionable_by=)`: `created_by <> me AND facts_edited_by IS DISTINCT FROM me`) and on
  `GET /agency-payments` (`payment_filter(actionable_by=)`: `recorded_by <> me`); /billing "Entered by: Someone else (I
  can act)" and the Payments tab "Recorded by: Someone else (I can approve)". The tiles open those views.
- **Stop-sales to review (review fix)**: `GET /supply/restrictions` gained `review=waiting|me` (shared builder
  `restrictions.restriction_filter`, `WAITING` = pending, or approved with an end request not decided yet; `me` drops
  the ones the caller entered / asked to end) and a `total`; rows now carry supplier code / name and the maker's and
  the end requester's names. New page **/stop-sales** (Supply group, every supply reader; Approve / Reject with a
  reason / Approve lifting for `stop_sale.approve`), the longest waiting first. Before this there was no stop-sale UI at
  all (API only), so the tile needed its page.
- **Same filter as the page**: each list query's WHERE moved into a pure builder (`app/ops/bill_filters.py` `bill_filter`,
  `trip_cases.service.case_filter`, `agency_billing.invoices.invoice_filter`, `agency_billing.payments.payment_filter`);
  the trip checks overdue definition became the constant `OVERDUE` used by both the tab badge and the tile; the desk
  reuses `STATE_WHERE["open"]`. Each module got a small `queue()` counter (count + oldest / earliest due).
- **"Due soon" = the reminder's window**: `supplier_bill_due_soon_days` (Pricing > Policy, already admin-editable,
  maker-checker). No new threshold. The issue text says "7 days"; the setting decides (3 on Dev today).
- **"My open cases" moved into the band**: the old fourth KPI tile for non-admins counted the same cases but opened
  `/cases?tab=mine` (every status). The band tile opens `?tab=mine&status=<every open status>`, so the list equals it.
- **"CIS: My work" link** sits in the band header (not the sidebar): the nav model holds internal pages only. It shows
  when the person has a CIS role.

## Changed

- Not built in this slice (need a list page, a new setting or AA-1158 part 1), kept for W2b / W2c:
  - contracts expiring within N days (needs a policy parameter seeded by a bk- migration and a contracts list);
  - contracts to publish (`contract.publish`) and suppliers to activate (`supplier.activate`): the issue puts them in
    the "Waiting on someone else" / "Waiting on me" bands that come after AA-1158 part 1. A draft contract is not yet
    "submitted for publishing" and `inactive` does not tell "never activated" from "deactivated" until that part adds a
    `pending` state, so a tile now would count the wrong rows. Not shown as an always-unavailable tile either (noise on
    every checker's dashboard). The orchestrator records this split on the Linear issue;
  - season stop-sale ranges (Pricing > Seasons, also `stop_sale.approve`) are reviewed on the Seasons page; the tile
    counts contract stop-sales only (one list, one count);
  - supplier bookings to send / waiting across cases: the list API exists, no page yet (the old "Supplier answers
    pending" tile stays);
  - tours not price-ready: the readiness page filters one status at a time (needs a "not ready" filter value);
  - notifications by capability, "Waiting on someone else" / "Waiting on me" bands.
- `GET /supplier-bills` gained `due_soon` (bool); /billing "Due" select gained "Due soon".

## Tradeoffs

- Counting with the list's WHERE (a second query per tile) instead of a combined SQL: nine small indexed counts on open
  rows, run in sequence on one connection, keep the "equals the page" rule structural. No cache, no polling.
- First cut counted every waiting item, the viewer's own included (review: a maker saw "3 to approve" they could never
  act on). Fixed with the `approvable=me` / `review=me` list options rather than a tile-only rule, so the equality
  "tile = its page" still holds. The unfiltered lists keep showing everything.
- `list_bills` takes the plain list filters as `**filters` (passed to `bill_filter`, which validates them): keeps
  `supplier_bills.py` under its code-health line baseline.
