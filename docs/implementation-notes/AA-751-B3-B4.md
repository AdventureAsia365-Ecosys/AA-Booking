# AA-751 (X6) B3 + B4 — Booking deploy gate

Plan: `AA-Ecosys/docs/audits/2026-10-16-S240-aa751/aa751_plan.md` §3 (facts F6, F19, F22). B3 = the app endpoint,
B4 = the `preflight` job in `.github/workflows/deploy-dev.yml`. Cost $0: no secret, no Terraform, no new variable.

## Decisions

- **Verifier (`backend/app/auth/ci.py`)**: `GithubDeployVerifier(JwksCache(http_fetcher(GITHUB_JWKS_URL)))`, built
  lazily (`GithubDeployVerifier.default()`): GitHub's JWKS is fetched on the first gate request, never at start-up.
  Constants as in the plan: issuer `https://token.actions.githubusercontent.com`, JWKS `<issuer>/.well-known/jwks`,
  audience `aa-booking-deploy-gate`; RS256 only, `kid` required, `exp`/`iat`/`iss`/`aud` required, 30 s leeway (same as
  the staff JWT). Claims: `repository`, `ref`, `environment`, `event_name` in {push, workflow_dispatch},
  `job_workflow_ref`.
- **`job_workflow_ref` is compared for equality, not "starts with"** (plan said starts with). For a workflow that
  runs as itself the claim is exactly `AdventureAsia365-Ecosys/AA-Booking/.github/workflows/deploy-dev.yml@refs/heads/main`;
  a prefix test would also accept `...@refs/heads/main-x`. (The `ref` check already rejects that branch, so this is
  belt and braces.) A non-string `event_name` is a 401, not a 500.
- **Shared decode helper**: the header checks + `jwt.decode` of `StaffTokenVerifier.verify` moved into
  `tokens.decode_rs256(jwks, token, audience, issuer, required)`; the staff verifier and the deploy verifier both call
  it. Behaviour of the staff path is unchanged (its tests pass unmodified). `AuthUnavailable`'s message is now
  "JWKS unavailable" (no test or caller matched the old text).
- **FastAPI dependency `deploy_caller`**: 401 `missing_bearer_token` / `invalid_token` (with `WWW-Authenticate:
  Bearer`), 503 `auth_unavailable`. The route takes the DB pool only **after** the token is verified, so an
  unauthenticated call never touches the database (tested). Accepted calls log `run_id`, `sha`, `actor`, `event`;
  rejections log the reason (never the token).
- **Exempt kinds**: `DEPLOY_GATE_EXEMPT = frozenset({"bk_inquiry_pull"})` added to the existing
  `backend/app/jobs/kinds.py` (created by B5 with `EXPECTED_SECONDS` / `DEFAULT_EXPECTED_SECONDS`; reused, nothing
  duplicated). A unit test keeps it a subset of the known kinds.
- **`queue.active_count(pool, exempt_kinds)`**: one `GROUP BY status, kind` over `queued`/`running`, exempt kinds
  excluded, no time filter (a job due in an hour still counts: same contract as CIS). Returns
  `{active, by_status, by_kind}`; `by_kind` sums both statuses and is sorted by kind.
- **Route**: `GET /booking/ops/deploy-gate` in the new `backend/app/routers/ops.py` (prefix `/booking/ops`),
  registered in `main.py`; response `{active, by_status, by_kind, safe_to_deploy, exempt_kinds}`.
- **Workflow `BASE_URL`**: `vars.BOOKING_API_BASE_URL` is not set anywhere, so both the gate and the smoke step use
  `${{ vars.BOOKING_API_BASE_URL || 'https://api-booking.lumiguides.it.com' }}` (that host serves `/booking/health/ready`
  200 bk-013, checked by the orchestrator).
- **Preflight script** (one step after `configure-aws-credentials`): `describe-services` runningCount → 0 means
  `::notice::` and pass; a non-numeric answer (service missing, AWS error) blocks unless overridden. Then mint the OIDC
  token from `ACTIONS_ID_TOKEN_REQUEST_URL`/`_TOKEN` (runner env, never interpolated with `${{ }}`), `::add-mask::` it,
  GET the gate. Anything but HTTP 200 with a boolean `safe_to_deploy` and numeric `active` = "unreachable or invalid"
  → block unless overridden. Not safe → `::error::Deploy blocked: N job(s) queued/running (1 queued, 1 running; by
  kind: k=n, ...)`, exit 1; with an override reason → `::warning::` naming the reason and the counts, exit 0. The
  override input arrives through `env:` (no script injection); a blank/whitespace reason counts as no override.

## Tradeoffs

- GitHub OIDC instead of a shared secret / public counts / RunTask / the B5 metric (plan §3 rejected designs).
  Downside: the gate depends on GitHub's JWKS being reachable from the task; a fetch failure keeps the last good key
  set, and with none at all the gate answers 503 and the workflow blocks (fail closed; the override exists for that).
- `runningCount == 0` skips the gate without calling it (F19): nothing can be interrupted, and with no task the gate
  could not answer anyway.
- No time filter in `active_count`: a job scheduled far in the future blocks a deploy even though the deploy would
  not interrupt it. Kept for parity with CIS and because a release/requeue is still a state change; such rows are rare
  in Booking (only the exempt pull is scheduled ahead).

## Should know

- **Merge order matters.** The preflight of the run that ships B4 calls the *running* app. If B4 lands before B3 is
  deployed, the gate URL answers 404 → "unreachable or invalid" → the deploy is blocked (unless the service runs 0
  tasks, or the run is dispatched with an override). Either merge B3 first (its own deploy uses the old workflow, so
  merge it while `booking.job` is idle, F22) and B4 after, or ship both in one PR and expect to re-dispatch the first
  deploy with an override reason. Both commits are on branch `feat/aa-751-booking-deploy-gate`.
- **The smoke test now runs on every deploy** (it was always skipped because `BOOKING_API_BASE_URL` is unset). It
  checks `/booking/health` git_sha == the commit and `/booking/health/ready` 200 through
  `https://api-booking.lumiguides.it.com`. A red smoke after a COMPLETED rollout is new behaviour, not a regression.
- The preflight job reuses the deploy role (`vars.AWS_ROLE_ARN`) only for `ecs:DescribeServices` (F19 says it has it)
  and runs in environment `dev`, so the role's OIDC trust (`environment:dev` subject) is the same as the deploy job's.
  If the `dev` environment ever gets required reviewers, both jobs wait for approval.
- WAF logs keep the `Authorization` header unredacted (lessons.md, S239): the gate's OIDC token would appear there.
  It expires in minutes and its audience opens nothing but this read-only count.
- A GitHub Enterprise "custom issuer" setting would change `iss`; the org uses the default issuer today.
- Verified locally: unit tests, ruff check + format, `yaml.safe_load`, actionlint (no shellcheck installed), the
  integration test on a throwaway local Postgres 16 (CI uses 15), and the preflight script's 13 branches with mocked
  `aws`/`curl` under `bash -e`. Not verified: a real GitHub OIDC token against the live gate (window B in the plan).
