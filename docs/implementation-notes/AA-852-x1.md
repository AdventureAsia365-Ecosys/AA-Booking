## S5 — prep PR, no migration (`feat/x1-s5-booking-prep`)

### Decisions

- **Per-file migration role** (`tests/migration_guard.py`): `MASTER_ROLE = aa_cis_admin`, `OWNER_ROLE = bk_owner`,
  `OWNER_TRANSFER = 14`, `migration_role(n)` = master for n ≤ 14, `bk_owner` after. The guard, the integration
  replay and the bk-001 owner test all read it, so there is one place that says "who runs bk-NNN".
- **Default privileges:** n < 14 → `FOR ROLE aa_cis_admin` GRANT/REVOKE (unchanged for bk-001…013); n = 14 →
  `FOR ROLE bk_owner` GRANT/REVOKE plus `FOR ROLE aa_cis_admin` **REVOKE only**; n > 14 → `FOR ROLE bk_owner` only.
- **New `owner` rule:** `OWNER TO x` only in bk-014 and only to `bk_owner`; `REASSIGN OWNED` / `DROP OWNED` never.
  Stricter than "allow OWNER TO bk_owner": after bk-014 every new object is created by `bk_owner` itself, so a later
  `OWNER TO` would be a smell. Loosen in review if a real case appears.
- **`no-set-role` widened** to the S1 lint's booking rule: `SET [LOCAL|SESSION] ROLE`, `RESET ROLE|ALL|SESSION
  AUTHORIZATION`, `SESSION AUTHORIZATION`, `set_config('role', …)` (also `E'role'`, inside DO bodies). The runner
  does the switch; a file never does.
- **Integration replay mirrors the runner (XD8):** each file runs as `migration_role(n)`; on the first pass the
  replay asserts that equals the live owner of schema `booking` (what DB Migrate would pick), so a drift between the
  guard's table and the real transfer fails in CI. After a switched file, the login role must own nothing in
  `booking` (the runner's post-check, simplified). The re-run pass uses the same per-file role (DB Migrate never
  re-runs a registered file; the re-run only proves idempotency/convergence).
- **Role bootstrap outside the tests:** `tests/integration/bootstrap_roles.py <superuser DSN> [<admin DSN>]` creates
  `aa_cis_admin` NOSUPERUSER CREATEROLE CREATEDB NOBYPASSRLS (owner of the database), `bk_owner` NOLOGIN +
  `GRANT bk_owner TO aa_cis_admin` (rl-001 stand-in), `booking` LOGIN with the CI-only password. The conftest
  fails fast when the admin role does not have that shape. Admin DSN comes from the existing env var (no new one)
  or argv.
- **Role `booking` is no longer dropped/recreated per session.** A non-superuser cannot `DROP OWNED BY booking`
  (needs the role's privileges); as on Dev the role exists before bk-001 (bk-001's `CREATE ROLE` is guarded).
  Its grants disappear with the dropped schemas.
- **CIS 243 stand-in:** `stub_shared.sql` grants `bk_owner` USAGE on `shared` + SELECT, INSERT on
  `shared.schema_versions`. The 243 prefix trigger is **not** mirrored (243 is not written yet; mirroring an
  unwritten file risks drift).
- **`supply.py` / future-table test** switch to the *live* owner of `booking` (not a hard-coded `bk_owner`), so
  they pass both before bk-014 (owner `aa_cis_admin`) and after it.

### Changed vs. plan

- Plan says "supply.py disables triggers via `SET ROLE bk_owner`": done as `SET LOCAL ROLE <live owner>`; with a
  hard-coded `bk_owner` S5 would fail (tables still owned by `aa_cis_admin`, `bk_owner` is not a member of it).
- Plan's `test_bk001.py:43` owner assertion `{aa_cis_admin, bk_owner}`: made exact instead — `aa_cis_admin` while
  bk-014 is not in `migrations/`, `bk_owner` once it is.

### Tradeoffs

- The re-run pass runs bk-001…014 as `aa_cis_admin` even after the transfer (they contain `FOR ROLE aa_cis_admin`
  rows that `bk_owner` cannot touch). Re-running them recreates the old default-privilege rows; bk-014's re-run
  revokes them again, and S6's tests check the end state, so convergence is still proven.
- PostgreSQL 16 locally vs 15 in CI/RDS: the bootstrap does every membership grant as the superuser, so the PG 16
  CREATEROLE changes (ADMIN OPTION) do not matter for the tests.
