# AA-1088 — Pre-pilot quick fixes (AA-Booking part: M13)

S278 system audit item M13: the B2B confirmation and the vouchers showed end date = start date (a 6-day tour read as
1 day), and a B2B trip case read "Custom trip ... no CIS tour linked". The other items of the issue are in AA-CIS-App
(M3) and AA-Partner (M3 studio side, M6, M9).

## Decisions

- **Where the days come from**: `app/b2b/plan_span.py`. A `tp:` line covers max(catalog `duration_days`, the plan's
  highest component `day_no`, 1), bounded to 366. Before, only the components counted, and most Dev plans price day 1
  or nothing, so the case end and the documents said 1 day. A plan priced past the catalog length keeps its own days.
- **Both places**: the confirm stores the right end (and the tour item's `day_to`), and the documents take the later
  of the stored end and the computed span, so bookings confirmed before this fix print the whole tour without a data
  fix. A staff-extended end is kept.
- **Catalog read**: in a savepoint, `asyncpg.PostgresError` / timeout fall back to the components (same rule as the
  AA-1013 title read); a document or a confirm never fails on it.
- **"Custom trip"**: a B2B case has no TripPlanner legs (`booking.trip_case_legs`). Its `trip_title` is now its first
  version's title, which the B2B confirm writes as the tour sold (AA-1013 headline). No legs are written: legs feed
  the TripPlanner read-back and leg countries, and a B2B case is not a TripPlanner chain. The empty legs note on a B2B
  case says the tours sold are in its version.

## Changed

- No migration. Stored end dates of B2B cases confirmed before this fix stay as they are in `booking.trip_cases`
  (the staff case header still shows those few as 1 day); the agency documents are right for them.

## Tradeoffs

- One more catalog read per confirmation / voucher request (one query for the plans, one for the tours of the
  booking's plan lines), bounded by the booking's lines.
