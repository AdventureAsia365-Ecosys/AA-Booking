# AA-1088 — Pre-pilot quick fixes (AA-Booking part: M13)

S278 system audit item M13: the B2B confirmation and the vouchers showed end date = start date (a 6-day tour read as
1 day), and a B2B trip case read "Custom trip ... no CIS tour linked". The other items of the issue are in AA-CIS-App
(M3) and AA-Partner (M3 studio side, M6, M9).

## Decisions

- **Where the days come from**: `app/b2b/plan_span.py`. A `tp:` line covers max(catalog `duration_days`, the plan's
  highest component `day_no`, 1), bounded to 366. Before, only the components counted, and most Dev plans price day 1
  or nothing, so the case end and the documents said 1 day. A plan priced past the catalog length keeps its own days.
- **Both places**: the confirm stores the right end (and the tour item's `day_to`), and the documents take the later
  of the stored end and the computed span, so bookings confirmed before this fix print the whole tour without a data
  fix. A staff-extended end is kept.
- **Catalog read**: in a savepoint, `asyncpg.PostgresError` / timeout fall back to the components (same rule as the
  AA-1013 title read); a document or a confirm never fails on it.
- **"Custom trip"**: a B2B case has no TripPlanner legs (`booking.trip_case_legs`). Its `trip_title` is now its first
  version's title, which the B2B confirm writes as the tour sold (AA-1013 headline). No legs are written: legs feed
  the TripPlanner read-back and leg countries, and a B2B case is not a TripPlanner chain. The empty legs note on a B2B
  case says the tours sold are in its version.

## Changed

- No migration. Stored end dates of B2B cases confirmed before this fix stay as they are in `booking.trip_cases`
  (the staff case header still shows those few as 1 day); the agency documents are right for them.

## Tradeoffs

- One more catalog read per confirmation / voucher request (one query for the plans, one for the tours of the
  booking's plan lines), bounded by the booking's lines.

## Should know

  an old case, the confirm's stored end and item span, `trip_shape` headline) and
  `backend/tests/integration/test_aa1088_b2b_trip_length.py` (real PostgreSQL through the HTTP API).

## S278 lane l18: display fix of older B2B cases

The live verify showed TC-000028 (confirmed before AA-1013) titled "B2B crm-proposal:… v1" with items "trip_plan tp:…
· line …", and TC-000035 / TC-000033 with end = start in the case header and Trip details (their documents were right).

### Decisions

- **The app computes, a migration only opens the lock.** The tour title and length come from `catalog.v_tour`, which
  only role `booking` reads (bk_owner cannot), so the values come from the same code as the confirm
  (`holds.line_titles`, made public, and `plan_span`), in `app/b2b/legacy_cases.py`. The approved version is locked by
  the bk-003 triggers; bk-052 adds one exception to each lock, open only while the transaction sets
  `booking.legacy_display_fix = 'aa1088'`: a version may change only its title and only over the exact pre-AA-1013
  placeholder of its hold; an item only its title (over its exact placeholder) and a longer `day_to`. Everything else
  stays refused with the same error.
- **What changes**: the end date only when later (a staff-extended end is kept, as the documents do); titles only
  over the exact placeholders; item spans only longer. Synthetic and real agencies alike (display data, not money).
  Versions sent to a customer are skipped (none for B2B).
- **A CLI, not a maker-checked route, bound to the reviewed DRY RUN**: run once by the operator (precedent
  `app.inquiry.leg_keys`); a maker-checked route needs two admin humans on Dev, which do not exist, and the change is
  bounded by the lock exception, not by the caller. Review fix pass: the DRY RUN prints `plan_hash` (SHA-256 of the
  canonical JSON of every planned change); `--apply` requires `--expect-plan <plan_hash>`, recomputes the plan and
  writes nothing (exit 3) when it differs (a case confirmed or a catalogue tour length changed since the review);
  every audit row carries the hash. The person who reviews the DRY RUN output (the case codes and their changes) is
  the checker of exactly what is written.

### Changed

- bk-052 (migration-only PR, contract), `backend/app/b2b/legacy_cases.py`, `holds.line_titles` public, readiness
  raised to bk-052 (code PR), CONTEXT.md.
- Tests: integration `test_bk052_schema.py` (migration PR), `test_aa1088_legacy_cases.py` (plan, apply, idempotent,
  the locks open only for the fix), unit `test_aa1088_legacy_cases.py`.
