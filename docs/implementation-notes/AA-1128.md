# AA-1128 B1: season calendars really assigned

Source: S283 UI audit (root `docs/audits/2026-11-17-S283-fe-audit/README.md` section 6, Booking row 11). On Dev the
Seasons page showed 0 calendars; the worker log had 405 of 405 `bk_trip_plan_sync` runs in 5 days with
`calendars: {"skipped": "TimeoutError"}` while each job said "succeeded".

## Root cause

`seasons_admin.UNASSIGNED_SQL` picked the batch with a `JOIN LATERAL` to `catalog.v_tour` for every trip plan
without a calendar, then `ORDER BY md5(id || salt) LIMIT 50`. Postgres resolved the CIS view for all ~844 plans before
the LIMIT, past the API pool's 5 s `command_timeout`. `_calendars()` caught `TimeoutError` as a catalog error and
returned `{"skipped": ...}`; `run()` still answered `outcome: ok`, so nothing but one warning log line showed it.

## Decisions

- The batch comes from `booking.trip_plans` alone (no catalog in the batch query). The catalog is read one plan at a
  time: `catalog.v_tour` by `(source_system, source_id)` equality for the tour id, then `catalog.v_tour_place` by
  `tour_id = $1` (the filter that reaches the view's per-tour parse, lesson "Dữ liệu" on `= ANY()`).
- Each catalog read runs with asyncpg's per-call `timeout` and inside a savepoint, so a cut read rolls back alone.
  The first cut read ends the batch (a slow catalog would cut every next read too); the plans after it are counted
  `not_tried`. No "N timeouts before stopping" number, so no extra threshold.
- Every plan picked is counted under one outcome: `assigned` (`calendars_created` of them made a new calendar),
  `no_tour` (paused or retired in CIS), `no_destination`, `timed_out`, `not_tried`. `picked` is their sum.
- "Degraded" lives in the job result, not the job status: `outcome: "degraded"`, `degraded: ["calendars"]`, plus a
  warning log line. `booking.job.status` has a CHECK (`queued/running/succeeded/failed/cancelled`); adding a status
  would be a contract migration of the job template for one job, and failing the job would retry the bridge part
  that already committed. The Seasons list (`GET /booking/pricing/season-calendars`) now returns `sync` (the last
  finished run's counts, `skipped`, `degraded`), `plans` and `plans_without_calendar`; the page shows them in the
  UI PR of this issue.
- Thresholds (tech lead rule S279): the batch size and the read timeout are pricing policy parameters
  `season_sync_batch_size` (50 plans, 1-500) and `season_sync_read_timeout_seconds` (5 s, 1-60), section
  "operations", approved by the administrator group. bk-059 seeds today's effective values (the former code constant
  and the pool timeout), so behaviour changes only by the fix itself. A policy without the two values skips the step
  with `skipped: "policy_unavailable"` (degraded), never a code fallback.

## Changed

- `app/pricing/seasons_admin.py`: `UNASSIGNED_SQL`, new `TOUR_ID_SQL`, `assign_default_calendars(conn, limit, salt,
  read_timeout)` with the counts; `sync_out()`, `LAST_SYNC_SQL`, `PLAN_COVERAGE_SQL`, `list_calendars()` adds `sync`,
  `plans`, `plans_without_calendar`.
- `app/catalog/trip_plan_sync.py`: `_calendars()` reads the two policy values; `calendars_degraded()`; `run()` answers
  `degraded`. `CALENDAR_BATCH` is gone.
- `app/pricing/policy_params.py`, `policy_guides.py` (EN + VI guide), `tests/unit/fakes.py` (seed), the Pricing >
  Policy page labels and units (`frontend/app/(staff)/pricing/policy/_parts/messages.ts`).
- `app/db.py`: readiness raised to bk-059 (MIG-4: the migration-only PR applies first).

## Tradeoffs

- Two catalog reads per plan (tour id, then day one) instead of one join: 100 short indexed reads per run, each
  bounded, versus one read that never finished.
- `no_tour` plans (paused in CIS) are picked again on later runs; the md5 salt rotates the batch so they never block
  the others, and the count says how many there are.

## Should know

- CI guard: `tests/unit/test_aa1091_seasons_admin.py::test_the_batch_never_reads_the_catalog_and_each_catalog_read_is_one_key`
  fails if the batch query reads the catalog again or a catalog read takes a list or a join.
- Integration `tests/integration/test_aa1128_season_sync.py` holds an `ACCESS EXCLUSIVE` lock on the catalog stub
  from a second session to cut a real read and checks the savepoint and the connection.
- After deploy on Dev, the first run assigns up to 50 calendars; with ~844 plans it takes about 17 runs (15-minute
  slots, ~4-5 hours) to cover the catalog unless the batch size is raised on Pricing > Policy.
