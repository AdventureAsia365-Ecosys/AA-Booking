# AA-975 (CRM-B3) — Event feed, on-request desk, incident flag

Linear AA-975 ("cursor feed (incl. `hold.extended`); staff admin accept/decline with an SLA badge; **"Flag incident on
departure" button in the Booking staff admin** (Fix B3). R: a non-CRM client → 403. E: replay from an old cursor
yields no duplicates; an incident flag never carries traveller data"). Sources: contract `booking.b2b.v1` (root
`docs/contracts/booking.b2b.v1.openapi.yaml`, `/events`, `Event`, `EventPage`), design v3 §2.5 (Booking staff admin),
§3.4 (`b2b_event` outbox), §5.2, §6.3 (card CRM-B3), the Booking commercial-core memo seams 4, 8, 10, root ADR 0004a
(supply outbox, for the "shared" part), Linear AA-835. Stacked on AA-972/973/974 (bk-019…bk-021). Session S249, agent

## Decisions

- **One shared outbox, `booking.outbox`** (not a `b2b_event` table). The lane brief asks for "one shared
  transactional outbox" that takes the AA-835 pattern; the design names the B2B part `b2b_event`. One table with a
  `stream` column (`b2b` now; AA-835 adds `supply`) keeps one ordering mechanism, one sequencer and one set of grants
  for every event Booking publishes. Typed columns (ids and codes), **no payload jsonb and no free-text column**: the
  "never traveller data" rule (Linear E) is then structural, not a review promise. No FKs: an outbox is a log; FKs
  would make retention and the integration test clean-ups of the named rows fail.
- **Events are written by triggers, not by service calls.** Memo seam 8 says a "trigger or service hook in Lane B"
  turns state changes into `line.*` events. A trigger covers every path that changes a state (requests, the expiry
  job, the lazy expiry in `POST /holds` and `DELETE /holds`, the desk, staff departure edits, AA-682 later), in the
  same transaction as the change, so an event exists if and only if its change committed. Producers:
  `b2b_holds` (status → `expired`: `hold.expired`; `extended_count` up: `hold.extended`), `b2b_hold_lines` (status →
  `confirmed` / `declined`: `line.confirmed` / `line.declined`), `b2b_cancellations` insert (`booking.cancelled`),
  `departures` (status → `guaranteed` / `cancelled`), `departure_incidents` (insert / clear).
- **Feed order = commit order, by a sequencer.** Paging on the identity id would skip a row whose transaction commits
  after a later id's (classic outbox gap). Options weighed: (a) `pg_snapshot_xmin` visibility on an `xid8` column —
  correct, but the shared RDS runs CIS jobs, and any long writing transaction anywhere in the cluster would stall the
  CRM feed for its whole length; (b) an advisory lock held by every writer until commit — correct only if every
  emitter takes it last, fragile with triggers (lock held mid-transaction, deadlock risk with row locks);
  (c) **a stamper** (chosen): writers only insert; `app/outbox.py` stamps `feed_seq` from a sequence on committed,
  unstamped rows in id order, in short transactions under one `pg_try_advisory_xact_lock`. A feed_seq is only ever
  given to a committed row and later stamps only give larger numbers, so `feed_seq > cursor` never skips or repeats.
  The feed stamps before it reads (fresh); the worker hook `OutboxSequencer` stamps on every maintenance pass (rows
  also become visible to future readers that do not stamp, e.g. AA-835's supply view). A stamper that finds the lock
  taken skips (the holder stamps those rows).
- **Cursor** `bk1.<feed_seq>`, opaque to the CRM. No `after` = from the start; `next_cursor` is always present (the
  contract requires it): the last item's cursor, or `after` itself when nothing is new. A malformed cursor or one
  ahead of the feed (never issued) is 422 `invalid`; `limit` 1–500 (default 200, the contract's).
- **Departure events fan out per agency**: one row per partner with a live hold, or a confirmed line that is not
  declined / cancelled, on the departure (`booking.outbox_departure_event`). Not per hold: the CRM maps the
  departure to its trips (AA lines carry `departure_id` from the quote), and an agency gets one banner per incident.
- **Contract minor 1.1 (additive)**: `departure.cancelled` (staff can cancel a departure; agencies with seats must
  learn it), `departure.incident_cleared` (the card's flag has an end), `Event.decline_code` (the CRM pre-selects the
  Lost reason "AA on-request declined", design §2.7, and needs the why). `departure.time_change` stays in the enum
  with **no producer**: departures have only a start date, no time or time zone; adding one is its own change.
  `new_start_time` is always `null` for now.
- **On-request desk scope = confirmed bookings only.** The contract confirms "fixed → confirmed; others →
  on_request" after the deposit; before the deposit ops do no supplier work. So the desk lists `on_request` lines of
  `confirmed` holds; an active hold's on-request lines are not on it and the hold length stays `b2b_hold_hours` (the
  memo's proposed "on-request until ops answer + 24 h" hold length is therefore not adopted; it would only matter if
  ops answered before the deposit).
- **SLA "1 business day"** (design Q1 6.2): `answer_due_at` is stored at confirm (a later settings change never moves
  an existing deadline): `booking.b2b_answer_due(now(), days, tz)`, Mon–Fri in the ops time zone; a weekend request
  starts at Monday 00:00. Settings `b2b_on_request_answer_business_days` = 1, `b2b_ops_timezone` = Asia/Ho_Chi_Minh
  (policy data; a bad value falls back to the default with a warning, checked in a savepoint so a confirm never
  fails on it). Computed in SQL because the API image has no tzdata and the database has the zone rules. Badge:
  `overdue` (past), `due_soon` (≤ 4 h), `on_time`; `answered` / `closed` after.
- **Decline codes** `sold_out | supplier_unavailable | minimum_not_met | other` (no free text, same reason as
  incidents). Accept = `confirmed`. Answers are idempotent (the same answer again returns the line unchanged); a
  different answer on an answered line is 409 `line_answered`. The hold row is locked first, as a cancel locks it, so
  an answer and a cancel of the same booking serialise. Declined seats are free at once (`sold` already leaves out
  declined lines, AA-973).
- **Incident flag** (Fix B3): codes from the contract enum only; at most one open incident per departure (partial
  unique index; 409 `incident_open` names it); a cancelled departure takes none (409); clear is idempotent. The staff
  member and time are stored (staff ids are internal, not traveller data); the event carries only the code and the
  departure.
- **Permissions** `b2b_desk.read` / `b2b_desk.write` = admin, sales, contracting. Booking has no ops role; the
  supplier checks behind an on-request answer are contracting's, the agency relationship is sales'; content creators
  stay out. `b2b_desk.read` is in the Preview-client cap (reads only), so the Preview smoke can open the page.
- **Staff notification** `b2b.on_request` (shared queue, one per confirmed booking with on-request lines, `data.code`
  = the TC code); the bell opens `/b2b-desk`. No overdue reminder yet (the badge and KPI tiles show it).
- **Confirm order**: the hold is now updated before its lines (it was lines first), so the `line.confirmed` trigger
  reads the trip case as `booking_id`.
- **AA-835 is not done by this.** Its Done-when needs the `supply.hotel.v1` / `supply.service.v1` contracts, a supply
  stream with `supply_version`, `v_supply_*` views granted to the CIS reader, a CIS migration and consumer job (LLM
  draft + human review + stale / diff handling), the `shared.v_supply_content` read-back, Booking hotel / service UI
  and `entity_media` usage rights. This issue builds only the shared outbox + ordering it will reuse. So the CIS
  consumer is not built here. What AA-835 still needs, exactly:
  1. bk-NNN: `outbox.stream` CHECK + `'supply'`; supply columns (`entity_type`, `entity_id`, `supply_version`) and
     their CHECKs; triggers on `hotels`, `hotel_room_types`, `services` (material-change rule, deactivate event);
     `v_supply_hotel` / `v_supply_service` / `v_supply_outbox` (stamped rows only, `feed_seq` as the cursor) with
     SELECT to `cis_app` (migration guard `CONSUMER_ROLES` already allows `booking.v_*`); `entity_media` + a
     Booking-owned S3 prefix; schema-ownership rows.
  2. Root contracts `supply.hotel.v1.json`, `supply.service.v1.json` + README rows.
  3. CIS migration (content tables keyed by `(source_system='booking', source_id)`, `supply_version` ordering, status
     draft / published / stale) + `shared.job` consumer with `LLMClient` cost logging and the review queue.
  4. CIS `shared.v_supply_content` with SELECT to `booking`; Booking hotel / service pages read it ("Edit in CIS");
     proposals read only `published` rows.
  5. Dev evidence of the AA-835 Done-when (create → draft → publish → read-back, rename → stale, replay → no change,
     deactivate → unpublish, media rights).

## Tradeoffs

- The stamper adds up to one maintenance pass (or one poll) of latency before a row is readable; the feed stamps
  inline, so a CRM poll always sees every committed change. Cost: one small write transaction per poll (an index
  probe when nothing is pending).
- Triggers hide the emit from the Python code path; the module docstrings and the migration header name them, and
  the integration test asserts every event type end to end.
- Typed columns instead of a payload: a new event field needs a migration, but nothing unreviewed can ever be
  published.
- No outbox retention yet: rows are ids only (no PII) and tiny; a delete window is a DM-7.5 decision for Nghiệp when
  volume needs it.
- Public holidays are not counted in the SLA (est.; a holiday calendar would be a settings table later).
