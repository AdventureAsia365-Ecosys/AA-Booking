# AA-973 (CRM-B2) — Departures, capacity, holds

Linear AA-973 ("`departure`, capacity, holds with TTL + reaper, B2B trip case without PII, confirm/release,
idempotency, auto-confirm vs on_request; hold set per `(tenant, proposal_ref, version)`. R: capacity 0 → `sold_out`;
confirm after expiry → refused. E: two concurrent holds on the last seat → exactly one wins"). Sources: contract
`booking.b2b.v1` (root `docs/contracts/booking.b2b.v1.openapi.yaml`), root ADR 0005a, ADR 0008a decision 3, the
Booking commercial-core memo (root `docs/audits/2026-10-22-S247-crm-w0/booking-commercial-core-memo.md`, seams 1, 2, 4,
9), design v3 §3.4, §5.2, §6.3 (card CRM-B2). Stacked on AA-972 (bk-019). Session S248, agent Claude Code.

## Decisions

- **Scope** (memo "order that avoids rework" step 2): `departures`, `b2b_holds` (+ lines), the trip-case changes of
  memo seam 2, and the routes `GET /departures`, `POST /holds`, `GET /holds/{id}`, `DELETE /holds/{id}`,
  `POST /holds/{id}/confirm`, plus the staff departure API and the hold-expiry job. `extend` (once) and the re-hold
  limit (429) are AA-974 (bk-021); the `b2b_event` outbox and `GET /events` are AA-975 (bk-022). The columns AA-974
  needs (`extended_count`) are created here so it adds no column to a hot table.
- **Error codes follow the contract, not the card's shorthand.** The card says "capacity 0 → 409 `sold_out`; confirm
  after expiry → 409". The approved contract (and design §5.2 "Errors") says `sold_out` = **422** and an expired hold
  = **410 `hold_expired`** ("re-hold"). The contract is the CI-checked interface the CRM is built against, so it wins;
  the error *codes* (`sold_out`, `hold_expired`) are what the CRM branches on. Recorded here so the reviewer is not
  surprised.
- **Held and sold seats are counted, never stored.** `departures` keeps only `capacity`; `held` = seats of lines of
  holds that are `active` and not past `expires_at`, `sold` = seats of lines of `confirmed` holds whose line is not
  `declined` / `cancelled`. Counted under `SELECT … FOR UPDATE` of the departure rows (ordered by id, so two holds on
  the same departures never deadlock). Why: counters would drift (a crash between the hold insert and the counter
  update is impossible inside one transaction, but expiry, decline and cancel each would need their own counter
  maintenance), and an expired-but-not-yet-reaped hold would keep blocking seats until the reaper ran. With counting,
  an expired hold frees its seats the second it expires.
- **Concurrency (card E).** The departure row lock is the serialisation point: two holds racing for the last seat both
  `SELECT … FOR UPDATE` the departure; the second waits, then (READ COMMITTED: each statement takes a new snapshot)
  counts the first one's committed lines and is refused `sold_out`. Covered by an integration test that runs two
  holds on two connections at once.
- **Seats** = adults + children of the line; infants take no seat (same rule as pricing, AA-972).
- **Availability** (design Q1 6.2 / Q2 6.1, "fixed departures auto-confirm; others on request"): a line on a departure
  with `auto_confirm` and enough free seats = `available`; on a departure without `auto_confirm` = `on_request`; a
  line without a departure = `on_request` (no allotment model: AA ops confirm with the supplier); not enough seats, a
  `cancelled` departure, or a departure that starts today or earlier = `sold_out`. Quotes now report this per line
  (AA-972 said `available` for every line as a placeholder); holds re-check it under the lock.
- **A departure belongs to a trip plan line.** `departure_id` is accepted only on a `tp:<plan>` line of the same plan,
  and the line's `service_date` must be the departure's `start_date`; anything else is 422 `invalid`.
- **One hold set per proposal version** (Fix A3): unique partial index on `(partner, proposal_ref, proposal_version)`
  while `active` or `confirmed`. A second `POST /holds` for the same version and the **same quote** returns the
  existing hold (201, idempotent on the proposal version as design F6 says); for a **different quote** it is 422
  `invalid` naming the hold to release first (the contract has no generic conflict code). Released or expired sets do
  not block a new hold (that is the re-hold path; its daily limit is AA-974).
- **Idempotency-Key** (required by the contract): unique per partner on `b2b_holds`. Same key + same request → the same
  hold; same key + a different request → 422 `invalid`. A concurrent duplicate that loses the unique index race is
  retried once and answered from the winner.
- **Quote validity is honoured as quoted.** A hold presents `quote_id` + `price_hash`: a hash that differs from the
  stored quote's → 409 `price_changed` (with the quote's hash); a quote past `valid_until` → 409 `price_changed`
  ("re-quote"). Within validity the hold does not re-price: the quote's FX lock and validity are exactly that promise.
- **Hold length**: setting `b2b_hold_hours` (48, data; the memo's proposal for seats). Capped by the earliest departure
  start (00:00 UTC of `start_date`): a hold never outlives its departure. The memo's "on-request until ops answer +
  24 h" needs the on-request desk (AA-975); until then on-request lines get the same 48 h.
- **Expiry job.** Kind `bk_b2b_hold_expire` (`app/b2b/expiry.py`): moves due `active` holds to `expired` in batches of
  500 (`FOR UPDATE SKIP LOCKED`, at most 20 batches a run). Scheduled by a worker maintenance hook that queues one run
  only when a due hold exists (idempotency key per UTC minute), so no job row is written while nothing is due. Reads
  never wait for it: every read and every capacity count treats `active` + past `expires_at` as expired. Not exempt
  from the deploy gate: a run takes seconds and exists only while a hold is due, so DM-11.4 ("no deploy while a job is
  queued or running") stays the rule rather than widening `DEPLOY_GATE_EXEMPT`. AA-975 adds the `hold.expired` event
  write to this job.
- **Release** (`DELETE /holds/{id}`): `active` → `released`; already released or expired → 204 (idempotent, nothing
  held); `confirmed` → 422 `invalid` ("cancel the booking", AA-974).
- **Confirm** (`POST /holds/{id}/confirm`, memo seam 1): only here does Booking create a commercial record. In one
  transaction, with the hold row locked:
  - expired / released → 410 `hold_expired`; `price_hash` ≠ the quote's → 409 `price_changed`; already `confirmed` →
    the same booking again (idempotent);
  - a **B2B trip case**: `channel = 'b2b'`, `customer_id` NULL, `party_tenant_id` = the agency, `source_system =
    'crm'`, `source_id` = `proposal_ref`, status `confirmed` (inserted directly; no post-sale edge is needed and the
    status history's `changed_by` is a staff FK, so it is a system change with the note "B2B confirm by
    m2m:<client_id> of hold <id>"), `idempotency_key = b2b_hold:<hold id>` (the existing
    unique index makes a double confirm impossible), dates from the lines, pax = the largest line party, currency
    from the quote;
  - **one approved version** (V1, `channel = 'b2b'`, total and currency of the quote, FX lock copied from the quote:
    plain rate + date, so nothing is re-converted, memo seam 6), one itinerary item per quote line (room type /
    service id when the line is `rt:` / `sv:`), and one cost row per line from the quote's net (`net_cost_usd`, USD,
    `supplier_rate_id` when the line used exactly one rate). Items and costs are written before the version is marked
    approved, because the bk-003 / bk-004 locks refuse writes to an approved version;
  - hold lines: `available` → `confirmed`; `on_request` stays (the AA-975 desk answers it).
  - Response `Booking`: `booking_id` = the trip case id, `trip_case_code` = its `TC-` code.
- **B2B trip case visibility.** Staff trip-case list and detail, the cross-case version list and the staff detail join
  customers with a LEFT JOIN now, so a B2B case shows (customer fields `null`, `channel = 'b2b'`,
  `party_tenant_id`). The staff UI already renders a missing customer name as "Unnamed customer"; a B2B badge and
  agency name are an AA-975 desk follow-up (memo open point "B2B tab").
- **Staff departure API** (needed to create departures at all): `GET|POST /booking/catalog/trip-plans/{source_id}/departures`
  and `PATCH /booking/departures/{id}` (read `supply.read`, write `trip_plan.write`, audited). Capacity can never be
  set below the seats held + sold; `cancelled` is final; status `scheduled` ↔ `guaranteed`. Departure edits touch the plan's `updated_at` (the products feed's change
  signal).
- **Hold lines keep two statuses.** `held_as` (`available` / `on_request`, never changes) is the contract
  `HoldLine.line_status`; `status` moves on (`confirmed`, `declined`, `cancelled`) and is the contract
  `BookingLine.status`. One column could not serve both enums once a line is confirmed.
- **Products** report `has_fixed_departures` = a non-cancelled departure starting after today (UTC), for sellable
  plans only.

## Changed

- **AA-972 quote behaviour**: lines without a departure now report `on_request` (AA-972 answered `available` as a
  placeholder; `quotes.AVAILABLE` removed); `departure_id` is accepted (was "unknown departure_id (no departures
  yet)"), stored on `b2b_quote_lines` and returned per line. `price_hash` covers `departure_id` (hash version
  `booking.b2b.v1/quote/2`); hashes of earlier quotes stay valid because holds compare against the stored hash, never
  a recomputation.
- **Staff trip-case reads** (`list_cases`, `get_case`, cross-case versions list, staff detail assignments) LEFT JOIN
  customers; the case body gains `channel` and `party_tenant_id`; the list filter `source` accepts `crm`.
- `tests/integration/test_bk005_w1.py`: the settings list gains `b2b_hold_hours`.
- `tests/unit/test_b2b_api.py`: availability is `on_request` without departures; the OpenAPI leak test covers the new
  routes (`DeparturePage`, `Hold`, `Booking`: still no net / cost / margin key); products carry
  `has_fixed_departures`; the hash test covers `departure_id`.
- Worker: handler `bk_b2b_hold_expire` + hook `ExpirySchedule` (`app/main.py`), `EXPECTED_SECONDS` 120 s.

## Tradeoffs

- **Counting vs counters**: one grouped query per hold / quote / list over `b2b_hold_lines` (index on
  `departure_id`). Cheap at agency volumes (tens of lines per departure); counters would be O(1) but need upkeep on
  expiry, release, decline and cancel, each a drift risk.
- **Row lock on the departure** serialises holds per departure only; holds on different departures never wait on each
  other. Lock order by id avoids deadlocks between holds that share several departures. A mutation check (lock
  removed) makes the race test fail with two winners.
- **No re-pricing at hold time** keeps the quote's promise (FX lock + validity) and avoids a second pricing pass; a
  supplier rate change inside the 48 h window is absorbed by AA (the version keeps the quoted net for margin review).
  Re-pricing with 409 on any change would make holds fail on unrelated rate edits.
- **On-request lines get the same 48 h** as seats until the AA-975 desk can answer; the memo's "until ops answer +
  24 h" needs that desk.
- **Cancelling a departure with seats sold is allowed**: a real cancellation (weather, minimum not reached) must be
  recordable; existing bookings stay `confirmed` until AA-974 (cancel with fee) / AA-975 (`departure.*` events) act on
  them. New holds and confirms on it are refused (`sold_out`).
