# AA-986 slice L5 — Booking: tours that are not served (root ADR 0015 decision 5)

Lane S248 `aa986-l5`. Authority: root ADR 0015 (Accepted, Q1–Q10 decided by Nghiệp; Q4 = keep confirmed work, staff
flag **and** a staff notification, refuse new quotes and holds) and the audit memo
`docs/audits/2026-10-23-S248-tour-deletion-propagation/memo.md` §2.4 / §3.4 (root repo).

## Decisions

- **No migration (no bk-022).** The staff flag is derived at read time from the catalog views (it disappears by itself
  on restore, nothing to keep in sync); the lifecycle consumer reuses `booking.inbox_cursor` and
  `booking.inbox_events`, whose `source` CHECK already allows `cis` since bk-002.
- **Rule**: a key is not served when it is not in `catalog.v_tour` **or** `catalog.v_tour_retired` says `retired` /
  `paused`. Fail closed when the two disagree (ADR 0015: the derived state is the truth, but Booking must never sell a
  key either side calls gone); the disagreement is logged (`catalog_liveness_disagree`) and is the nightly probe's job.
  Only `retired` and `paused` rows are tombstones: CIS 274 keeps a `restored` row once a key is served again, and
  that row (or any state Booking does not know) is ignored, `v_tour` decides (review round 1).
- **Which lines are checked**: only `tp:` lines (a trip plan = a catalog key). `rt:` / `sv:` are supply items that
  exist without a tour; refusing them because some retired plan also uses them would block unrelated sales.
- **Confirm is refused too** (409 `tour_not_served`), not only quote and hold: a confirm creates the sale, and the ADR
  consequence is "Booking never sells a retired tour". A confirmed hold's replay still returns its booking. **Extend**
  is not refused (it sells nothing; the confirm that would sell is refused).
- **Paused** (ADR 0015 decision 5 paused table, AA-Booking: "confirmed work kept, **no staff flag**"): refused with
  the same 409 (`tour_state = paused`), no staff notification, no alert box, no leg pill, not in the orphaned list or
  its facet count, not listed as withdrawn in the delta feed. The leg's `catalog` field still carries `paused` (data
  for the API reader); the UI flags only `retired` / `not_in_catalog` (`isFlaggedState`).
- **Problem body** gains three optional fields: `tour` (TourKey), `tour_state` (`retired | paused | not_in_catalog`)
  and `reason` (the CIS reason, or `not_in_catalog`). The CRM needs `tour_state` to tell "gone" from "temporary".
- **Products delta**: withdrawn rows only with `updated_since` (a full list is the current offer); `updated_at` of a
  withdrawn row = the retirement time; one row per plan (keyset on `source_id`), the live row wins. Only plans that
  were offered to agencies are listed withdrawn (`sellable`, or with components): a plan never offered is not told to
  partners (review round 1). The live part's
  `updated_at` now includes `catalog.v_tour.updated_at` (CIS 273: follows the Master row) so a restored tour comes back
  in a delta without a full resync.
- **Staff notifications**: shared staff queue (no recipient), one per open trip case (status not completed /
  cancelled) and one per trip plan of the key; types `tour.retired`, `tour.reinstated`. A case is affected through a
  leg (bk-011 key), its own key (started from a trip plan) or an item of a live version (`source_tour_id` = the key:
  staff "use for trip case" and the B2B confirm write the plan's source_id). `restored` notifies only when a
  retirement was notified for the key (read from `booking.notifications`, not from the inbox payload, which the
  90-day redact job trims). The plan text never calls active holds safe: confirm refuses them, so it says they
  "can no longer be confirmed and will expire: contact the agency", and `data.active_hold_list` (≤ 20) names each
  hold with its agency (review round 1).
- **Trigger**: a worker maintenance hook (like `bk_b2b_hold_expire`), not a `Recurring` kind: a recurring kind needs a
  singleton unique index on `booking.job`, i.e. a migration and a template exception. The hook writes a job row only
  when the outbox has a row the inbox lacks (key per UTC minute).
- **Apply in the pull transaction** (no per-event process job as in the inquiry intake): applying an event is a few
  reads and inserts, and one transaction keeps "inbox row + notifications + processed" atomic.
- **Feature detection** instead of a startup check: `view_ready` reads `pg_class` / `pg_attribute` and the privilege
  functions (never a relation, so it cannot raise or abort a transaction), cached 60 s per process, and requires the
  columns Booking selects. Readiness (`/booking/health/ready`) is unchanged: Booking works without CIS 274.
- **Orphaned plans**: `?orphaned=true` on the existing list route (not a new route), `q` = exact source_id; facets
  gain `orphaned`. Rows carry the counts staff need to act (open cases, future departures, confirmed holds).

## Changed (vs. the lane brief)

- The brief names `catalog.v_tour_retired` / `catalog.v_tour_lifecycle_outbox` from CIS 274 (lane aa986-l3l4). The
  first build guessed the outbox id column as `id`; review round 1 aligned Booking with what CIS 274 (commit
  a858171) actually defines and asserts:
  `v_tour_retired(source_system, source_id, tour_id, state, reason, changed_at)`, `state` ∈ `retired | paused |
  restored`, and `v_tour_lifecycle_outbox(event_id, source_system, source_id, tour_id, event, reason,
  replaced_by_tour_id, occurred_at, idempotency_key)`. Booking selects a subset; a view without one of them is
  treated as missing (degraded, logged `catalog_view_unready`), never a 500. The integration stubs are built from the
  exact column lists 274's closing check asserts, and the fixture fails when Booking selects a column 274 lacks.

## Tradeoffs

- Reading `v_tour` per key with a correlated `EXISTS` (equality pushed into the view per key) instead of
  `source_id = ANY($1)` (lessons.md: `ANY` is not pushed through the view's joins).
- Feature detection costs one catalog query per process per minute; a request never pays more.
- Fail closed on a tombstone/v_tour disagreement can block a sale after a CIS bug; the alternative (trust v_tour) can
  sell a retired tour. Selling the wrong tour is worse; the probe reports the disagreement.
