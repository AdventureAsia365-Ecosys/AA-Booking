# AA-823 — Booking wave 2b: hotels, room types, services and supplier net rates (bk-010)

Session S237 (Claude Code). Sources: Linear AA-823, S237 lane plan (`AA-Ecosys/docs/audits/2026-10-14-S237-lane-backlog/`,
booking lane item 5 + cross lane edits, locked decisions D1–D9), root ADR 0004a (supply facts in Booking, content in
CIS), ADR 0005 decisions 2 and 8, S236 UI spec (§3, §6.3, §7), Q17 (no customer-facing hotel photos in v1).

Delivery follows D8: branch `feat/aa-823-bk-010` carries the migration file only (plus its schema test and these
notes); `feat/aa-823-hotels-services` is stacked on it with the API, the frontend and the `REQUIRED_SCHEMA_VERSIONS`
bump.

## Decisions

- **Base = main after wave 2a and bk-009.** The task brief said to stack on `feat/aa-822-bk-008`; by the time this
  slice ran, bk-008 (#9), the suppliers code (#10) and bk-009 trip_plans (#11) were all merged to main, so both
  branches start from `origin/main` and `RESERVED_ON_OTHER_BRANCHES` in the migration guard stays empty.
- **Four tables.** `booking.hotels` (facts of ADR 0004a d1: supplier, name, style, star rating, address, CIS place,
  geo point, check-in/out, amenities, staff links, internal notes, status; human code `HTL-000123`),
  `booking.hotel_room_types` (name, max occupancy, bed types, internal notes, status), `booking.services` (one table
  for activity / transfer / guide / entrance / meal, UI spec §6.3; code `SVC-000123`; internal title, pricing unit,
  CIS place, optional CIS source reference, max group size, duration, inclusions, internal notes, status) and
  `booking.supplier_rates` (net rate rows).
- **CIS place = soft key, no FK.** `destination_id` is a `catalog.v_destination` id checked by the API (same as
  suppliers, bk-008): role `booking` has SELECT on the catalog views, not REFERENCES on `shared`. `country_code`
  follows the place. Services also carry an optional `source_system = 'cis'` + `source_id` (e.g. the catalog
  component the service delivers), CHECKed as a pair; no FK either.
- **Rates hang off a supplier contract.** A rate row prices exactly one room type or one service (CHECK
  `num_nonnulls = 1`), under a contract of the same supplier, in the contract currency, inside the contract validity
  (trigger `supplier_rate_guard`). Maker-checker comes from the contract (ADR 0005 d8): rates are written while the
  contract is a draft and are fixed once a second person publishes it ("never overwrite", ADR 0005 d2). Only rates of a
  published contract are "in force" for quoting. The reverse trigger `supplier_contract_rates_fit` keeps a draft
  contract with rates from changing its currency or shrinking its validity below a rate.
- **Rate shape:** season label, `valid_from` / `valid_to`, unit (`room_night` for rooms; the service unit `person` /
  `group` / `vehicle` / `day` otherwise, CHECKed), meal plan (rooms only: RO/BB/HB/FB/AI), pax band (`pax_min` /
  `pax_max`), `net_amount` NUMERIC(16,2), currency, notes.
- **Version items reference supply.** `trip_case_version_itinerary` gains `hotel_room_type_id` / `service_id` (at most
  one, CHECK); `version_item_costs` gains `supplier_rate_id` (provenance of a defaulted net; the line's own amount is
  what prices the version).
- **No customer-facing column anywhere** (ADR 0004a d2, O7, Q17): no description, highlights, photo. A schema test
  asserts the absence. Hotel/service `title`/`name` are internal working names.
- **No delete** on hotels, room types, services (role `booking` has no DELETE; deactivate instead). A draft rate may be
  deleted (the guard refuses once the contract is published).
- **Per-object grants**, never `ON ALL TABLES` (would re-open UPDATE/DELETE on the bk-004 append-only pricing tables
  and the bk-008 no-delete tables).
- **`conf:commercial` comment tags** on internal notes, `net_amount` and rate notes (data standards DM-6.1).

## Changed (vs. the Linear issue / lane text)

- Linear sketch `category` on hotels → `hotel_style` (free text, e.g. boutique / resort) + `star_rating` 1–5. `kind` on
  services → `service_type` (UI spec §6.3 names).
- Lane text "room types" inside hotels → its own table (rates hang off a room type, so it needs an id).
- Net rates are not columns on the hotel/service: they are rows under a supplier contract (ADR 0005 d2 versioning +
  d8 maker-checker reuse the bk-008 contract flow instead of a second approval flow).

## Tradeoffs

- Rates inherit maker-checker from the contract instead of their own approval: a correction to a published rate means
  a new contract (or expiring the old one). Simpler and matches "new rates are new rows", at the cost of one more step
  for contracting staff.
- One `services` table for five types: a few columns are irrelevant for some types (duration for a meal), but one
  list, one API and one rate shape.

## Should know

- Migration-only PR contents: `migrations/010_hotels_services_rates.sql`, `backend/tests/integration/test_bk010_schema.py`,
  `backend/tests/integration/supply.py` (clean-up helper) and these notes. No `REQUIRED_SCHEMA_VERSIONS` change (D8).
- **Known gap (ADR 0004a decision 4):** CIS connects as `aa_cis_admin`, the owner of every `booking.*` object, so the
  database does not stop CIS from reading net rates and internal notes. Only the contract, the views and review do,
  until CIS runs as a non-owner role (AA-817 follow-ups). The supply outbox (`booking.outbox`, `v_supply_outbox`,
  `v_supply_*` views, `supply.hotel.v1` / `supply.service.v1`) is out of this slice: cross-repo, own issue.
- Review fix found by the schema test: `services_source_chk` first used `length(source_id) BETWEEN …`, which is NULL
  (= passes) for `source_system = 'cis'` with no `source_id`; it now requires `source_id IS NOT NULL`.

# Code branch `feat/aa-823-hotels-services` (API + staff admin, stacked on bk-010)

## Decisions

- **Permissions reuse `supply.read` (admin, sales, contracting) and `supply.write` (admin, contracting)** from AA-822
  for every hotel, room type, service and rate route. Sales reads (it needs rates and the item picker).
- **One implementation for hotels and services** (`app/supply/records.py`, parametrised by `Kind`): list (offset
  paging like suppliers, search, status / supplier / country / place / stars or type filters, sort), detail (with room
  types for hotels and the last 20 audit rows), create, edit, deactivate / activate. Addressed by UUID or code.
- **Supplier rules:** set on create, never edited (PATCH `supplier_id` is 422 `not_editable`): rates of a record live
  under that supplier's contracts. The supplier must be active (409 `supplier_inactive`) and carry the matching
  category (hotel; transfer → transport; otherwise the service type), else 422 `supplier_category_missing`.
  Activating a record of an inactive supplier is refused.
- **Place:** the same `check_place` as suppliers (made public in `app/suppliers/service.py` together with
  `place_names` and `clean_text`): a CIS `catalog.v_destination` id, fail closed on writes, soft on reads; the country
  follows the place.
- **Service unit** cannot change once the service has any rate (409 `service_has_rates`): rates were entered per unit.
- **Rates API:** `GET/POST /booking/contracts/{id}/rates`, `PATCH/DELETE /booking/rates/{id}`, plus read lists per
  hotel (`/hotels/{ref}/rates`) and per service. Currency = the contract's (not sent); unit = `room_night` for a room,
  the service unit otherwise; validity defaults to the contract's. Draft contracts only (409 `contract_locked`).
- **Writing a rate makes the writer the contract's maker** (`supplier_contracts.updated_by`), so the bk-008
  maker-checker publish rule covers the rates: whoever added or changed a rate cannot publish the contract. Without
  this, a checker could add prices to someone else's draft and publish them unseen.
- **Rate in force** (`/booking/supply/rate-in-force`, and what items take): contract published and both validities
  cover the day; among several matches the newest `valid_from`, then a rate with a pax band, then the lowest net.
- **Version items default their net.** An item that books a room type or service and is saved without `costs` takes
  one cost line from the rate in force on its first day (trip `start_date` + `day_from` - 1, else today UTC) for the
  case `pax`: amount = rate × quantity (rooms: `max(day_to - day_from, 1)` nights, 1 room; per person: pax; per day:
  days; group / vehicle: 1). The line carries `supplier_rate_id` and a note "HTL-… Hotel · Room BB Low: 1200000.00 VND x
  2 night". Defaulting runs when the item starts booking the record, or books it and has no line yet; the response
  lists `rate_defaults` (or `rate_id: null` when nothing is in force). The AA-810 engine then prices the lines as before.
- **Supply checks on items:** a referenced record must exist (422 `unknown_supply`); a newly referenced one must be
  active (422 `supply_inactive`; items that already book a since-deactivated record keep it). A cost line may name only
  a rate of a published / expired contract (422 `unknown_rate`): draft rates are not prices yet, and it also keeps
  draft rates deletable.
- **Cost lines are compared by value** (amount, currency, note); `supplier_rate_id` is provenance only. A client that
  sends the same lines back without it (the builder before this change, or any other client) keeps the stored lines,
  their provenance and the version price.
- **Item picker:** `GET /booking/supply/options?q=&kind=&supplier_id=` lists active room types (of active hotels) and
  active services; the rate drawer uses it with `supplier_id`.
- **Frontend:** `/hotels` grid (search, status, country, stars, sort, server paging) + hotel drawer (`?hotel=HTL-…`:
  facts, room types with add / edit / deactivate, net rates, activity; Edit / Deactivate), add / edit hotel drawer;
  `/services` list + `/services/{SVC-…}` detail (Overview, Rates) + add / edit drawer; supplier page **Rates** tab
  (pick a contract, add / edit / remove rates while it is a draft); proposal item drawer "Hotel room or service"
  typeahead (no cost line → the API defaults the net; the item card shows the booked room / service). Nav entries
  Hotels and Services are `shipped: true`. Kit tokens and components only.

## Changed

- Lane text "GET/POST/PATCH + deactivate" kept; added room-type routes, rate routes and the two item helpers (options,
  rate-in-force) because the Linear done-when needs rates and items that use them.
- `/hotels` is a data grid with a drawer (Figma 07 hotel cards were not copied: the DataTable keeps paging, filters and
  mobile behaviour consistent with the other lists).
- No "Used in" tab on a service yet (the WaveFrame listed one): it needs a query over version items, left for the
  proposal reports.

## Tradeoffs

- Defaulting books one room for the nights of the item; staff edit the line for more rooms or a different meal plan.
  A rooms count on items would be a schema change (later).
- The hotel drawer's rate table repeats the hotel name per row; acceptable for a handful of room types.
- The supply picker searches all suppliers; the place of the trip is not used to narrow it yet.
