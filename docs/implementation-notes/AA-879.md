# AA-879 — CI gate parity (AA-Booking part)

Booking was the model for the parity work (failing pip-audit, gitleaks, resource-ID check and a Frontend
Build job already existed). What it lacked: a blocking image scan and a security-header check on deploys.

## Decisions

- **Trivy blocking, same settings as CIS**: `exit-code: 1`, `ignore-unfixed: true`, `trivyignores:
  .trivyignore`. Reviewed a real report first (main run 39622898902, 21/10/2026): 44 HIGH OS findings on the
  base image, none with a fixed version, so the flip turns no current PR red and `.trivyignore` starts empty.
  `.github/scripts/check_trivyignore.py` is a byte copy of the AA-CIS-App script (unit-tested there): every
  entry needs a `# reason` line and an `exp:` date at most 90 days ahead.
- **Header check through `vercel curl`, no new secret.** Booking has no `VERCEL_AUTOMATION_BYPASS_SECRET`.
  `vercel curl` (CLI already pinned, `vercel@60.0.1`) reads the project's own automation-bypass token through
  the API with `VERCEL_TOKEN` and sends it only to the deployment. Tested locally against a live Booking
  preview. Gotcha found while testing: `vercel curl` forwards unknown flags (even `--token` / `--scope`) to
  curl, so the token and team come from the environment (`VERCEL_TOKEN`, `VERCEL_ORG_ID`). Never add `--debug`:
  it prints the bypass token.
- **Path `/login`**: the only page that answers 200 without a session (others redirect there).
- **Three headers added to `frontend/next.config.ts`** (HSTS, minimal CSP, Permissions-Policy) so Booking sends
  the same six as CIS and TripPlanner (AA-876 / AA-885). The live preview checked before the change had only
  three (the check reported `csp-frame-ancestors permissions-policy` missing; HSTS came from Vercel). Safe for
  the app: no iframe, no camera/microphone/geolocation use; sign-in is a link to `/api/auth/signin` (redirect to
  Cognito managed login) and sign-out a `fetch` + navigation, so `form-action 'self'` does not apply to them.
- **The step runs on both targets** (preview and production), inside the "Vercel deploy" job, after the deploy.

## Changed

- `.github/workflows/ci.yml` (Docker Build Check: ignore-file check step + blocking Trivy).
- `.github/workflows/vercel-deploy.yml` (step "Check the security headers").
- New: `.trivyignore`, `.github/scripts/check_trivyignore.py`, `.github/scripts/check_security_headers.sh`.
- `frontend/next.config.ts`, `CONTEXT.md`.

## Tradeoffs

- The header step makes "Vercel deploy" red when the headers are missing, not a separate check: the workflow
  has a `frontend/**` path filter, so none of its checks can be a required check anyway (a required check that
  does not run blocks every backend PR).
- If someone removes the project's "Protection Bypass for Automation" in Vercel, the step goes red with a hint
  ("a Vercel login page here means the protection bypass did not work").

## Should know

- Local verification: `npm run lint`, `npm run typecheck`, `npm run build` pass; `next start` + the script
  against `http://localhost:<port>/login` → all six headers.
- **Branch protection** (orchestrator): add "Frontend Build" (exists since ADR 0004, non-required until now).
  The 5 required names are unchanged.
- The first real run of the header step is this PR's own preview deploy (the PR touches `frontend/**`).
