# AA-678 — AA-Booking bootstrap (health slice)

Scope of this pass (S235, Gate-1): repo scaffold, 5-check CI, `bk-001` first slice,
`GET /booking/health` + `GET /booking/health/ready`, Dev deploy workflow. Root ADR 0004 is the
design source; this file records what the ADR did not pin down.

## Decisions

- **bk-001 = ADR 0004 "Foundation" + "Tier A" only**: schema, role `booking` NOLOGIN, grants,
  default privileges `FOR ROLE aa_cis_admin`, `customers`, `customer_otps`, `customer_sessions`,
  `media_files`, `audit_logs`, `inbox_events`. All Tier B tables (staff, trip cases, areas,
  country profiles) wait for their open decisions (O1, O6, O7). No enum types at all in bk-001,
  so nothing here is expensive to change later.
- **`inbox_events` is created, but no consumer exists.** The table has no open decision against
  it; the intake consumer (O3/O6) is out of scope. Drop the block before the copy PR if the
  orchestrator reads "no guest intake" as "no inbox table either" — nothing references it.
- **Readiness reads `booking.v_schema_versions`**, a view in Booking's own schema over
  `shared.schema_versions WHERE version LIKE 'bk-%'`. The view runs with its owner's rights
  (`aa_cis_admin`), so role `booking` needs no grant on schema `shared` and the CIS grant
  migration stays out of the bootstrap. `security_barrier` is on; INSERT/UPDATE/DELETE on the view
  are revoked (a simple view is auto-updatable and would write into `shared.schema_versions`).
- **Role `booking` gets `USAGE` on the schema, not `USAGE, CREATE`** (ADR 0004 table says both).
  All DDL goes through bk-NNN applied by DB Migrate as `aa_cis_admin`; an app role that can create
  objects would own them and bypass the migration path. One line to add later if ever needed.
- **`audit_logs` is append-only for the app** (UPDATE/DELETE revoked).
- **Uniqueness on live rows only**: `customers` email (case-insensitive) and phone are unique where
  `deleted_at IS NULL`, so a soft-deleted customer can register again. ERD v2 said plain `unique`.
- **`text` instead of `varchar`** for string columns (ERD v2 uses `varchar` without lengths; same
  semantics in PostgreSQL).
- **`DB_SSL`**: the app passes `ssl="require"` to asyncpg by default (program rule). Only
  `ENVIRONMENT=test|local` may set `DB_SSL=disable` (CI's Postgres service has no TLS); any other
  environment refuses to start the DB pool with SSL off.
- **Readiness contract**: 200 `{status:"ok", db:"ok", schema_version:"bk-001"}` only when the DB
  answers `SELECT 1` and the highest registered `bk-NNN` is at least the version the code needs
  (`REQUIRED_SCHEMA_VERSION`). Otherwise 503 with `db` = `ok` / `error` / `not_configured`.
  Error bodies carry only the exception class name, never the DSN or message.
- **Lazy pool** (`min_size=0`): the process starts and `/booking/health` answers even when the DB is
  down, so the ALB health check never depends on the DB (ADR 0004 decision 9).
- **CI check 5 = Security Audit** (pip-audit, failing) **plus a gitleaks secret scan** in the same
  job, keeping the CIS check name so branch protection reads the same. Chosen over a type checker:
  the app is ~150 lines, while this repo is the one that carries the DB role/password flow, so a
  committed secret is the more likely and more expensive mistake.
- **Deploy workflow does not change `desired_count`.** Scaling 0 → 1 is a billable, approved step.
  With `desired_count = 0` the deploy still registers the task definition and updates the service,
  then skips the live smoke with a warning.
- **Deploy is a no-op until configured**: if the `AWS_ROLE_ARN` variable is not set on the `dev`
  environment, the deploy job is skipped with a warning instead of failing every push to main
  before Infra-2 applies.

## Changed (vs. the AA-678 issue / ADR 0004)

- AA-678 Done-when says "Migration 001 creates booking schema v2"; bk-001 is the first slice
  (ADR 0004 O5, Gate-1 answer "bk-001 first slice").
- No `frontend/` and no `docs/erd/` move in this pass (frontend waits for O1/O8; the ERD move is a
  root-repo change for the orchestrator).

## Tradeoffs

- View over `shared.schema_versions` vs. a CIS grant migration: the view keeps the bootstrap free of
  cross-repo ordering, at the cost of a Booking object that reads a CIS table through its owner's
  rights. It exposes Booking's own rows only.
- Pinned direct dependencies only (no lock file), as in CIS; versions picked at least two weeks old.

## Should know

- bk-001 must be applied by DB Migrate as `aa_cis_admin` (confirm the RDS master user live in
  `check` mode). Run as any other role it fails on `ALTER DEFAULT PRIVILEGES FOR ROLE aa_cis_admin`
  unless that role is a member of `aa_cis_admin` — by design.
- After apply, Nghiep sets `ALTER ROLE booking WITH LOGIN PASSWORD …` out-of-band and stores the
  DSN in `booking/dev/database-url`; the integration test simulates that step with a CI-only value.
