# AA-682 — Operations MVP, slice S1: supplier bookings + supply track (bk-026)

Linear AA-682 (operations MVP: supplier bookings, trip checks, invoices + payment schedule, supplier bills, My
Payments; manual payment marking only). Sources: the S252 design (root `.tmp-session/s252/aa682/design.md`, saved with
the S252 audits) **with every "critic" edit applied**, the adversarial critic (`critic.md`, blocking issues B1–B9 and
notes 1–18), this repo's `CONTEXT.md`, `docs/architecture/db-schema-reference.md` (Booking at bk-025),
`docs/database/schema-ownership.md`, the lessons log (migrations; "a CHECK value exists before its writer"). Session
S252, agent Claude Code. Slice S0 (root DM-7 retention rows, schema ownership, ERD design page) ships in the root
repo PR `docs/aa-682-s0-s1`; this file covers S1. Nothing from S2–S5 (trip checks, invoices, payments, bills, My
Payments) is built here.

## Decisions

- **D1–D16 of the design are taken as written** (summary): case status stays the 13 DB values and "Confirmed &
  Booked" is a computed supply badge (D1); post-sale statuses move only by the system, forward from facts (D2);
  supply and money may happen in either order (D3); one generic transitions table `ops_transitions` + one trigger
  function for supplier bookings now, invoices / bills later (D4); files in a private ops-docs bucket with a KMS CMK
  through the base64 JSON path (D10); no RLS on the new tables (D11); B2B cases get supplier bookings but no voucher or
  confirmation files (D12, DM-6.8); the B2B desk and the supplier booking are one action both ways (D13); no new
  role (D16). D5–D9, D14, D15 are S3/S5.
- **Migration bk-026 = S1 only.** `ops_transitions` (+ supplier-booking edges), the post-sale case edges of bk-026
  (critic B1: the money edges wait for bk-028), the fact guard `trip_cases_post_sale_guard`, `ops_files`,
  `supplier_bookings`, `v_trip_case_supply_state`, three settings rows. Key re-checked on the day: origin/main of
  AA-Booking and AA-CIS-Infra end at bk-025 and no branch of either repo holds a `026_` file → **bk-026**, held by the
  Infra copy branch `chore/aa-682-copy-bk-026`.
- **"Live" supplier booking = `pending`, `requested`, `confirmed`** everywhere (critic B3): the partial unique index
  on `version_item_id`, the supply view, the guard, the reopen rule. A `declined` row never blocks a replacement
  booking with another supplier (B2C). B2B: a declined line is final (the agency was told `line.declined`), so no
  replacement there.
- **Supply state `none` means "nothing to book"**, not "no live booking" (critic: `none` passes the pre_departure gate).
  The view counts the supply items of the approved version (room type or service) and how many are booked; a case
  whose items were all declined with no replacement is `confirming`, never `none`. B2B: an item whose on-request line
  is confirmed counts as booked (answered on the desk before or without a supplier booking); an item whose line is
  declined or cancelled needs no supply (the agency was told). This is stricter than the design's "live / confirmed
  counts" and keeps a half-booked trip from ever passing as `none`.
- **Auto-advance on the first request, not on generate** (design §4 "first request"): pending bookings are staff's
  to-do list, the case moves to `supplier_confirming` once a supplier was actually asked. Back to `confirmed` when no
  live booking is left. System moves: empty `booking.actor`, status note "Auto: …", audit actor `aa682:advance_case`.
- **No B2C `pre_departure` in bk-026.** The guard needs a paid invoice for B2C, which exists only with bk-028, so
  bk-026 refuses B2C `pre_departure` outright and bk-028 replaces the function. B2B reaches it with supply `booked` /
  `none` (the lifecycle job is S2).
- **No document of any kind on a B2B case** (design D12 names vouchers; a supplier confirmation PDF names travellers
  just the same, and Q11 says "confirmation ref only"). The DB guard and the API both refuse it.
- **Lock order hold → case → booking.** The AA-974 cancel locks the hold, then updates the case; the supplier-booking
  writes of a linked booking lock the hold first too, so the two never deadlock (race test in `test_bk026_b2b.py`).
- **Generate refuses mixed cost currencies** (critic note 17) for the whole call (409 naming the item), rather than
  silently leaving that item's net empty; staff add that one by hand.
- **API transport cap 3 MiB per document** (same as AA-835 photos, Vercel's 4.5 MB body limit); the DB allows 10 MB
  (`ops_docs_max_bytes`) for a later presigned-POST path (design Q10).
- **FK indexes** on every new FK (critic note 2), partial where the column is mostly NULL.
- **PII tags** (critic note 9): `supplier_bookings.notes` is `pii:free_text; also conf:commercial`, `cancel_reason`,
  `ops_files.file_name` and `removed_reason` are `pii:free_text`, `ops_files.s3_key` is `pii:payment; also pii:name`.
  The tag grammar is `tag; also tag` (bk-018 parser), not `tag (also tag)`.

## Changed (vs. the design)

- §5 `POST /ops-files` accepts the kinds of every slice in its body schema but answers 422 `kind_not_available` for
  payment evidence, bills and payouts until bk-028 / bk-029 replace `ops_files_guard`.
- Added `GET /booking/supplier-bookings/summary` (dashboard tile "Supplier answers pending", design §6) and
  `GET /booking/supplier-bookings/{id}`; the case list response carries `unbooked_items` (items without a live
  booking and why Generate skips them) and `documents_allowed`.
- The desk list rows carry `supplier_booking` (the code of the live booking that covers the line).
- The Infra ops-docs bucket + CMK + task-role policy + `OPS_DOCS_BUCKET` env (design S1 "Infra PR applied before the
  code deploy") are **not** in this lane (the lane was told: Infra = the bk-026 byte copy only). Without them the
  upload / download routes answer 503 `ops_storage_unavailable` and every other S1 route works, so the code can deploy
  first; the bucket PR is a follow-up before the voucher part of the Done-when.
- Fix round 2 (review): generated room bookings take their nights on the channel's convention
  (`supplier_bookings._nights`). B2C = `supply_rates.quantity('room_night')` = max(day_to − day_from, 1), the same
  rule `versions.default_cost` priced the item with, so net and nights agree on the row; B2B = day_to − day_from + 1,
  the inverse of `holds._open_case`. The first cut used +1 for both, which asked a B2C supplier for one night more
  than was costed and sold. Pricing was not changed (no migration, no data on Dev yet); the one convention per
  channel is written in CONTEXT.md. The unit test covers both channels and a same-day item; the integration fixture's
  room item is now days 1-3 (2 nights); the Infra live-check generate SQL follows the same CASE and prints
  `b2c_room_nights`.
- PRD §7–9 (critic note 1) still unread: the PDF cannot be read in WSL; S0 Windows task stays open.

## Tradeoffs

- Generic `ops_transitions` vs. one edges table per entity: one function to review and the same pattern for bk-028 /
  bk-029 (design D4), at the cost of a TG_ARGV parameter.
- Status moves stay in the app (`advance_case`) and are double-checked by the guard, rather than a trigger on
  `supplier_bookings` moving the case: the app needs the move in the response and the audit row; the guard keeps any
  other writer (a script, a later job) honest.
- The supply view recomputes per case (LATERAL counts) instead of a stored counter: no drift, cheap at Booking's size.

# Slice S2: trip checks + case lifecycle (bk-027)

Session S253, agent Claude Code (subagent lane; the orchestrator does the live steps). Sources: the same S252 design
(§2 S2 row, §3.2 bk-027, §4, §5 trip-check routes, §6 `/trip-checks` + case Checks tab + drawer, §9 jobs) and critic
(B7, B8 respected), the data standards DM-6.1 v1.3 (`emergency_contact` class) and the DM-7 row of
`booking.trip_case_checks` (already in the root register: contact fields and notes nulled at trip end + 90 days by
`bk_case_lifecycle`, first run DRY RUN).

## Decisions

- **Key bk-027** (live Dev at bk-026 per the 27/10 04:12 UTC schema dump; no `027_` file on any branch). One file,
  `migrations/027_trip_checks_lifecycle.sql`, merged alone first (lesson S249 / AA-847), then the Infra byte copy.
- **Checks are rows, three standard + custom.** `pre_trip_recheck`, `emergency_contact`, `insurance` (at most one of
  each per case, partial unique index) and any number of `custom` rows. Standard rows carry a fixed English title
  (seeded; the guard refuses a new title), custom rows a staff title. `status` open → done | not_applicable, and back
  to open (reopen); done ⇔ `done_at`, `done_by` only on done.
- **Seeding is a trigger on `trip_cases`** (AFTER INSERT OR UPDATE OF status, start_date): entering `confirmed` seeds the
  three rows ON CONFLICT DO NOTHING, which covers the B2C version approval (UPDATE) and the B2B confirm that inserts
  the case at `confirmed` without touching `holds.py`; leaving and re-entering `confirmed` adds nothing. Due date =
  `start_date - pre_departure_days` (bk-026 setting, 14). The same trigger moves the due date of a standard row still
  `open` on the derived date when the start date changes (done rows and custom rows keep theirs).
- **Backfill = the open sold cases** (`confirmed` .. `on_trip`, not deleted); `completed` and `cancelled` cases get no
  rows (nothing left to check).
- **No emergency contact on a B2B case, enforced by the DB** (DM-6.8): the seeded row is `not_applicable` with no due
  date, and `trip_case_checks_guard` refuses any other status or any contact field on it, whoever writes.
- **`ON DELETE CASCADE` from the case.** Booking only soft-deletes cases; a hard delete is a reviewed script, and the
  check rows have no meaning without their case. Without it every test module (and any future purge script) that
  deletes a case at `confirmed` would have to know about checks. Role `booking` still has no DELETE on the table.
- **`cleared_at` + CHECK**: the lifecycle job nulls the emergency contact and every note of a case's checks once the
  trip ended `emergency_contact_keep_days` (90) ago and stamps `cleared_at`; a CHECK keeps those fields empty after
  that and the guard keeps `cleared_at` final (no re-entry of a third person's phone into an old trip).
- **`v_trip_check_board`** = one row per open sold case: stored counts (open / done / not applicable / overdue, next
  due) + the derived checks `suppliers_confirmed` (supply state `booked` or `none`, the bk-026 view) and
  `payment_verified` (`NULL::boolean` until bk-028 replaces the view; the column list stays).
- **The reminder dedupe index moves forward to bk-027** (design had it in bk-028): the S2 jobs already write reminders
  (gate notices, supplier answers, checks due). `notifications_reminder_uq` = UNIQUE (recipient_type, type,
  entity_id, data->>'reminder_key') WHERE data ? 'reminder_key' (critic B7: recipient_type included). bk-028 no longer
  creates it.
- **Settings rows** `trip_check_reminder_days` 3 and `emergency_contact_keep_days` 90 (policy data, values not code).
- **Tags**: `emergency_contact_name` `pii:emergency_contact; also pii:name`, `emergency_contact_phone`
  `pii:emergency_contact; also pii:contact`, `note` and `title` `pii:free_text`. The bk-018 tag test learns the three
  DM-6.1 v1.3 classes (`government_id`, `health`, `emergency_contact`), the same list as Infra `TAG_CLASSES`.
- **The lifecycle's "today" is the ops date.** `bk_case_lifecycle` reads the date in `b2b_ops_timezone` (AA-974
  setting, Asia/Ho_Chi_Minh; a bad value falls back to it) and sets the transaction `TimeZone` to that zone, so the
  bk-026 guard's `current_date` is the same day whatever the server or pool zone (tested with UTC-11 and UTC+14
  sessions). Runs at 01:00 UTC = 08:00 in Vietnam, when the UTC and ops dates agree.
- **Gates.** Hard gates are the guard's facts: supply `booked` / `none`, and for B2C the money track (`paid`, the only
  B2C source of `pre_departure` once bk-028 adds that edge). Until S3 every B2C case is reported blocked `not_paid`
  (one notice) and keeps its status: that is what the bk-026 guard already enforces. **Open checks never block** a
  move (the trip date is a fact; a stuck `confirmed` case during the trip helps nobody): their count travels in the
  gate notice and in the run result (`open_checks_at_move`), and `bk_ops_reminders` chases them. Design §9 listed
  "open checks" among blocked gates; this reads it as "reported", not "refused".
- **Moves chain in one run** (catch-up after missed days) and each move is its own savepoint: a refusal keeps the
  moves before it. A blocked gate after the start date targets `on_trip` (a second, sharper notice than the
  `pre_departure` one). No end date → `completed` blocked `no_end_date` once the trip started; no start date →
  `pre_departure` blocked `no_start_date`.
- **DRY RUN first, DM-7.2 style**: manual runs default to DRY RUN; the scheduled run stays DRY RUN until one live run
  over every case (no `case_ids`) has succeeded. A scoped live run (`case_ids`, ≤ 50, the synthetic Dev check) never
  unlocks the schedule. The nulling of emergency contacts uses the same mode.
- **`bk_ops_reminders` S2 parts** (design §2 lists them in S2): supplier answers waiting > `supplier_answer_days` (to
  the requester, key includes `requested_at` so a re-request reminds again) and checks due within
  `trip_check_reminder_days` or overdue (to the assignee, key includes the due date). No DRY RUN: it writes
  notifications only, deduped by the index.
- **Routes** (design §5): `GET /trip-checks` (status open default / done / not_applicable / all, `due_before`,
  `assignee` key / `me` / `none`, `code`, `case`, `q` on case code or title; only open sold cases), `GET|POST
  /trip-cases/{ref}/checks`, `PATCH /trip-checks/{id}`. Plus `GET /case-lifecycle/runs` (ops.read) so the DRY RUN
  result and the live moves are readable on Dev without DB access (the E2E session is read-only).
- **Audit without personal values**: a check's audit row lists `note` / contact fields as `"(set)"` or null, never
  the text (audit rows are kept longer than the 90-day contact window).
- **Staff UI**: `/trip-checks` (nav `shipped: true`, page rule widened to contracting, which has `ops.*`), the case
  **Checks** tab (derived checks card + checks table + Add check), one shared drawer
  (`trip-checks/_parts/CheckDrawer.tsx`) built on the kit `FormDrawer`; `TripCheckStatusBadge` in
  `ui/booking/StatusBadge.tsx` (Booking-owned file, not kit core). English copy; never claims an e-mail.

- PRD §7–9 still unread (S0 Windows task stays open).

- Seeding by trigger vs. in `versions.approve_version` and `holds._open_case`: one place, both entry paths (and any

- The run-script mimics the lifecycle step in SQL (it may not import app code) and, on apply, also queues a real scoped
  live job and an unscoped DRY RUN job for the worker, so the job code itself is exercised on Dev.

# Slice S3: invoices + payment schedule + manual payments (bk-028)

Session S253, agent Claude Code (subagent lane; the orchestrator does the live steps). Sources: the S252 design (§2 S3
row, §3.3 bk-028, §4 machines, §5 billing routes, §6 `/billing` + case Billing tab, §9 `bk_ops_reminders`, §11
defaults) with every "critic" edit, the critic (B1, B4, B5, B6, B8, B9; notes 2, 3, 4, 5, 6, 8, 11, 12, 13, 14, 18),
`CONTEXT.md`, the S1 / S2 code (`app/ops/*`, routers, `jobs`, notifications, staff UI), the lessons log (migrations:
"a CHECK value exists before its writer", "code needing a new migration merges after the apply").

## Decisions (migration, commit 1)

- **Key bk-028**, one file `migrations/028_invoices_payments.sql`, merged alone first (lesson S249 / AA-847), then the
  Infra byte copy, DB Migrate check + apply, then the code PR (adds bk-028 to `REQUIRED_SCHEMA_VERSIONS`).
- **Money is `numeric(16,2)` everywhere** (the brief; the design said 14,2 for invoices / payments). Same width as
  `version_item_costs.net_amount`.
- **Money states are derived, enforced by the DB** (design D5): `booking.invoice_settle(id)` is the only writer of
  `sent / partially_paid / paid` (called by AFTER triggers on `invoice_items` and `payments`); `invoices_guard`
  recomputes on every UPDATE and refuses a status that is not what the verified, non-voided payments imply, and a
  `total_amount` that is not the sum of the lines. A direct `UPDATE invoices SET status = 'paid'` as role `booking`
  fails (integration test). Overpayment stays `paid` (negative balance); a refund that would take the net paid below 0
  is refused at verify.
- **A void keeps the money invariants (review S253)**: `payments_guard` refuses any void when the invoice is not live
  (a cancelled invoice holds net verified paid 0, so its payments are final), and refuses voiding a verified receipt
  when it would take the net paid below 0 (`void the refund first`). Without it, receipt + refund verified then the
  receipt voided left net -X on a `sent` invoice (not cancellable, balance above the total), and voiding either
  payment of a cancelled invoice left a cancelled invoice holding money. Voiding a verified refund only raises the net
  (at worst an overpayment, already a known `paid` state), so it is not checked.
- **Lock first (critic B4).** `invoice_settle` and `payments_guard` take the invoice row `FOR UPDATE` before summing;
  the API also locks case → invoice → payment at the start of every money write. Test: two concurrent verifies on one
  invoice end `paid`.
- **Maker-checker in the DB**: CHECK `verified_by <> recorded_by` plus a guard message `maker-checker` (the API answers
  403 `maker_checker` before the DB is reached). Verify needs the evidence file unless the method is `cash`.
- **Amendment rule (critic B5)**: draft lines and schedule rows change freely (the version total line is inserted once
  with the version total and is locked); after send lines are only appended as `adjustment`s, the total and the state
  follow (a paid invoice can drop to `partially_paid`); schedule rows the verified payments already cover (waterfall,
  oldest due first) are frozen, and a changed / new row comes after them. After send, lines and rows change only in
  the amendment window (`invoices.amending`, see "Amendment window" below); Σ schedule = total is checked immediately
  at send and when the window closes.
- **Idempotency (critic B6)**: `idempotency_key` + `request_sha256` NOT NULL on `invoices` (unique per case) and
  `payments` (unique per invoice).
- **One live invoice per case** (partial unique index); a draft is soft-deleted (`deleted_at`, final); a cancelled
  invoice is final and a new one may follow.
- **Case money edges moved here (critic B1)** with the replaced fact guard `trip_cases_post_sale_guard`:
  `invoice_sent / payment_pending / paid` must equal the sent invoice's `sent / partially_paid / paid`, never on B2B;
  B2C `pre_departure` needs the invoice `paid`; back to `confirmed / supplier_confirming` only once the invoice is
  cancelled; reopen refused while a supplier booking is live, an invoice is not cancelled or a payment waits for
  verification (critic B9). No back-step from travel statuses (critic note 12).
- **`ops_files_guard` replaced**: payment evidence of an existing, unverified, non-voided payment; the evidence of a
  verified payment is never removed.
- **`v_trip_check_board` replaced** (same columns): `payment_verified` = invoice paid (B2C), NULL on B2B. The S2 test
  of the board and the trip-checks API now expect `false` / "open" for a B2C case with no paid invoice.
- **Settings rows** (§11 Q4 defaults, values not code): `deposit_due_days` 3, `balance_due_days_before_start` 30,
  `payment_due_soon_days` 7, `payment_overdue_reminder_days` [1, 7]; **placeholders** for `invoice_issuer` and
  `payment_instructions` (public repo: the real values are a DB Migrate run-script).
- **`received_on date`** instead of the design's `received_at` (a manual entry is a day, not an instant), plus optional
  `received_amount` / `received_currency` (critic note 4, informational, never counted).
- **Grants**: `invoices` / `payments` SELECT, INSERT + column UPDATEs, never DELETE; `invoice_items` /
  `payment_schedule` also DELETE (the draft edit and the uncovered rows of an amendment; the guards refuse the rest),
  never TRUNCATE. cis_app reads nothing.
- **Tests replaying older files**: the bk-026 / bk-027 re-run tests now replay the later files after the re-run
  (`apply_migrations(only=range(next, 1000))`), because bk-028 replaces functions / a view those files create.

## Decisions (API, jobs, UI; commit 2)

- **Modules**: `app/ops/invoices.py` (create / edit draft / delete / send / cancel / amend / remind, reads, case Billing
  tab, KPIs, case-cancel cascade, money badge), `app/ops/payments.py` (record / edit / verify / void, reads),
  `app/ops/money.py` (pure: Decimal amounts in minor units, default schedule, staff schedule check, waterfall, canonical
  request hash, card-number refusal, Idempotency-Key check), `app/ops/track.py` (**one** `advance_case` for the supply
  and the money track; `supplier_bookings.advance_case` delegates to it, its SQL fragments unchanged), router
  `app/routers/billing.py`. `REQUIRED_SCHEMA_VERSIONS += bk-028`.
- **Permissions**: `billing.read` / `billing.write` = admin, sales; `payment.verify` = admin. Contracting sees no
  customer money (design §5): `GET /trip-cases/{ref}` returns `money: null` without `billing.read`. **None of them is in
  the preview cap** (critic note 8): bill-to snapshots and payment references stay off unmerged preview code.
- **Maker-checker**: 403 `maker_checker` when the verifier recorded the payment (before the DB, which refuses it too).
  **Voiding a verified payment needs `payment.verify`** as well as `billing.write` (sales void only their unverified
  mistakes): undoing verified money is the checker's act. Not in the design; it closes "sales voids the balance".
- **Idempotency-Key** is required on the two creating writes (create invoice, record payment / refund). Send, cancel,
  verify, void, remind are idempotent by state (a replay answers the current row), so they take no key. Replay = 200 +
  `replayed: true`; another body = 409 `idempotency_conflict`. The hash covers the business fields (not
  `allow_duplicate_reference`, so "record anyway" after a 409 `duplicate_reference` reuses the key). The staff BFF now
  forwards `Idempotency-Key` (8–200 printable ASCII) and the UI makes one key per opening of a form.
- **Evidence order** (critic note 6): record → `POST /ops-files` (kind `payment_evidence`, entity the payment) → the
  upload sets `payments.evidence_file_id` in its transaction (newest file wins while unverified). The Record dialog does
  both in one click; a failed upload leaves the payment recorded and says so.
- **Case money track**: a B2C case follows its sent invoice (forward on verify, back on void / amendment, back to
  `supplier_confirming` / `confirmed` on cancel). After departure nothing steps back; a void or refund then raises a
  staff `invoice.balance_reopened` (critic note 12).
- **Case cancel cascade / reopen** (critic B9): cancel soft-deletes a draft invoice, keeps a sent one and notifies staff
  (`invoice.case_cancelled`); reopen = 409 `live_invoice` while an invoice is live or a payment waits.
- **Amendment** (`POST /invoices/{n}/amend`): adjustment lines appended; `schedule` = the new rows after the covered
  ones, or (omitted) the difference lands on the last uncovered row / a new `other` row; the writes run inside the
  amendment window (`amending = true` first, `amending = false` last, one transaction) and a schedule mismatch at the
  close is a 409 `invalid_amendment`. Customer feed row `invoice.updated`.
- **Customer rows, no e-mail** (design D15): `invoice.sent`, `invoice.updated`, `invoice.cancelled`,
  `payment.reminder` (manual, once a day), `payment.due_soon` / `invoice.overdue` (job). `notify_customer_once` added
  (ON CONFLICT DO NOTHING on the bk-027 index; `recipient_type` keeps staff and customer rows apart). The staff
  preference vocabulary (`STAFF_TYPES`) is unchanged: operations rows are work items, not switchable preferences (S1 /
  S2 did the same).
- **bk_ops_reminders payment part**: due-soon rows (`payment_due_soon_days`) and overdue rows at the steps of
  `payment_overdue_reminder_days` ([1, 7], the highest step reached), one staff row (the case's active sales owner,
  else the shared queue) + one customer row each, read in the ops time zone (the job transaction sets `TimeZone`).
  Result gains `payments_due_soon`, `payments_overdue`, `payments_notified`, `customer_rows`.
- **KPIs**: per currency + a USD total at each version's `fx_rate_locked` (critic note 5: the rate the quote was sold
  at). Received this month = verified receipts − refunds by `received_on` in the ops month.
- **Card numbers**: a 13–19 digit run starting 3–6 that passes Luhn (spaces / dashes allowed) in the reference or the
  note is 422 `card_number_not_allowed`; longer digit runs (bank transaction ids) pass.
- **UI** (English; kit components): `/billing` (4 KPIs, Invoices / Payments tabs, server paging, URL filters),
  `/billing/invoices/[number]` and the case **Billing** tab share `billing/_parts/InvoiceView.tsx`; the 4-step
  `InvoiceForm.tsx` (approved version → adjustments → schedule → review) also edits a draft and amends a sent invoice;
  `PaymentDialogs.tsx` (Record with optional evidence, Verify, Void, evidence list); `/billing/payments/[ref]`. Case
  header `MoneyBadge` (Invoice draft / To pay / Overdue / Paid in full). Nav "Payments & Invoices" shipped. Form
  arithmetic in BigInt cents (`_parts/money.ts`); the API is the authority.

## Amendment window instead of deferred sums triggers (S253, Infra X1 lint)

- **Why.** bk-028 checked Σ schedule = total of a sent invoice with three `DEFERRABLE INITIALLY DEFERRED` constraint
  triggers (`invoices_sums_check`, `invoice_items_sums_check`, `payment_schedule_sums_check` →
  `invoice_sums_check()`), because an amendment changes lines and schedule rows in one transaction. AA-CIS-Infra
  `db/run_migration.py` (`DEFERRAL_RES`, rule X1) refuses any deferred constraint trigger and `SET CONSTRAINTS …
  DEFERRED` in a file that runs under the owner-role switch (every `booking/` file): work queued for COMMIT runs after
  the switch's ownership post-check, as whatever role is current then. The lint failed on the three triggers; bk-028
  (merged in #111, not yet copied to Infra or applied) is changed in place.
- **Decision.** `booking.invoices.amending BOOLEAN NOT NULL DEFAULT false` (column UPDATE granted to `booking`), the
  amendment window:
  - `invoice_items_guard` and `payment_schedule_guard` (which lock the invoice row first) refuse any change to a
    sent / partially_paid / paid invoice's lines or rows unless `amending` is true; drafts change freely as before;
    append-only lines, frozen covered rows and "changed rows after the covered ones" still apply inside the window.
  - `invoices_guard`: the window opens (false → true) only on an invoice already sent, never in the statement that
    sends it (`invoices_amending_chk` also keeps it off drafts and cancelled invoices); no cancel while it is open,
    even in the statement that closes it. Whenever a sent / partially_paid / paid invoice is written with
    `amending = false` (the send, the close true → false, every settle), the schedule must have rows that add up to
    the total, checked immediately (same message as before: `the payment schedule adds up to X but the total is Y`).
  - `payments_guard` refuses a verify or a void while the invoice is amending (`… is being amended; finish the
    amendment first`, check_violation → 409 `payment_not_verifiable` / `payment_not_voidable` in the API).
  - `invoice_settle` never touches `amending`; the three constraint triggers and `invoice_sums_check()` are gone.
- **App.** `invoices.amend` sets `amending = true` (`AMENDING_SQL`) before the first line / row write and false after
  the last, in the route's transaction; a mismatch at the close is a 409 `invalid_amendment` (was `SET CONSTRAINTS ALL
  IMMEDIATE`). The send path is unchanged: the guard checks the sums at send. No other path writes a sent invoice's
  lines or schedule. The row-count check of an amendment now runs before the first write (pure Python, same 422).
- **Tradeoffs.** A flag can be committed true by a direct writer (the API never does: it closes the window in the same
  transaction). That state is safe by construction: no verify, void or cancel, and the window only closes with the
  sums right. Recording a payment stays allowed while amending (it moves no money and leaves the invoice as it is);
  the views still show the schedule as it stands. The alternative, one "replace lines and schedule" function that
  checks at its end, would have moved the amendment logic (waterfall, covered rows) into SQL; the flag keeps the
  per-row guards and the Python planner as they were.
- **Tests.** `test_bk028_schema.py`: direct line / schedule edits of a sent invoice without the window are refused;
  inside the window lines stay append only and covered rows frozen; closing with a wrong sum fails at once and the
  whole transaction (open, edit, close) rolls back; the window does not open on a draft or with the send; verify and
  void refused and cancel refused while amending, record still accepted; the concurrent schedule-change test now
  opens the window, which waits on the verify's invoice row lock. `test_bk028_billing_api.py`: after `amend` the flag
  is false and a direct schedule edit is refused. Unit: the window opens before the first write and closes after the
  last; a close that raises check_violation is a 409.
- **Lint.** `python3 db/check_migration_files.py` of AA-CIS-Infra on a copy at
  `db/migrations/booking/028_invoices_payments.sql`: ok, 0 problems (was 3 × X1 deferral).

## Decisions (migration, commit 1)

- **Key bk-030, not bk-029.** The design says bk-029; AA-996 took `029_catalog_geo_profiles.sql`. One file,
  `migrations/030_supplier_bills_payouts.sql`, in its own commit with `tests/integration/test_bk030_schema.py`, so it
  can ship as the migration-only PR (lesson S249 / AA-847) once AA-996's bk-029 is merged.
- **No amendment flag, no deferred trigger: the `received` state is the window.** A bill is a working draft while
  `received` (facts, lines and document change freely and need not add up). **Approve** is the check, immediately, in
  `supplier_bills_guard`: approver ≠ creator (CHECK + guard, maker-checker), ≥ 1 line, Σ lines = amount. After
  approval facts, lines and document are fixed, so the invariant holds without any COMMIT-time work (Infra X1 lint).
- **`paid` is derived** (design "paid only by settle"): `supplier_bills_guard` refuses `approved` / `paid` unless they
  equal what the live payouts imply (paid ⇔ live payouts = amount), so a direct `UPDATE … SET status = 'paid'` fails
  as role `booking`. `supplier_bill_settle()` (called by the AFTER trigger on payouts) is the only writer of
  `approved ⇄ paid` and `paid_at`; it locks the bill row first (critic B4). The payout guard locks the bill first too,
  so two concurrent payouts of the full amount end with one payout (schema test).
- **Payouts never exceed the bill** (no supplier overpayment; a partial payout leaves the bill `approved` with a
  balance) and go on an `approved` bill only, in its currency. **Maker-checker for payouts**: the recorder is never
  the person who entered the bill (design §5 "payout.write ≠ bill creator"), enforced by the guard (a cross-table rule,
  so not a CHECK).
- **Payouts have no verify step** (design: record → counts). Their money facts, reference and note never change (the
  grant covers only the evidence and the void columns); a mistake is voided (final, reason) and recorded again.
  Evidence is uploaded after the row exists (critic note 6 order) and is **replaced, never removed** while the payout
  is live; it is not required by the DB (the row exists before its file), the UI uploads it in the same dialog and the
  API flags `needs_evidence`.
- **Lines** (`supplier_bill_items`, PK bill + booking): a CONFIRMED booking of the bill's supplier (and of the bill's
  case when the bill names one; a supplier's statement bill without a case may span cases), amount in the bill
  currency, inserted / deleted only while `received`, never updated (the app replaces the set). A booking may sit on
  several bills (supplier deposit, then balance). The supplier and case of a bill stay fixed while it has lines. A
  booking moved off `confirmed` later (re-request, cancel) keeps its line: a cancellation fee is still billed.
- **B2B (design D12, DM-6.8)**: B2B cases take bills and payouts, but a **bill document** (a hotel invoice names the
  guests) is refused when the bill touches a B2B case (its case, or any line's case), and a bill that has a document
  takes no B2B line. A **payout's bank slip** (AA's own transfer) is allowed on every case.
- **Documents**: a bill's document only while `received` (it is what the approver checks); the document of an
  approved / paid bill stays; a received bill's attached document is detached before removal (as bk-028 payments).
- **Idempotency** (critic B6 rule): `idempotency_key` + `request_sha256` NOT NULL on bills (unique globally: the create
  route has no parent in its path) and payouts (unique per bill).
- **Bill number** unique per supplier, case-insensitive, among bills not cancelled (a cancelled entry can be redone).
- **`v_supplier_bill_balance`**: paid amount, live payouts, balance (0 once cancelled), lines count / sum, `overdue`
  (received / approved past due, session time zone).
- **Tags** (critic note 9): `bill_number`, `amount` (bills, lines, payouts), `payouts.reference` `conf:commercial`;
  `supplier_bills.notes` `pii:free_text; also conf:commercial`; `cancel_reason`, `payouts.note`, `void_reason`
  `pii:free_text`.
- **Settings row** `supplier_bill_due_soon_days` 3 (policy data, `bk_ops_reminders`).
- **Grants**: bills and payouts SELECT, INSERT + column UPDATEs, never DELETE / TRUNCATE; lines SELECT, INSERT, DELETE
  (guarded), no UPDATE; cis_app reads nothing. Only role `booking` grants change (one role, one lane).
- **Tests replaying older files**: the bk-028 re-run test now replays the later files (bk-030 replaces
  `ops_files_guard` again); `tests/integration/ops.py` purges bills / lines / payouts before supplier bookings,
  suppliers and files; `test_bk005_w1` lists the new setting.
- **Infra lint**: `python3 db/check_migration_files.py` of AA-CIS-Infra on a copy at
  `db/migrations/booking/030_supplier_bills_payouts.sql` (with AA-996's 029 beside it): ok, 0 problems;
  `check_retention_rows.py`: 0 tables without a row (Booking is grandfathered; the root DM-7 rows exist since S0).

## Changed (vs. the design, S4)

- Migration key **bk-030** (design: bk-029, taken by AA-996).
- No `partially_paid` bill state: a partial payout leaves the bill `approved` with a balance (the design's edges have
  no such state); KPIs and the list show the balance.
- Payouts are capped at the bill amount (the design allowed no overpayment rule either way; S3 allows customer
  overpayment, but AA overpaying a supplier is always an error).
- Bills carry `idempotency_key` + `request_sha256` too (design: payouts only), as invoices do in S3.
- Supplier bill documents are refused for bills touching a B2B case (design D12 allowed bills on B2B cases but said
  nothing of their documents; DM-6.8).
- `bill.read` / `payout.write` stay out of the preview cap (design §5 "reads join PREVIEW_PERMISSIONS"; critic note 8).
- Added: `GET /supplier-bills/summary`, `GET /supplier-bills/billable`, `GET /trip-cases/{ref}/supplier-costs`.
- Not built: a supplier-bill CSV export, bill attachments other than the one document, partial line matching per
  payout (a payout pays the bill, not a line).

## Tradeoffs (S4)

- "Received = the window" vs. the bk-028 `amending` flag: a received bill has no money attached yet, so its sums may be
  wrong while staff work; approval is the single checkpoint and everything after it is frozen. No flag to leave open,
  nothing deferred.
- Payouts without a verify step (design) vs. the S3 maker-checker on payments: the check here is on the bill (approved
  by another person) and on who pays (never the bill's creator); a second verify of every transfer would double the
  admin work for AA's own outgoing money.
- Evidence not required by the DB for payouts (the row must exist before its file): the API flags `needs_evidence`,
  the UI uploads in the same dialog and the drawer shows "No bank slip yet".
