# AA-682 — Operations MVP, slice S1: supplier bookings + supply track (bk-026)

Linear AA-682 (operations MVP: supplier bookings, trip checks, invoices + payment schedule, supplier bills, My
Payments; manual payment marking only). Sources: the S252 design (root `.tmp-session/s252/aa682/design.md`, saved with
the S252 audits) **with every "critic" edit applied**, the adversarial critic (`critic.md`, blocking issues B1–B9 and
notes 1–18), this repo's `CONTEXT.md`, `docs/architecture/db-schema-reference.md` (Booking at bk-025),
`docs/database/schema-ownership.md`, the lessons log (migrations; "a CHECK value exists before its writer"). Session
S252, agent Claude Code. Slice S0 (root DM-7 retention rows, schema ownership, ERD design page) ships in the root
repo PR `docs/aa-682-s0-s1`; this file covers S1. Nothing from S2–S5 (trip checks, invoices, payments, bills, My
Payments) is built here.

## Decisions

- **D1–D16 of the design are taken as written** (summary): case status stays the 13 DB values and "Confirmed &
  Booked" is a computed supply badge (D1); post-sale statuses move only by the system, forward from facts (D2);
  supply and money may happen in either order (D3); one generic transitions table `ops_transitions` + one trigger
  function for supplier bookings now, invoices / bills later (D4); files in a private ops-docs bucket with a KMS CMK
  through the base64 JSON path (D10); no RLS on the new tables (D11); B2B cases get supplier bookings but no voucher or
  confirmation files (D12, DM-6.8); the B2B desk and the supplier booking are one action both ways (D13); no new
  role (D16). D5–D9, D14, D15 are S3/S5.
- **Migration bk-026 = S1 only.** `ops_transitions` (+ supplier-booking edges), the post-sale case edges of bk-026
  (critic B1: the money edges wait for bk-028), the fact guard `trip_cases_post_sale_guard`, `ops_files`,
  `supplier_bookings`, `v_trip_case_supply_state`, three settings rows. Key re-checked on the day: origin/main of
  AA-Booking and AA-CIS-Infra end at bk-025 and no branch of either repo holds a `026_` file → **bk-026**, held by the
  Infra copy branch `chore/aa-682-copy-bk-026`.
- **"Live" supplier booking = `pending`, `requested`, `confirmed`** everywhere (critic B3): the partial unique index
  on `version_item_id`, the supply view, the guard, the reopen rule. A `declined` row never blocks a replacement
  booking with another supplier (B2C). B2B: a declined line is final (the agency was told `line.declined`), so no
  replacement there.
- **Supply state `none` means "nothing to book"**, not "no live booking" (critic: `none` passes the pre_departure gate).
  The view counts the supply items of the approved version (room type or service) and how many are booked; a case
  whose items were all declined with no replacement is `confirming`, never `none`. B2B: an item whose on-request line
  is confirmed counts as booked (answered on the desk before or without a supplier booking); an item whose line is
  declined or cancelled needs no supply (the agency was told). This is stricter than the design's "live / confirmed
  counts" and keeps a half-booked trip from ever passing as `none`.
- **Auto-advance on the first request, not on generate** (design §4 "first request"): pending bookings are staff's
  to-do list, the case moves to `supplier_confirming` once a supplier was actually asked. Back to `confirmed` when no
  live booking is left. System moves: empty `booking.actor`, status note "Auto: …", audit actor `aa682:advance_case`.
- **No B2C `pre_departure` in bk-026.** The guard needs a paid invoice for B2C, which exists only with bk-028, so
  bk-026 refuses B2C `pre_departure` outright and bk-028 replaces the function. B2B reaches it with supply `booked` /
  `none` (the lifecycle job is S2).
- **No document of any kind on a B2B case** (design D12 names vouchers; a supplier confirmation PDF names travellers
  just the same, and Q11 says "confirmation ref only"). The DB guard and the API both refuse it.
- **Lock order hold → case → booking.** The AA-974 cancel locks the hold, then updates the case; the supplier-booking
  writes of a linked booking lock the hold first too, so the two never deadlock (race test in `test_bk026_b2b.py`).
- **Generate refuses mixed cost currencies** (critic note 17) for the whole call (409 naming the item), rather than
  silently leaving that item's net empty; staff add that one by hand.
- **API transport cap 3 MiB per document** (same as AA-835 photos, Vercel's 4.5 MB body limit); the DB allows 10 MB
  (`ops_docs_max_bytes`) for a later presigned-POST path (design Q10).
- **FK indexes** on every new FK (critic note 2), partial where the column is mostly NULL.
- **PII tags** (critic note 9): `supplier_bookings.notes` is `pii:free_text; also conf:commercial`, `cancel_reason`,
  `ops_files.file_name` and `removed_reason` are `pii:free_text`, `ops_files.s3_key` is `pii:payment; also pii:name`.
  The tag grammar is `tag; also tag` (bk-018 parser), not `tag (also tag)`.

## Changed (vs. the design)

- §5 `POST /ops-files` accepts the kinds of every slice in its body schema but answers 422 `kind_not_available` for
  payment evidence, bills and payouts until bk-028 / bk-029 replace `ops_files_guard`.
- Added `GET /booking/supplier-bookings/summary` (dashboard tile "Supplier answers pending", design §6) and
  `GET /booking/supplier-bookings/{id}`; the case list response carries `unbooked_items` (items without a live
  booking and why Generate skips them) and `documents_allowed`.
- The desk list rows carry `supplier_booking` (the code of the live booking that covers the line).
- The Infra ops-docs bucket + CMK + task-role policy + `OPS_DOCS_BUCKET` env (design S1 "Infra PR applied before the
  code deploy") are **not** in this lane (the lane was told: Infra = the bk-026 byte copy only). Without them the
  upload / download routes answer 503 `ops_storage_unavailable` and every other S1 route works, so the code can deploy
  first; the bucket PR is a follow-up before the voucher part of the Done-when.
- Fix round 2 (review): generated room bookings take their nights on the channel's convention
  (`supplier_bookings._nights`). B2C = `supply_rates.quantity('room_night')` = max(day_to − day_from, 1), the same
  rule `versions.default_cost` priced the item with, so net and nights agree on the row; B2B = day_to − day_from + 1,
  the inverse of `holds._open_case`. The first cut used +1 for both, which asked a B2C supplier for one night more
  than was costed and sold. Pricing was not changed (no migration, no data on Dev yet); the one convention per
  channel is written in CONTEXT.md. The unit test covers both channels and a same-day item; the integration fixture's
  room item is now days 1-3 (2 nights); the Infra live-check generate SQL follows the same CASE and prints
  `b2c_room_nights`.
- PRD §7–9 (critic note 1) still unread: the PDF cannot be read in WSL; S0 Windows task stays open.

## Tradeoffs

- Generic `ops_transitions` vs. one edges table per entity: one function to review and the same pattern for bk-028 /
  bk-029 (design D4), at the cost of a TG_ARGV parameter.
- Status moves stay in the app (`advance_case`) and are double-checked by the guard, rather than a trigger on
  `supplier_bookings` moving the case: the app needs the move in the response and the audit row; the guard keeps any
  other writer (a script, a later job) honest.
- The supply view recomputes per case (LATERAL counts) instead of a stored counter: no drift, cheap at Booking's size.

# Slice S2: trip checks + case lifecycle (bk-027)

Session S253, agent Claude Code (subagent lane; the orchestrator does the live steps). Sources: the same S252 design
(§2 S2 row, §3.2 bk-027, §4, §5 trip-check routes, §6 `/trip-checks` + case Checks tab + drawer, §9 jobs) and critic
(B7, B8 respected), the data standards DM-6.1 v1.3 (`emergency_contact` class) and the DM-7 row of
`booking.trip_case_checks` (already in the root register: contact fields and notes nulled at trip end + 90 days by
`bk_case_lifecycle`, first run DRY RUN).

## Decisions

- **Key bk-027** (live Dev at bk-026 per the 27/10 04:12 UTC schema dump; no `027_` file on any branch). One file,
  `migrations/027_trip_checks_lifecycle.sql`, merged alone first (lesson S249 / AA-847), then the Infra byte copy.
- **Checks are rows, three standard + custom.** `pre_trip_recheck`, `emergency_contact`, `insurance` (at most one of
  each per case, partial unique index) and any number of `custom` rows. Standard rows carry a fixed English title
  (seeded; the guard refuses a new title), custom rows a staff title. `status` open → done | not_applicable, and back
  to open (reopen); done ⇔ `done_at`, `done_by` only on done.
- **Seeding is a trigger on `trip_cases`** (AFTER INSERT OR UPDATE OF status, start_date): entering `confirmed` seeds the
  three rows ON CONFLICT DO NOTHING, which covers the B2C version approval (UPDATE) and the B2B confirm that inserts
  the case at `confirmed` without touching `holds.py`; leaving and re-entering `confirmed` adds nothing. Due date =
  `start_date - pre_departure_days` (bk-026 setting, 14). The same trigger moves the due date of a standard row still
  `open` on the derived date when the start date changes (done rows and custom rows keep theirs).
- **Backfill = the open sold cases** (`confirmed` .. `on_trip`, not deleted); `completed` and `cancelled` cases get no
  rows (nothing left to check).
- **No emergency contact on a B2B case, enforced by the DB** (DM-6.8): the seeded row is `not_applicable` with no due
  date, and `trip_case_checks_guard` refuses any other status or any contact field on it, whoever writes.
- **`ON DELETE CASCADE` from the case.** Booking only soft-deletes cases; a hard delete is a reviewed script, and the
  check rows have no meaning without their case. Without it every test module (and any future purge script) that
  deletes a case at `confirmed` would have to know about checks. Role `booking` still has no DELETE on the table.
- **`cleared_at` + CHECK**: the lifecycle job nulls the emergency contact and every note of a case's checks once the
  trip ended `emergency_contact_keep_days` (90) ago and stamps `cleared_at`; a CHECK keeps those fields empty after
  that and the guard keeps `cleared_at` final (no re-entry of a third person's phone into an old trip).
- **`v_trip_check_board`** = one row per open sold case: stored counts (open / done / not applicable / overdue, next
  due) + the derived checks `suppliers_confirmed` (supply state `booked` or `none`, the bk-026 view) and
  `payment_verified` (`NULL::boolean` until bk-028 replaces the view; the column list stays).
- **The reminder dedupe index moves forward to bk-027** (design had it in bk-028): the S2 jobs already write reminders
  (gate notices, supplier answers, checks due). `notifications_reminder_uq` = UNIQUE (recipient_type, type,
  entity_id, data->>'reminder_key') WHERE data ? 'reminder_key' (critic B7: recipient_type included). bk-028 no longer
  creates it.
- **Settings rows** `trip_check_reminder_days` 3 and `emergency_contact_keep_days` 90 (policy data, values not code).
- **Tags**: `emergency_contact_name` `pii:emergency_contact; also pii:name`, `emergency_contact_phone`
  `pii:emergency_contact; also pii:contact`, `note` and `title` `pii:free_text`. The bk-018 tag test learns the three
  DM-6.1 v1.3 classes (`government_id`, `health`, `emergency_contact`), the same list as Infra `TAG_CLASSES`.
- **The lifecycle's "today" is the ops date.** `bk_case_lifecycle` reads the date in `b2b_ops_timezone` (AA-974
  setting, Asia/Ho_Chi_Minh; a bad value falls back to it) and sets the transaction `TimeZone` to that zone, so the
  bk-026 guard's `current_date` is the same day whatever the server or pool zone (tested with UTC-11 and UTC+14
  sessions). Runs at 01:00 UTC = 08:00 in Vietnam, when the UTC and ops dates agree.
- **Gates.** Hard gates are the guard's facts: supply `booked` / `none`, and for B2C the money track (`paid`, the only
  B2C source of `pre_departure` once bk-028 adds that edge). Until S3 every B2C case is reported blocked `not_paid`
  (one notice) and keeps its status: that is what the bk-026 guard already enforces. **Open checks never block** a
  move (the trip date is a fact; a stuck `confirmed` case during the trip helps nobody): their count travels in the
  gate notice and in the run result (`open_checks_at_move`), and `bk_ops_reminders` chases them. Design §9 listed
  "open checks" among blocked gates; this reads it as "reported", not "refused".
- **Moves chain in one run** (catch-up after missed days) and each move is its own savepoint: a refusal keeps the
  moves before it. A blocked gate after the start date targets `on_trip` (a second, sharper notice than the
  `pre_departure` one). No end date → `completed` blocked `no_end_date` once the trip started; no start date →
  `pre_departure` blocked `no_start_date`.
- **DRY RUN first, DM-7.2 style**: manual runs default to DRY RUN; the scheduled run stays DRY RUN until one live run
  over every case (no `case_ids`) has succeeded. A scoped live run (`case_ids`, ≤ 50, the synthetic Dev check) never
  unlocks the schedule. The nulling of emergency contacts uses the same mode.
- **`bk_ops_reminders` S2 parts** (design §2 lists them in S2): supplier answers waiting > `supplier_answer_days` (to
  the requester, key includes `requested_at` so a re-request reminds again) and checks due within
  `trip_check_reminder_days` or overdue (to the assignee, key includes the due date). No DRY RUN: it writes
  notifications only, deduped by the index.
- **Routes** (design §5): `GET /trip-checks` (status open default / done / not_applicable / all, `due_before`,
  `assignee` key / `me` / `none`, `code`, `case`, `q` on case code or title; only open sold cases), `GET|POST
  /trip-cases/{ref}/checks`, `PATCH /trip-checks/{id}`. Plus `GET /case-lifecycle/runs` (ops.read) so the DRY RUN
  result and the live moves are readable on Dev without DB access (the E2E session is read-only).
- **Audit without personal values**: a check's audit row lists `note` / contact fields as `"(set)"` or null, never
  the text (audit rows are kept longer than the 90-day contact window).
- **Staff UI**: `/trip-checks` (nav `shipped: true`, page rule widened to contracting, which has `ops.*`), the case
  **Checks** tab (derived checks card + checks table + Add check), one shared drawer
  (`trip-checks/_parts/CheckDrawer.tsx`) built on the kit `FormDrawer`; `TripCheckStatusBadge` in
  `ui/booking/StatusBadge.tsx` (Booking-owned file, not kit core). English copy; never claims an e-mail.

## Changed (vs. the design, S2)

- `notifications_reminder_uq` ships in bk-027 instead of bk-028 (the S2 jobs need it).
- `GET /case-lifecycle/runs` added (not in §5) for the read-only live check and the "Automatic updates" panel.
- Open checks are reported, not a hard gate (above).
- `trip_case_checks` gained `cleared_at`, `created_by` / `updated_by` and a phone pattern; the FK cascades from the case.
- The `/trip-checks` page rule now includes contracting (UI spec said admin, sales; the API grants `ops.*` to
  contracting since S1).
- PRD §7–9 still unread (S0 Windows task stays open).

## Tradeoffs (S2)

- Seeding by trigger vs. in `versions.approve_version` and `holds._open_case`: one place, both entry paths (and any
  future one, e.g. a script) covered, `holds.py` untouched (design §3.2); the cost is a trigger on `trip_cases`.
- A board view per case vs. per check: the page lists checks (DataTable rows) and reads the derived checks per case;
  per-check rows would repeat the case facts on every row. bk-028 replaces the view with the same columns.
- Reusing `b2b_ops_timezone` instead of a new `ops_timezone` key: one ops zone for the whole back office; a rename
  later is a settings migration.
- The run-script mimics the lifecycle step in SQL (it may not import app code) and, on apply, also queues a real scoped
  live job and an unscoped DRY RUN job for the worker, so the job code itself is exercised on Dev.
