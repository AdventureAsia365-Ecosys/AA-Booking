# AA-835 — Supply content: outbox supply stream, supply_version, supplier photos, v_supply_* views (bk-023)

Linear AA-835 (root ADR 0004a: Booking owns hotel / service facts and emits them on a supply stream with a monotonic
`supply_version`; CIS drafts the customer content, a human publishes it, CIS serves it back). This file covers the
Booking side. Slice S3 (this PR) is the migration bk-023 and its integration tests; slice S4 (upload API, read-back,
proposals, UI, `REQUIRED_SCHEMA_VERSIONS += bk-023`) follows after the apply. Contracts: root
`docs/contracts/supply.hotel.v1.json` / `supply.service.v1.json` (S1). Session S250, agent Claude Code.

## Decisions

- **Typed ids on the outbox, facts read at pull time** (as bk-022 and the plan's contract note). A supply row carries
  `entity_type`, `entity_id`, `supply_version` and the event type only. The consumer reads the current facts from
  `v_supply_hotels` / `v_supply_services` with the event; the contract's `supply_version` is the one of the facts, so a
  late read is safe (apply only if newer than what CIS holds).
- **One CHECK for both streams** (`outbox_supply_chk`): a supply row has a supply event type, an entity type in
  `hotel|service`, an entity id, a version ≥ 1, and none of the b2b columns (partner, hold, booking, line, departure,
  incident, decline); a b2b row has none of the three supply columns and no supply event type. `coalesce(..., false)`
  around the nullable parts: a NULL inside a CHECK makes it unknown, and unknown passes (caught by the test "supply
  without a version").
- **State-based event type.** `supply.deactivate` whenever the new version's status is `inactive`, `supply.upsert`
  whenever it is `active`, including an insert of an inactive row and a rename of an inactive row. The contract ties
  `change` to `facts.status` (deactivate ⇔ inactive), so the event type never contradicts the facts of its version.
- **Any write of `supply_version` is exactly one bump.** The BEFORE trigger sets `OLD + 1` when the facts changed *or*
  the column was written, whatever value was sent (insert: always 1). The room-type and photo triggers bump the parent
  with `SET supply_version = supply_version + 1`, which takes the same path; the app (which has table UPDATE on
  hotels / services) cannot jump or rewind the version. A deliberate re-send ("touch") is the same statement.
- **Material fields** are exactly the contract facts: hotels `name, hotel_style, star_rating, address,
  destination_id, country_code, latitude, longitude, check_in_time, check_out_time, amenities, status`; services
  `service_type, title, unit, destination_id, country_code, duration_minutes, max_group_size, inclusions, status`. Not
  material: `internal_notes`, `links`, `source_system/source_id`, `supplier_id`, `code`, the audit columns. A same-value
  write is no change (`IS DISTINCT FROM` on the row).
- **Room types**: insert, or a change of `hotel_id, name, max_occupancy, bed_types, status` bumps the hotel (both
  hotels when it moves). Room type notes do not. The view lists every room type (active and inactive), as the
  contract says.
- **`entity_media` key derived by CHECK**: `s3_key = 'supply-media/' || entity_type || '/' || entity_id || '/' || id ||
  '.' || ext(content_type)`. No free URL or foreign key can be stored, and S4 has one way to name an object (the plan's
  `supply-media/<type>/<entity>/<media id>.<ext>`). The bucket is a column (`s3_bucket`, set by S4 from
  `SUPPLY_MEDIA_BUCKET`) with a naming CHECK `^aa-booking-[a-z0-9]+-supply-media-[0-9]{12}$`, so `v_supply_media` can
  never point CIS at another bucket. No account id is written in the repo.
- **No FK from `entity_media` to the entity** (one column pair for two tables). The AFTER bump trigger updates the
  entity and raises `foreign_key_violation` when no row was found (also for the wrong kind). `purge_supply` (test
  helper) now deletes photos before hotels / services.
- **Removed is final** (`entity_media_guard`): status and usage_rights are fixed once removed; a new upload is a new
  row. One active copy of the same bytes per entity (`entity_media_entity_sha_uq`, partial on active).
- **Size caps**: table ≤ 10 MB (the plan); the S4 API caps uploads at 8 MB. Width / height optional (1–20,000).
- **Views are `security_barrier`** and owned by `bk_owner`; `cis_app` gets SELECT on the four views only. EXPLAIN on
  the local scratch DB: `feed_seq > n` on `v_supply_outbox` and `id = ANY(...)` on `v_supply_hotels` both filter in the
  scan under the barrier (no `Filter` above a `Subquery Scan`).
- **Guards in the file**: before (runs as `bk_owner`, `cis_app` exists, bk-010/bk-022 objects exist, `cis_app` has
  USAGE from bk-017) and after (`cis_app` reads the four views and none of hotels, room types, services, entity_media,
  outbox; the views are security_barrier; `booking` cannot delete photos).

## Changed

- No backfill of outbox rows for hotels / services that exist before bk-023. Each enters the stream on its next
  material change, or by a touch (`UPDATE booking.hotels SET supply_version = supply_version + 1 WHERE ...`), which
  writes one `supply.upsert` per entity. Reason: a backfill would make the CIS consumer draft (paid LLM) content for
  every existing entity the moment it starts; the touch keeps that a deliberate, sized step (paid-runs subset rule).
- `REQUIRED_SCHEMA_VERSIONS` is **not** changed here (plan: S4, after the apply), so readiness does not fail between
  merge and apply.
- Existing tests adjusted: `test_bk017_ops_views` (the exact cis_app grant set now includes the four supply views),
  `test_bk018_pii_tags` (allowlist `v_supply_hotels.name` / `.address`, `v_supply_services.working_title`: business
  name / address and the internal service title, mirrored into Infra `PII_ALLOWLIST` with the bk-023 copy),
  `test_bk022_schema` (`outbox.entity_type` is a new CHECKed text column), `supply.py` (purges photos).

## Tradeoffs

- Trigger-written events (as bk-022) over service calls: every path that changes a fact emits, in the change's
  transaction. Cost: a burst of edits in one transaction gives several rows (v2, v3, v4…); the consumer applies the
  newest facts once and records the rest as older / duplicate.
- Table-level UPDATE on hotels / services stays with role `booking` (the API edits facts); the version is protected by
  the trigger rather than by column grants, which would need every existing UPDATE path re-granted column by column.
- `media` and `room_types` as JSON columns in the views (one round trip per entity for the consumer) rather than
  separate views per child.
