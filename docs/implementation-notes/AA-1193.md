# AA-1193 — Auto-rollback of the API deploy (AA-Booking part)

Whole picture, the other repos and the drill: root `docs/implementation-notes/AA-1193.md` (S297, lane l5-rollback;
S295 Well-Architected review OPS06). Same mechanism as the web deploy's rollback (AA-1119).

## Decisions

- **Where**: `deploy-dev.yml` gets two conditional jobs after `verify`: `rollback` (only on main, after a successful
  `deploy` and a FAILED `verify`) and `report` (the `deploy-smoke-red` issue, closed by the next verified deploy).
  `result` does not wait on them; a rolled-back run stays red through `verify`.
- **Target**: the Booking api (aa-booking-dev-api) revision recorded by the deploy job before update-service (`ecs_smoke_rollback.py previous`,
  output `previous_td`). `.github/scripts/ecs_api_rollback.py rollback` checks it with every AA-1119 rule first
  (unknown or template revision, image gone from ECR, deployment in progress, service moved since, desired 0: refused,
  nothing written), then update-service, services-stable, the running image, and `/booking/health` must answer the previous
  commit in `git_sha`.
- **Deploy gate**: the rollback re-runs `.github/scripts/booking-deploy-preflight.sh` (task counts, then the OIDC deploy gate; the token is
  minted by the same workflow file on main, environment dev) with the run's `override_running_jobs` reason. A held
  gate rolls nothing back; the alert and the issue say "held by the deploy gate" (hand runbook: root
  `docs/ops/runbooks/rollback-booking.md`).
- **Alert**: `ecs_api_rollback.py alert` publishes one message on the alerts SNS topic, read from the running task
  definition's `ALERTS_TOPIC_ARN` (no GitHub setting; never printed). It needs `sns:Publish` on the deploy role
  (AA-CIS-Infra PR of this lane); until then it logs "not sent" as a warning and the issue still opens.
- **Failing checks**: `post_deploy_verify.sh` (byte copy shared by AA-Booking and AA-Partner) appends each failed check
  name to `VERIFY_FAILED_FILE`; `post-deploy-verify.yml` returns them as the workflow output `failed_checks`.
- **Drill**: dispatch input `drill_force_smoke_fail` (boolean, default off): the verify runs every real check, then
  its drill step fails on purpose, so the real rollback, alert and issue run. The deploy job refuses the drill before
  the roll when Dev already runs this commit.

## Changed

- `deploy-dev.yml`: input `drill_force_smoke_fail`; deploy output `previous_td` and step "Record the revision before
  this deploy (rollback target)"; jobs `rollback`, `report`.
- `post-deploy-verify.yml`: call input `drill_force_fail`, output `failed_checks`, drill and names steps.
- `post_deploy_verify.sh`: `VERIFY_FAILED_FILE`.
- New `.github/scripts/ecs_api_rollback.py` + `test_ecs_api_rollback.py` (byte copies of AA-CIS-App's); Workflow Lint
  runs the test.
- Tests: `backend/tests/unit/test_post_deploy_verify.py` (wiring, the rollback step's shell against stubs, the names step, the failed file).

## Tradeoffs

- A flaky verify now rolls back a good build (the AA-1119 trade-off): the next deploy of main brings it back.
- The health retry count / delay are CLI defaults in the script (CI timing, like `VERIFY_TRIES`), not admin settings:
  the CI runner has no settings store.
- No schema rollback (migrations only move forward; expand migrations keep the previous build working, ADR 0017).

## Should know

- Never a loop: the rollback is an update-service to an existing revision; it builds, pushes and dispatches nothing.
- Merging this PR deploys (deploy-dev.yml is in the push paths), so for the drill main must move again first with a
  commit that does not deploy (a docs-only commit), then dispatch Deploy Dev with `drill_force_smoke_fail`.
