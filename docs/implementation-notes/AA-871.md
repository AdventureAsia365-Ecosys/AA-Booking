# AA-871 — JSON logs, request ids and Sentry (Booking)

Linear AA-871 (S241 review P1-6). This file covers the AA-Booking half; AA-TripPlanner-Web has its own note.

## Decisions

- **One package, `app/observability/`.** `log_config.py` (structlog JSON for structlog *and* stdlib loggers),
  `request_id.py` (pure ASGI middleware), `scrub.py` (PII / secret redaction shared by logs and Sentry),
  `sentry.py` (init + `before_send` / `before_breadcrumb`). `setup(settings)` runs logging, then Sentry, once at import
  of `app.main` (`build_app()`); `create_app()` only adds the middleware and the 500 handler, so tests that build their
  own app never touch global logging or Sentry.
- **Existing log calls are unchanged.** Every module keeps `logging.getLogger(__name__)` and `%`-style calls; the root
  handler renders them through `structlog.stdlib.ProcessorFormatter`, so each line is one JSON object with `event` (the
  formatted message), `level`, `logger`, `timestamp` (UTC ISO), `service`, `environment`, `git_sha` and whatever is bound
  in the context (`request_id`, `job_id`, `job_kind`).
- **Request id.** `X-Request-ID` from the caller is kept when it matches `[A-Za-z0-9._:-]{1,128}` (API Gateway's
  `context.requestId` is a UUID; anything else, e.g. a header-injection attempt, is replaced, never echoed). Otherwise a
  new `uuid4().hex`. It is bound to the structlog contextvars for the request, set as a Sentry tag, stored in
  `request.state.request_id` and echoed as `X-Request-ID` on every response, the unhandled-500 included (an `Exception`
  handler, because Starlette's `ServerErrorMiddleware` answers outside user middleware).
- **One `request_completed` line per request** (method, path, route template when matched, status, `duration_ms`), no
  query string. It replaces uvicorn's plain-text access log (`uvicorn.access` is disabled; `uvicorn` / `uvicorn.error`
  now propagate to the JSON root handler).
- **Jobs.** The worker binds `job_id` + `job_kind` around each job, so handler log lines carry them. A job that ends
  `failed` (permanent error or attempts used up) is also sent to Sentry with the same two tags; a retryable attempt is
  not (it is a warning line only).
- **Sentry copies the CIS `shared/sentry_init.py` pattern** (AA-870): `send_default_pii=False`,
  `max_request_body_size="never"`, request bodies and cookies dropped, request headers reduced to an allowlist
  (`authorization` is never on it), key-like query parameters redacted, `traces_sample_rate=0.1`,
  `profiles_sample_rate=0.1`, Starlette + FastAPI integrations, `release` = `GIT_SHA`, `environment` = `ENVIRONMENT`.
  Added on top of CIS: `include_local_variables=False` (frame locals would hold customer rows), `user` dropped, and the
  text / key scrubber below applied to exception values, frame source lines, messages, `extra`, tags, contexts and
  breadcrumbs. Exception messages from `asyncpg`, `pydantic`, `jsonschema` and `json` are dropped (type and stack kept):
  they echo input values (asyncpg: "invalid input for query argument $1: 'Jane'"). One unit test drives the real SDK (capturing transport, no network) through a failing request with an
  `Authorization` header, a cookie and an e-mail in the query, and checks the event has the `request_id` tag and none
  of those values.
- **DSN from `SENTRY_DSN`** (the task definition maps it from a Secrets Manager secret), not fetched by name like CIS:
  no new IAM read path in the app, and unset = Sentry off (a log line `sentry_disabled`, no error).

## Changed (vs. the Linear scope)

- **Missing-DSN guard is opt-in.** Linear scope 3 says "startup fails when the DSN is missing and `ENVIRONMENT != test`".
  Shipping that as the default would stop the Dev service at the next deploy, before the DSN secret exists. Instead:
  `SENTRY_REQUIRED=true` with an empty `SENTRY_DSN` raises `SettingsError` at start-up (tested). Infra turns it on in
  the same change that wires the secret; from then on Dev fails closed as the issue asks.
- **`db_ms` (C1.1d) is not in this slice.** It needs timing around every pool call (`app/db.py` + the services that
  acquire connections). Left for a follow-up so this PR stays a pure logging/Sentry change.
- **`tenant_id`**: Booking has no tenant concept yet; nothing bound.

## Tradeoffs

- **Scrubbing is pattern- and key-based.** E-mails, `+`-prefixed phone numbers, Bearer tokens, JWTs, `key=`/`token=`
  query values and Postgres `Key (email)=(…)` details are redacted in any string; values under keys such as `email`,
  `phone`, `name`, `first_name`, `password`, `token`, `authorization`, `cookie`, `secret` are replaced whole. Free-text
  names in a message cannot be found by a pattern: the rule stays "ids only in log lines" (DM-6.4) and this is the net.
  Phone numbers without a leading `+` are not matched on purpose: a bare digit run is far more often an id or a count.
- **Pure ASGI middleware**, not `BaseHTTPMiddleware`: no extra task per request, no buffering of streamed bodies, and
  contextvars bound in it are visible to the endpoint.
- **Health checks are logged** like any request (as uvicorn's access log did before): about two lines a minute, which
  is what makes the uptime check visible in CloudWatch.

## Should know

- New pins: `structlog==25.5.0`, `sentry-sdk[fastapi]==2.70.0`.
- New environment (all optional): `SENTRY_DSN`, `SENTRY_REQUIRED`. Underscore names: set by hand / Terraform, not here.
- API Gateway REST does not forward its own request id by default. To make the header id equal API Gateway's
  `context.requestId`, Infra adds `integration.request.header.X-Request-ID = context.requestId` to both Booking proxy
  integrations; until then the app generates the id (still echoed and logged, just not equal to API Gateway's).
- CloudWatch Logs Insights for one request: `fields @timestamp, level, event | filter request_id = "<id>" | sort @timestamp`.
