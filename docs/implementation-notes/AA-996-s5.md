# AA-996 audit slice 5: billing detail, notifications and staff

Session S254, agent Claude Code (lane, orchestrated).

Source: the S254 Figma visual audit (root repo `docs/audits/2026-10-28-S254-booking-figma-audit/`, items 13 and 15
plus the "smaller items" paragraph and the `SEND REMAINDER.png` decision). Slice 1 (en-GB dates, CSV, filter bar,
billing table nowrap) is a separate PR; this slice avoids the files and hunks it changes.

## Decisions

- **No migration.** Every API change is additive and reads columns that exist (bk-005 `audit_logs`, bk-028
  `payments` / `invoices`, `trip_cases`, `customers`).
- **Staff deactivation reason.** `PATCH /booking/staff/{id}` takes an optional `reason` (max 500). It is written to the
  audit row only (`after.reason` and the summary `… Reason: …`), never to `booking.staff_users`. The API keeps it
  optional (additive: an old client still works, and activation or a role change may have none); the staff admin UI
  requires it on Deactivate (the confirm stays disabled until one is typed) and offers it as optional on Activate.
- **Audit-log search.** `GET /booking/audit-logs?q=` matches the summary, the action, the record label or the actor's
  name, case-insensitive, with `%` / `_` literal (`app.paging.contains`). No index: the table is small (hundreds of
  rows on Dev) and the existing keyset order still bounds each page; a trigram index is a later migration if needed.
- **Payment customer and trip.** Every payment row now carries `customer` `{id, code, name}` (null on a B2B trip); the
  payment detail adds the trip case facts (status, style, start / end date, pax, channel) and, only with
  `customer.read`, the customer's e-mail and phone. The payments list does not show the customer yet: that column lives
  in `billing/page.tsx`, which slice 1 rewrites (left for after it merges, to avoid a conflict).
- **Invoice PDF.** No PDF generator exists in Booking (the proposal PDF job of ui-spec §6.3 is not built either), so
  the invoice page says "PDF: coming later" in its Dates card instead of showing a dead button. No PDF service is
  built here.
- **Totals footer without a tax row.** The invoice is a proforma payment request with tax-inclusive prices (bk-028,
  design D7: no tax line; the legal VAT invoice stays outside Booking). The footer shows Approved proposal,
  Adjustments (when any), Total due, Paid (verified) and Left to pay / Overpaid, and a one-line note that prices
  include tax, instead of inventing a "Tax 0 %" row.
- **Issue date / Due date.** Issue date = `issued_at` ("Not sent yet" for a draft). Due date = the last payment-schedule
  row (the balance date: when the whole amount is due); the next due date is shown under it when it differs.
- **Light table for short lists.** The invoice Lines, Payment schedule and Payments use a plain `<table>`
  (`billing/_parts/LightTable.tsx`) instead of the kit DataTable: no Columns menu, no pager, padded inside the card,
  stacked rows under 640 px. The kit DataTable stays for real lists. The kit file is a CIS byte copy and the Booking
  wrapper is being changed by slice 1, so neither gets a "hide tools" prop here.
- **Remind confirm.** Remind opens a confirm dialog (Figma `SEND REMAINDER.png` frame, which in the export is the
  shared delete-dialog layout); confirming calls the same `POST /booking/invoices/{n}/remind`. The copy says what the
  endpoint does: a reminder in the customer's My Trips feed, no e-mail, at most once a day.
- **Notifications.** Labels and icons for every type the backend writes to the staff feed (service, lifecycle,
  payments, invoices, supplier bookings and bills, retention), so the Type filter can select them. Targets: invoice
  types → `/billing/invoices/<number>` "Open invoice"; `payment.recorded` → the payment; supplier booking and trip
  check reminders → the case (by `case_code`); `retention.held` → none (no page). Codes `INV-`, `PMT-`, `BIL-`, `SB-`
  are bold like `TC-` / `CUS-`. ISO dates in messages are slice 1's frontend `localizeIsoDates`.
- **Audit-log tones (ui-spec §1.3).** Mapped on the verb: created / provisioned / opened / recorded / approved /
  verified / published / sent → success; status_changed / amended / reminded / held → warning; archived / blocked /
  deleted / cancelled / voided / deactivated / declined / expired / removed → danger; anything else (updated, edits,
  dry runs, syncs) → info. A `staff.updated` row whose `after.active` is false reads as a deactivation (danger).

## Changed

- Backend: `app/auth/admin.py`, `app/routers/staff.py` (reason); `app/audit.py`, `app/routers/reference.py` (q);
  `app/ops/payments.py` (customer + detail context); `docs/api/openapi.json` regenerated (2 additive fields).
- Frontend: invoice view (dates card, totals footer, light tables, Remind confirm, PDF note), payment page (two
  columns: transaction, Related trip, Customer), notification vocabulary / icons / targets, staff Deactivate reason,
  audit-log search + tones, Settings copy.
- Not done here (other slices or later): payments list customer subline, row actions and CSV (`billing/page.tsx`,
  slice 1 file); en-GB dates (slice 1); issuer legal name / address values (a Dev settings row, data not code).

## Tradeoffs

- Reason optional in the API but required in the UI: an API rule would break the "additive only" constraint and the
  activation path; the audit row is where it matters and the UI always sends one on Deactivate.
- Email / phone of the customer on the payment page only with `customer.read`: today every `billing.read` role also
  has `customer.read`, but the check keeps contact data from following a future role split by accident.
- Settings: the server `description` of `deposit_pct` / `quote_validity_days` is stored in `booking.settings` and
  carries internal notes; the page now shows its own staff-facing help text instead (changing the row is data, and a
  migration is out of scope).
