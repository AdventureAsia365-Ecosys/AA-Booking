# AA-1037 lane b2c-writes-off: no B2C write path is left

Root ADR 0019 d8 (B2B-only model), the AA-1034 R0 follow-up. Done-when "No B2C write path is left" plus the scope line
"nav cleaned up; Partners and Settlement pages". Session S270 (05/11/2026).

## Decisions

- **One switch.** Every refusal reads `settings.b2c_intake_enabled` (`B2C_INTAKE_ENABLED`, default off), the R0
  switch: turning it on reopens the intake, the staff writes and the jobs' B2C scope together. No new setting.
- **Same answer as R0.** 410 `b2b_only` with the R0 message (`app.errors.Gone`), raised before any read or write of
  the service. Each guarded route documents the 410 in `docs/api/openapi.json` (`b2c.GONE_RESPONSE`).
- **Two kinds of guard** (`app/b2c.py`):
  - `refuse_b2c_write(request)`: routes that exist only for B2C. Customer invoices and payments
    (`booking.invoices` / `booking.payments` are B2C-only, ADR 0019 d9), customer edit and archive, `POST /trip-cases`
    (a staff-made case is always for a customer, new or existing; B2B cases come only from the B2B confirm path) and a
    new case from a trip plan. First line of the handler, so not even the DB is touched.
  - `refuse_b2c_case_write(request, conn, ref)` and siblings (supplier booking, trip check, ops file): routes shared
    with B2B cases. They read only `trip_cases.channel` (by id, code, or the record's case) inside the route's
    transaction, before the service call, and refuse a `b2c` case. An unknown ref reads NULL and falls through to the
    service's own 404, so the guard never says whether a ref exists beyond what the route already said.
- **Proposal send / approve**: refused on a b2c case (the customer-facing send of a version), together with every
  other version write, status move, note edit and assignment on a b2c case.
- **Customers PATCH / DELETE (DM-6.x)**: both refused. DM-6.7 erasure is not a staff edit: it is the reviewed DB
  Migrate `run-script` of the root DSAR runbook (`docs/legal/dsar-erasure-runbook.md`), which does not go through these
  routes. DELETE (archive) also cancels the customer's new cases, a B2C write. A rectification request on a frozen
  record goes through the same runbook route (a reviewed script) or, if the business owner wants staff to edit again,
  the switch. Nothing in `app/retention` calls a customer route.
- **Supplier bills and payouts stay open** even for a past b2c trip: they are AA's own payables to suppliers (supply
  side), not B2C records. Payment evidence files (`ops_files.entity_type = 'payment'`) are B2C money and frozen.
- **Billing reads stay**, masked: `b2c.frozen_view` turns every `actions` flag off and `invoiceable` false (reason
  `b2b_only`) on the billing GETs, so the admin pages draw no button the API would refuse. The frontend applies the
  same mask (`ui/booking/b2cFrozen.ts frozenView`) so a build with the switch closed is safe against an API that is
  still open, and vice versa.
- **Jobs**: `bk_inquiry_pull` / `bk_inquiry_process` were already disabled by R0 (`Worker(disabled_kinds=...)`).
  `bk_notify_email` only reads and sends the staff "new inquiry" e-mail; the intake is its only producer, so it has
  nothing to do and writes no B2C row. `bk_case_lifecycle` moves only `channel = 'b2b'` cases and `bk_ops_reminders`
  names only B2B cases and skips the customer payment reminders (they read `booking.invoices` and write customer feed
  rows); both results carry `"b2c": "frozen" | "open"`. The DM-7 clearing of trip-check emergency contacts is
  retention and still covers every case.
- **No DB backstop in this lane.** A `trip_cases` CHECK `channel = 'b2b'` `NOT VALID` is enforced on every UPDATE of an
  existing row, so it would refuse the erasure script's redaction of `trip_cases.notes` / `inquiry_snapshot` on a b2c
  case (DM-6.7) and any retention UPDATE that touches the row. The b2b-only CHECK lands with the B2C drop (lane
  aa1037-b2c-drop-dryrun), after the b2c rows are handled. No migration in this lane.
- **Frontend gating**: the same build flag R0 used (`NEXT_PUBLIC_B2C_INTAKE`, `lib/config.ts B2C_INTAKE_OPEN`, unset =
  closed). The staff layout takes the B2C-only write permissions out of the staff profile (`billing.write`,
  `payment.verify`, `customer.write`, `customer.admin`); the case page also takes `trip_case.write`,
  `trip_case.assign`, `version.write`, `ops.write` inside a b2c case and shows a "Read-only" pill.
- **Per-case mask on every case route (review fix).** The mask sits in `app/(staff)/cases/[code]/layout.tsx`, not in
  the workspace page, so the proposal builder (`/cases/{code}/proposals/{n}`) and its preview inherit it: no Save, Send,
  Record approval or item edit on a b2c case; the builder's lock note gives the B2C reason. The layout runs the same
  case query as the pages (one load); until the case is known its channel is unknown and a closed build offers none of
  those writes (the pages show their skeleton meanwhile).
- **Pages outside a case gate per row (review fix).** `/proposals` row actions (New version, Send, Delete draft) and the
  "New proposal" case picker skip b2c cases (`isFrozenCase`); `GET /booking/versions` now returns
  `trip_case_channel` per row (the version's own `channel` is its pricing channel, so a new name). The trip-check
  drawer (shared by `/trip-checks` and the case Checks tab) is read-only on a b2c trip and says why. Pages that only
  create b2c cases (cases list, new case, customers, trip plan "new case") were already gated by `B2C_INTAKE_OPEN` in
  R0. `b2cFrozen.test.mjs` lists every file outside `/cases/{code}` that reads `trip_case.write`, `trip_case.assign`,
  `version.write` or `ops.write` with the gate it must keep, so a new entry point fails the unit test.
- **Nav**: B2B group right after Overview: Partners (`/agency-billing?tab=agencies`), Settlement (`/agency-billing`,
  every other tab and the invoice pages), B2B desk. With the switch closed, Customers and Payments & Invoices move to
  a "B2C records (read-only)" group before Admin; open, they go back to Sales and Operations. The phone bottom nav
  shows the B2B desk instead of Customers while closed.

## Tradeoffs

- Route-level guards rather than service-level: the services stay reusable by the switch-on path and by tests, and the
  refusal happens before any read. The cost is that a new write route on B2C data must call a guard; the unit test
  enumerates the guarded routes, and a unit guard fails when a write route on those paths lacks the documented 410.
- Masking the billing reads instead of hiding the B2C pages: staff can still look up an old customer trip, invoice or
  payment (the DSAR runbook's manual name check needs the case pages), with no write affordance.
- No visual-run allowlist change was needed: the B2C pages render the same frame with fewer buttons. The agency billing
  pages (now Partners / Settlement) stay in `e2e/visual/pages.ts EXCLUDED` until lane aa1037-billing-visual-fixture adds
  their layout-mock fixtures.

- Reviewers: the auth-like change is "refuse more", never "allow more". A route that was 403 for a role stays 403 (the
  permission dependency runs first); the 410 only replaces a success or a domain error.
- Live check after deploy needs no data change: every refused write answers 410 before the service runs, so a probe
  with a made-up ref is enough (the case-scoped guards answer the service's 404 for an unknown ref instead; probe those
  with a real b2c case: a case in the cases list without the B2B pill, its code read from the list; the probe body is
  a valid body: FastAPI validates it first, then the guard refuses before the service, so nothing is written).
- `NEXT_PUBLIC_B2C_INTAKE` stays unset on the `aa-booking-admin` Vercel project (unset = closed). It is an underscore
  env var: set or edit it by hand or by script, never through generated markdown.
- Pre-existing, not from this lane: the layout-mock `case-workspace.spec.ts` proposal preview tests fail on
  `GET /api/booking/settings` (no fixture; `SendProposalModal` queries the settings on mount).
