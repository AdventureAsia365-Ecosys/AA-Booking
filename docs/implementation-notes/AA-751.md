# AA-751 (X6) — Booking half, PR B1: migration bk-013

Scope (plan `docs/audits/2026-10-16-S240-aa751/aa751_plan.md` §B1 in the root repo; ADR 0003a decisions 2 and 6):
`booking.job` catches up with the job table template (AA-CIS-App `shared/jobs/job_table_template.sql`). Migration
only: no app code reads the new columns in this PR (B2 does: release on shutdown, `cancel_requested` in claim/reap,
`progress.attempt_started_at`, `REQUIRED_SCHEMA_VERSIONS += bk-013`, the template comparison test).

## Decisions

- **`migrations/013_job_template_catch_up.sql` (bk-013)** adds `cancel_requested BOOLEAN NOT NULL DEFAULT false`,
  `progress JSONB NOT NULL DEFAULT '{}'`, `cost_usd NUMERIC(12, 6) NOT NULL DEFAULT 0`, `parent_job_id UUID REFERENCES
  booking.job(id)`; `job_parent_idx`; `job_running_idx (kind, locked_until) WHERE status = 'running'`;
  `job_queued_due_idx (run_after, created_at) WHERE status = 'queued'`; drops `job_lease_idx` / `job_due_idx`; sets
  `autovacuum_vacuum_scale_factor = 0.02, autovacuum_vacuum_threshold = 50`. Same column types/defaults and index
  definitions as the template, so the B2 comparator test sees no diff on these.
- **Converge, never RENAME** (plan F10). `test_bk001.py` re-applies every migration on the migrated DB: bk-002
  re-creates `job_due_idx` / `job_lease_idx` (`IF NOT EXISTS`), then bk-013 skips its three `CREATE INDEX IF NOT
  EXISTS` and drops the two old ones again. A RENAME would have left both names after the second pass (or failed).
- **Index names aligned with the template** (plan appendix point 1): the comparator ignores names, but the same
  names make `\d booking.job`, the schema dump and the docs read the same as `shared.job`.
- **Autovacuum `0.02 / 50`** (orchestrator S240, plan F17): never later than the default `0.2 / 50` at any row count;
  the C5.1b text (`1000 + 0.02 N`) would have made vacuum rarer below ~5k rows. C5.1b is amended in the root R1 PR.
- **`job_active_pull_uq` stays**: it is Booking's singleton index for `bk_inquiry_pull`; B2's comparator lists it in
  `allow_extra_indexes`.
- **Not in `REQUIRED_SCHEMA_VERSIONS` yet**: apply first, then code (B2 adds it), so this merge cannot make
  `/booking/health/ready` return 503 before DB Migrate applied bk-013.

## Changed

- Plan SQL taken as written, plus two header lines on the retention FK guard (below).
- New `backend/tests/integration/test_bk013_schema.py` (pattern of `test_bk012_schema.py`): registration, the four
  columns (type, NOT NULL, default) and the self-FK (`NO ACTION`), the three template indexes present by definition,
  the two old ones absent, `job_active_pull_uq` / `job_finished_idx` kept, reloptions, behaviour (defaults on insert,
  FK rejects an unknown parent), and a third full pass of 001→013 that must leave the same shape (explicit
  convergence proof, independent of test order).
- CONTEXT.md: a `bk-013` section in the migrations list.

## Tradeoffs

- **Inline FK in `ADD COLUMN IF NOT EXISTS`** (plan's form) instead of a named `ADD CONSTRAINT` in a DO block: on
  PG ≥ 13 a skipped `ADD COLUMN IF NOT EXISTS` also skips its inline constraint, so a re-run does not add a second FK
  (the test asserts exactly one FK). The FK gets PostgreSQL's generated name `job_parent_job_id_fkey`, which matches CIS.
- **ACCESS EXCLUSIVE on `booking.job`** for the whole file (ADD COLUMN, CREATE INDEX non-concurrently, SET): fine on
  an idle table of ~1.4k rows; `lock_timeout 5s` and DB Migrate's idle check (I1) are the guards. No CONCURRENTLY
  (cannot run inside the BEGIN/COMMIT the guard requires).

## Should know

- **Merge only while `booking.job` is idle** (plan F22): the PR touches `backend/tests/**`, which triggers Deploy
  Dev, and Booking has no deploy job guard until B4. The code change is inert either way.
- **Retention FK guard**: `parent_job_id` is a single-column FK onto `booking.job.id`, so `bk_retention_job`
  (`app/retention/runner.py fk_refs`) now adds `NOT EXISTS (SELECT 1 FROM booking.job r WHERE r.parent_job_id = t.id)`
  to its delete predicate and reports `fk_protected_by: ["booking.job.parent_job_id"]`. A parent job is never deleted
  while a child exists (the child goes first, on its own window). `job_parent_idx` serves that probe. No Booking kind
  sets a parent today; a future spawning kind must accept that.
- **Recurring-kind prune is NOT guarded** (B1 review): `app/jobs/queue.py prune` (called from `worker.py maintenance`
  for every recurring kind, today `bk_inquiry_pull`) deletes `succeeded`/`cancelled` rows of that kind with no FK
  guard, and `maintenance()` has no try/except around it. Harmless while no kind sets `parent_job_id`. A kind that sets
  `parent_job_id` to a recurring job (e.g. a pull spawning `bk_inquiry_process` children) must first add
  `NOT EXISTS (SELECT 1 FROM booking.job c WHERE c.parent_job_id = booking.job.id)` to prune (`job_parent_idx` serves
  it), or make parents outlive children; otherwise one ForeignKeyViolation fails the whole DELETE, escapes
  `maintenance()` and `run_once()` before `claim()`, and the worker stops claiming. Not added in B1 on purpose: the
  clause names `parent_job_id`, which only exists after DB Migrate applies bk-013, and this PR's merge triggers Deploy
  Dev first. It belongs with the app change that requires bk-013 (B2).
- Nothing in Booking code or docs referred to `job_due_idx` / `job_lease_idx` (grepped).
- Rollback: additive; leave the columns. Reverting the index names would need a bk-014 (not expected).
