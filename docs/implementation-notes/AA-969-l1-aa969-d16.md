# AA-969 part 2 (lane l1-aa969-d16): Booking clean-up skips the pilot tenant

Item (3) of the S265 re-scope comment on AA-969 (root ADR 0019 d16): every clean-up, E2E and wave job skips the pilot
tenant. This note covers the `booking.job` kinds.

## Decisions

- **Marker source:** the CIS contract view `catalog.v_tenant_account_v1` (CIS 357), column `is_pilot`
  (= `shared.tenants.is_pilot`, CIS 354). `booking` already holds SELECT on it (bk_tenant_pull reads it). No Booking
  migration, no copy of the marker: one read per run, feature-detected through `app.catalog.liveness`.
- **Which kinds skip the pilot** (the inventory):
  - `bk_case_lifecycle`, the clearing step (trip-check emergency contacts and notes 90 days after the trip): skips cases
    whose `party_tenant_id` is the pilot. The case *moves* (pre_departure, on_trip, completed) keep running: they follow
    the travel dates and are not clean-up.
  - `bk_retention_inbox_redact`: skips inbox rows whose trip case (`trip_cases.inbox_event_id`) belongs to the pilot.
  - Not changed: `bk_retention_job` (finished `booking.job` rows, no tenant data), `bk_b2b_hold_expire` (the hold's own
    agreed expiry), `bk_tenant_pull` / `bk_trip_plan_sync` / `bk_price_recompute` (projections of CIS and AA data),
    `bk_ops_reminders` / `bk_notify_email` (notifications), `bk_inquiry_*` / `bk_tour_lifecycle_pull` (intake),
    `bk_noop_sleep` (Dev proof kind). Booking has no seed, E2E clean-up or wave job kind (the B2B seeds are AA-CIS-Infra
    run-scripts, guarded by item (2) there).
- **Retention predicate with the pilot ids inlined:** retention `Part.where` takes no bind parameters, so
  `Spec.pilot_where` holds a template and `without_pilots()` fills it with a uuid[] literal built from ids parsed by
  `uuid.UUID` (no other text can get in). The windows stay the same, so the DM-7.2 "same windows as the last live run"
  rule is unaffected.
- **Fail-open** when the view is not readable (warning `pilot_view_unreadable`): both clean-ups only reach rows 90 days
  past a trip end or an inquiry, longer than the pilot's 8 weeks, so data written during the pilot is out of reach either
  way, and a missing CIS view must not stop data minimisation for every other tenant.

## Changed

- `backend/app/pilot.py` (new): `pilot_tenants()`, `uuid_array_literal()`.
- `backend/app/ops/lifecycle.py`: `CLEAR_WHERE` gains `$4` (pilot ids), `CLEAR_SQL`'s limit moves to `$5`.
- `backend/app/retention/policy.py`: `Spec.pilot_where`, `without_pilots()`; `INBOX_SPEC.pilot_where`.
- `backend/app/retention/jobs.py`: a run of a spec with `pilot_where` reads the pilots first; the result carries
  `pilot_tenants_skipped` when there is one.

## Tradeoffs

- The admin retention status page (`status()`) still counts candidates with the plain spec, so it may show the pilot's
  rows as candidates while the run leaves them out (display only).
- A B2B case never holds an emergency contact (DM-6.8, bk-027 guard), so for the pilot the clearing is about trip-check
  notes; B2C cases have no `party_tenant_id` and are never the pilot's.

## Should know

- No migration, no new setting. Live check after deploy: a manual DRY RUN of `bk_retention_inbox_redact` and of
  `bk_case_lifecycle` succeeds; with a pilot marked in CIS, the inbox result shows `pilot_tenants_skipped: 1`.
