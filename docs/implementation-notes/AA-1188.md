# AA-1188 — Booking part: twin share tariff, availability per row, quote rules on /terms (contract 1.12)

S295 pricing audit (roadmap S2 + the Booking half of S4, decision D5): the agency tariff priced an odd band with the
quote's default room mix (doubles plus one single), so 3 travellers cost more per person than 2; it had no on-request
flag although the 8-10 and 11+ bands are only quoted on request; the season column read the matrix label (mostly
empty); nothing told the agency that a departure can change the price. The CRM also had no AA booking conditions to
show beyond the payment terms.

## Decisions

- **Twin share by halving, not a second formula.** An odd party is asked of the quote engine with `(party + 1) / 2`
  doubles (the engine already accepts a half-empty double: capacity only has to hold the adults), then half of one
  double room night per hotel night is taken off (`tariff.twin_share`: each room part's net over its rooms, from the
  `PartCost` rows `price_lines` already returns). The sell price is linear in the net (`quotes.price_line`), so the
  twin line goes through the same `price_line` as before. An even party keeps the default mix (`rooms=()`), so even
  rows stay exactly what a quote answers.
- **The single supplement is now against the twin share** for every band, a party of one included (it used to be 0
  for one traveller "who already sleeps in a single"). A solo traveller reads twin share + supplement, the market's
  tariff shape (D5).
- **`price` stays the line of the party**, now the party sharing; for an odd party a quote in the default mix charges
  one supplement more. The integration parity test asserts exactly that (even: equal; odd: twin + one supplement,
  within the per-person rounding).
- **A room part in two currencies cannot be halved**: the odd band is unpriced with a reason (staff see it); the even
  bands of the same plan still price. Rare (one hotel night priced by two DMC currencies).
- **Availability from the existing policy value**, no new threshold: `on_request` when the band reaches
  `group_on_request_min_pax` (`pax_max >= value`, or an open band). With the seeded 9 this is exactly D5 (8-10 and 11+
  on request). The value is answered at the top (`group_on_request_min_pax`) so the CRM can say "groups of 9 or more".
  A missing policy value is AA-side (503 `unavailable`), as on a quote.
- **Season label** = the plan calendar's season code of the row's first day once the calendar is configured
  (`low` / `high` / `peak` / `festive`), else the matrix label. `season` joined into `SAME_PRICE` so a low and a high
  piece at the same price stay two rows.
- **Departure note as data**: `departure_adjusted` per row (an approved adjustment in force on an upcoming departure
  inside the row's dates) and `early_booking_days` (the b2b rule's, only when it has a discount). Never the
  adjustment's size, the early-booking points or a margin.
- **Coverage**: `tours_priced` (tours with a priced row) and `catalog_tours` (`count(DISTINCT source_id)` of
  `catalog.v_tour`, null for a one-tour read) for the CRM's "Priced tours N of M".
- **`GET /terms` `quote_rules`**: quote validity days, the group size and AA's default age bands from the pricing
  policy in force; null (not a 503) when a value is missing, so the payment terms and clauses still answer.
- **Contract 1.12, additive**: every new field has a default in the response models; the CSV appends two columns at the
  end, so a reader of the 1.7 columns by position keeps working.

## Tradeoffs

- Halving the half-empty double relies on one rate per room part (`PartCost.net` / `quantity`). A plan whose room
  type has `max_occupancy` 1 cannot be asked as doubles: its odd bands are unpriced, the same as an even party would
  have been before (the default mix asks doubles too).
- Stop-sale dates are not a tariff availability reason: the calendar's stop-sale ranges are not cut points of the
  tariff windows, so a row could be half on stop-sale. The quote still answers `on_request` on those dates.
- No new setting: the group size and the age bands are existing pricing policy parameters (Pricing > Policy).
