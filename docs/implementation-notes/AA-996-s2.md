# AA-996 fix slice 2 — trip-plan commercial and list

Linear AA-996, Figma visual audit S254 (`AA-Ecosys/docs/audits/2026-10-28-S254-booking-figma-audit/`, slice 2: items
1 and 2, plus the trip-plan picker in `/cases/new` and the Convert inquiry dialog). Session S254, agent Claude Code
(lane, orchestrated). Migration `bk-032` in its own commit.

## Decisions

- **The price matrix stores selling prices per person, priced with the existing engine.** ADR 0005 d6 calls
  `trip_plan_prices` "the published price list" (season × pax band × currency × validity), and d3/d4 say a price comes
  from a net cost per pax band and season through the channel margin. So a row is a *selling* price per person; when
  staff give the net cost per person, the API prices the row with `app.pricing.service.price` (the same rule, FX and
  rounding as `POST /booking/pricing/quote-preview` and `…/versions/{n}/price`) as a one-line quote. No second
  engine: the row is exactly what quote-preview would answer for one cost line. A row without a net cost is a price
  entered by hand (like the bk-009 hint, per band).
- **Channel is a matrix dimension.** The engine prices per channel (B2C tailor-made 30 %, fixed departure 25 %, B2B
  15 %), so the same plan has different prices per channel; `channel` is a column and overlaps are checked per channel
  and currency.
- **Overrides follow the version rule.** An `amount` sent with a net cost is a sales override of the computed price
  (ADR 0005 d4), stored with `overridden = true` so the editor can tell a computed price (shown blank, computed again
  on save) from an override (kept). Below the channel floor it needs a reason (`below_floor_reason`, 422
  `override_reason_required` otherwise, the code versions use), kept in the audit row.
- **Pricing day = the save day (UTC).** A row valid next season is priced with today's approved rule and FX rate, as
  quote-preview does; `priced_on` and `effective_margin` are stored so staff see when and at what margin.
- **Replace the set, like plan components.** `PUT …/prices` deletes and inserts in one transaction (role `booking`
  has SELECT, INSERT, DELETE; no UPDATE, no trigger), one audit row with all rows before and after. The history is in
  `audit_logs`, so the table is a current-state list: no DM-7.1 retention row (same reasoning as bk-029).
- **No overlap per channel + currency** (dates and pax bands), checked in the API: one day and party size has one
  price, so a later `v_from_prices` / quote lookup is unambiguous. An exclusion constraint would need `btree_gist`
  (extensions are not allowed in Booking migrations).
- **From price derived on read** (cheapest B2C row, `b2c_tailor_made` or `fixed_departure`, whose band covers 2 pax and
  that is still valid, USD first). ADR 0005 d6 says "2 pax in low season": the cheapest valid row covering 2 pax is
  that row whenever seasons are priced sensibly, without parsing season labels. `booking.v_from_prices` (contract
  `price.from.v1`, consumer grants) stays a later key; the B2B parity read keeps using the price hint until then.
- **Supplier = one main supplier on the commercial row** (`trip_plans.supplier_id`), picked from active suppliers.
  Left out of a `PUT …/commercial` body it is **kept** (the sellable toggle and an older UI send no supplier and must
  not wipe it); `null` clears it. Set or changed, it must be active; an unchanged supplier that was deactivated since
  stays (saving other fields must not fail). Supplier, prices and from price are commercial: hidden without
  `pricing.read` (content creators).
- **List: sellable first by default** (`sort=sellable`: sellable DESC, then title), destinations from the CIS day
  places (first appearance, trimmed, max 8), a cover that falls back to the first tour photo, the from price. The
  extras are LATERAL joins on equality keys after the LIMIT (lesson S238: `= ANY` does not push through the catalog
  views), so they run for the page rows only.
- **`bk-032` in `REQUIRED_SCHEMA_VERSIONS`**: every trip plan query now reads `supplier_id`, so the code needs the
  migration; DB Migrate must apply bk-032 before the code deploys (CONTEXT "apply before merging code that needs it").

- **UI: one drawer, two saves.** The commercial drawer saves `PUT …/commercial` first, then `PUT …/prices` only when
  the matrix was edited (an untouched or still-loading matrix is never sent, so a slow load cannot wipe it). A 422
  `override_reason_required` keeps the drawer open and shows a reason field; the second save sends it.
- **UI: matrix rows are cards, not a table** (channel, season + peak, validity, pax band, currency, price, optional net
  cost + currency): the drawer is 640 px and must work at 390 px without sideways scroll. Client checks mirror the API
  (`ui/booking/tripPlans.ts`, unit-tested), the API stays the authority.
- **UI: list columns.** Duration is "15 days" over "14 nights" (two lines) and the title / trip style truncate (with a
  title tooltip): with "N days / N-1 nights" on one line the table no longer fitted 1400 px (layout check). The price
  column shows the matrix from price, else the hint marked "hint".
- **Trip plan picker** (`cases/_parts/TripPlanPicker.tsx`): sellable plans only, debounced search. `/cases/new` with a
  plan posts the same fields to `POST /booking/catalog/trip-plans/{source_id}/trip-cases` (new case + V1 from the
  plan's CIS days); the Convert dialog, after the status change, posts `{trip_case: <code>}` (a new draft version).
  Both need `version.write` (admin, sales), so the picker is hidden otherwise.

## Changed

- Spec route map said "Commercial edit (sellable, supplier, price matrix, trip style)"; all four are now in the
  drawer. Figma's age-category price rows (Adult 12+ …) stay dropped (ui-spec §4 table): the rows are pax bands.
- The audit asked for the cover photo on list rows: the CIS cover is used when set, else the first tour photo (the
  detail page keeps the CIS cover field as is).

## Tradeoffs

- Storing the computed selling price (not recomputing on read) means a changed FX rate or rule does not move the
  published list until someone saves again; that is what a published price list should do, and `priced_on` shows the
  age. Recomputing on read would make the list price drift silently.
- The from price is a LATERAL query per list row (page of ≤ 100) instead of a view; cheap on a small table and keeps
  the contract view for its own key.
