# AA-1128 B0 hardening: same-day tie-break and the scheduled-drop warning

Source: the B0 review in the S283 UI audit (root `docs/audits/2026-11-17-S283-fe-audit/README.md` section 6, row 1).
The test b2b rule dated 01/01/2027 was closed in S283 (Infra run-script); this slice adds the two optional guards the
review asked for. No DB write, no migration.

## Decisions

- **Tie-break `approved_at DESC`, then the row id**, in every "row in force" query of the maker-checker tables:
  `repository.RULE_SQL` / `FX_SQL` (the pricing engine), the `in_force` CTEs of `policy.RULES_SQL` / `FX_SQL` (the
  staff list status), `b2b.reads.FX_ALL_SQL` (the B2B FX read) and `b2b.cancellation` `LIST_SQL` / `IN_FORCE_SQL`
  (same pattern, same review finding). The engine and the list use the same keys, so the row the list marks
  "In force" is the row that prices quotes (unit test `test_engine_and_list_agree_on_the_rule_order`).
- The id after `approved_at` makes the order total even for two approvals in one transaction (same `now()`).
- **Warning banner on /pricing/rules**: `ui/booking/ruleDrops.ts` compares each `scheduled` rule with the approved rule
  just before it on its channel (in force or an earlier scheduled one) and lists every lowered target margin, floor
  margin or RRP markup (a scheduled rule without an RRP after one with an RRP counts as a drop). Shown on both tabs,
  under the maker-checker banner, EN and VI (the page's `messages.ts`).

## Changed

- The issue said `RULE_SQL` and `FX_SQL` "and policy.py if the same queries live there"; the B2B FX read and the
  cancellation-policy reads had the same pattern, so they got the same order too.

## Tradeoffs

- Today the unique constraints `pricing_rules (channel, valid_from)`, `fx_rates (currency, as_of)` and
  `cancellation_policies (channel, trip_plan_id, valid_from)` make a same-day tie impossible, rejected and withdrawn
  rows included. The tie-break is a guard for the day those constraints are relaxed (for example to re-enter a day
  whose row was rejected); it costs nothing at these table sizes. The integration test drops the constraints inside
  a transaction it rolls back, and runs both insert orders (one of them fails without the tie-break).
- Pending rows are not compared in the banner: they price nothing until a second person approves them, and the
  approve dialog already shows their values.

## Should know

- The banner is client-side only, from the rules list the page already reads; no API change.
- Closing an approved scheduled row is not possible from the UI (reject / withdraw are for pending rows only), so the
  banner's hint points to a pricing admin. A UI to close a scheduled row is not part of this slice.
