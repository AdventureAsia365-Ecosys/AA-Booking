# AA-1096 — Booking thresholds on Pricing > Policy (S279 thresholds program, lane L3)

Design: root audit `docs/audits/2026-11-13-S279-session/thresholds-audit/` (sections 3, 3.3, 5, lane L3) and root
ADR 0005b decision 15. Tech lead rule (S279): every threshold, limit, cap, quota, retry limit or retention window is an
admin-editable value (administrator role, seeded default, audited), never a code literal, an env var or a config file
value alone. Booking gets no new settings table: its values extend `booking.pricing_policy` (bk-050).

Two PRs, MIG-4 order: the migration-only PR `bk-056` (contract), then this code PR.

## Decisions

- **Migration number bk-056** (owner main max was bk-055). The AA-1093 plan also wants a bk- migration later; it takes
  the next free number after this one.
- **19 new parameters, one per value.** Holds (`b2b_hold_hours` 48, `b2b_hold_extend_hours` 72,
  `b2b_hold_max_extensions` 1, `b2b_rehold_limit_per_day` 3), desk (`b2b_on_request_answer_business_days` 1,
  `b2b_on_request_due_soon_hours` 4), travellers (`b2b_child_age_max` 11, `b2b_infant_age_max` 1), departures
  (`departure_decision_days_default` 21), operations (`pre_departure_days` 14, `supplier_answer_days` 2,
  `trip_check_reminder_days` 3, `supplier_bill_due_soon_days` 3), agency invoices (`agency_reminder_steps_days`
  [1, 7, 14]), rounding (`rounding_increment_by_currency` 5 per selling currency), retention
  (`retention_job_succeeded_days` 30, `retention_job_failed_days` 90, `retention_inbox_redact_days` 90,
  `emergency_contact_keep_days` 90).
- **Seed = today's effective value.** A value moved from `booking.settings` is copied from its row when the row holds a
  whole number inside the range the old code accepted, else the old code default (what was really in force). Version 1
  is made by `seed:bk-056` and approved by `tech lead S279` (all audit defaults approved), in force from 2026-01-01
  like the bk-050 seed.
- **Two new value types.** `integers` (a sorted list of distinct whole numbers, the reminder steps) and `amount_map`
  (exactly one amount per selling currency, at most 2 decimals, the rounding increments).
- **Sections.** `Param.section` groups the page (quotes, prices, surcharges, payments, holds, desk, travellers,
  departures, operations, agency_billing, rounding, retention).
- **A new approver group `admin`** (`pricing_policy.approve_admin` = admin only) for the retention windows and
  `emergency_contact_keep_days`: changing a retention window is a DM-7.5 decision. A finance or contracting maker may
  propose; the administrator approves; never the maker (same CHECK as bk-050).
- **No fallback in code.** Every reader goes through `app.pricing.policy_values` (value in force on the UTC day). A
  missing value is 503 on a staff or agency path (`policy_unavailable` / B2B `unavailable`) and a failed job on a job
  path (the runner retries; retention fails the run with `PermanentError`). The bk-056 post-check guarantees the seed.
- **Rounding stays pure.** `engine.price_quote` / `round_price` / `rrp_price` take `increments` as an argument;
  `app.pricing.service.rounding_increments` reads the policy (`PricingDataUnavailable` without it). The cost sheet
  loads them with the rules and FX of a run (`Pricing.rounding`); empty = every row refused like a row without a rule.
- **Retention windows.** `Part.window_key` names the parameter; `retention.policy.resolve` fills `window_days` at run
  time. A changed window still makes the next scheduled run a DRY RUN (the windows comparison is unchanged).
- **Hold extensions.** `b2b_hold_max_extensions` 0 or 1 (the `b2b_holds_extended_chk` CHECK caps `extended_count` at
  1); 0 turns extensions off (409 `extend_limit`, "holds cannot be extended"). Allowing more than one needs a contract
  migration of that CHECK first.
- **The decision day default** is no longer a pydantic default: `decision_days_before` is `int | None` (None = the
  policy value), and `GET …/departures` returns `defaults.decision_days_before` so the form starts from the policy
  value instead of a frontend copy of 21.
- **`ops_docs_max_bytes`: one source.** The 10 MB settings row was never read; the cap is the code bound
  `app/ops/files.py MAX_BYTES` (3 MB), which must match the staff BFF body cap (audit section 4 item 8: a body cap tied
  to a gateway limit is engineering, not policy). The row is marked "Retired (bk-056)".
- **booking.settings rows are kept**, only re-described ("Moved (bk-056)" / "Retired (bk-056)"): deleting them is the
  destructive class. `b2b_ops_timezone` and `b2b_ops_contact` stay settings (a zone and a printed line, not policy).

## Tradeoffs

- **Stored-only parameters: badge, not wired.** The 15 parameters of bk-050 with `used_by="stored"` read features that
  do not exist yet (surcharges after confirmation, provisional prices, FOC, gala dinners, group deposit terms, agency
  currency by country, the next tariff reminder, recompute approval). Wiring any of them means building that feature;
  each now says what is missing (`pending`) and the page badges it "Not enforced yet" (audit Q6 default).
- **Baseline in the guard instead of 80 inline comments.** The 80 constants that predate the rule are listed in the
  test with a reason (technical bound, job mechanics, or a known gap); new ones need `# technical-constant: <why>` or a
  policy parameter. The baseline only shrinks (an entry whose constant is gone fails).
- **Per-call policy reads.** Each reader loads the policy rows in force (one small indexed query). No process cache:
  a change applies on its day without a restart, and the cost is negligible next to the quote queries.

## Fix round (S280): Pricing › Policy search (settings UX audit, lane cis-settings)

The CIS Platform › Settings Booking tab links here; the S280 audit found the same search defect as on the CIS page.

### Changed

- **One search over every section** (`frontend/app/(staff)/pricing/policy/_parts/PolicyView.tsx`, `PolicySearch`):
  a full-width box (up to 560 px) above the sections; each word of the query must appear in the parameter's key, its
  label as shown, its help or its guide (English and Vietnamese), in any case. (Since the merge with the settings
  audit lane below, the matching is `lib/policyEdit.ts` `searchText` / `matchesSearch`, tested in
  `lib/policyEdit.test.mjs`.) While a query is typed the sections show only their matches (empty sections
  are hidden) and a line counts the matches across all sections; no match shows "No parameter matches".
- The section tables no longer have their own search (`searchable={false}`): each kit box filtered only its own
  section, by label only (the key did not match), in the kit's narrow 220 px input.

### Decisions

- The section layout stays while searching (headers and hints keep the context); only the rows are filtered.
- The guide text of both languages is searched, so a Vietnamese word finds a parameter while the page is in English.

### Tradeoffs

- **One page search vs the kit's per-table search**: a single box finds a parameter in any section and matches the
  key, at the cost of turning off the kit feature on these tables (`searchable={false}`) and owning the matching in
  `lib/policyEdit.ts` instead of the kit.
- **Every word must match (AND) vs any word (OR)**: AND narrows as the person types, which suits a known parameter;
  a loose topic search ("deposit refund") may return nothing where OR would list both groups.
- **Searching both guide languages vs the shown language only**: more matches for a mixed-language team, with the
  small risk of a match whose matching words are not visible on the page in the current language.
- **Client-side filtering vs a server search**: the policy parameters are a short, already loaded list, so no API
  change was needed; it would need revisiting only if the list grew to hundreds of rows.

### Should know

- The kit table search input gains an `aria-label` in the CIS canonical kit (CIS PR of the same round); it reaches
  `frontend/ui/core/DataTable.tsx` here through the next kit sync.

## S280 — bk-058: reject and withdraw of pending policy rows (migration only, MIG-4)

### Decisions

- **A closure table, not a status column.** `pricing_rules`, `fx_rates` and `cancellation_policies` are append-only
  (no UPDATE for role `booking`), so the end of a pending row is a row of `booking.policy_row_closures` (`rejected` by
  a second person with a reason, `withdrawn` by its maker), the same shape as `pricing_policy_events` (bk-050).
- **Backstops in the database.** CHECKs carry the maker-checker rule; a trigger checks that `maker` is the row's
  creator and that the row is not approved; a trigger on `policy_approvals` refuses an approval of a closed row. The
  app also takes a per-row advisory lock, so approve and close never race.
- **Key bk-058.** The bk-057 header names bk-058 for the B2C table drop, but that file is not on main and the guard
  wants contiguous numbers; whichever lands second renumbers.

### Tradeoffs

- **The day stays taken.** The three unique keys (scope + day) still count a closed row, so a corrected row takes
  another day. Freeing the day means dropping those constraints and keeping "one approved row per scope and day" only
  in the app (plus a tie-break in every reader, the bk-039 `v_from_prices` view included): a tech lead decision.

### Should know

- Contract class (new append-only table with a REVOKE, new trigger on `policy_approvals`): migration-only PR first,
  then the code PR (branch `fix/s280-policy-row-reject-withdraw`) raises readiness to bk-058.
- DM-7.1: the root data standards need a retention row for `booking.policy_row_closures` (kept, configuration, like
  `booking.policy_approvals`) before the Infra copy.

## S280 — settings UI audit fixes (Pricing › Policy, Pricing rules & FX, Agency billing › Settings, Settings)

Lane "booking" of the S280 "check and fix everything" pass over the settings and threshold screens; the findings were
adversarially verified before this lane.

### Decisions

- **Integers parameter (overdue invoice reminders).** `PolicyProposal.value` takes `list[int]` before `list[str]`:
  Pydantic never turns a JSON number into a string, so `[3, 10]` was a 422 for every `integers` parameter. An
  integration test POSTs `agency_reminder_steps_days` with JSON numbers.
- **Another maker's draft.** A draft never expires and blocked the parameter for everyone (409 `open_version`). New
  `POST /booking/pricing/policy/{id}/discard`: a member of the parameter's approver group (never its maker) discards
  another maker's draft with a reason. It is stored as the existing step `rejected` (the table CHECK already wants a
  second person and a reason for it), audit action `pricing_policy.discarded`; no migration. The row shows "Draft by
  <name> since <date>", Change says in its tooltip why it is locked, and the 409 names the draft's maker
  (`open_status`, `open_by` in the error body).
- **Value on the chosen day.** The API compares a proposal with the value in force on its effective day; the drawer
  now pre-fills and shows that value (in force or a scheduled one starting by then), lists every scheduled change and
  warns when a later scheduled change will replace this one. The row lists every scheduled change; the API sorts
  `scheduled` by effective day.
- **Page hints from the API** (`app/pricing/policy_hints.py`, kept out of `policy_params.py`, which sits on the file
  size baseline): `cross_bound` `{relation, key}` per parameter with a cross check, `not_enforced_reason_vi` per
  "not enforced yet" reason. A unit test keeps both maps complete and checks the integer bounds against `normalise`.
  The drawer writes the bound with the other parameter's label and value on that day and refuses a value outside the
  range or the bound before sending.
- **One page-wide search** (URL `q`) instead of a search box per section: label in both languages, key, the whole
  guide in both languages, help, approver name in both languages, the value; sections with no match hide.
- **One search after the merge with the search fix round above** (both lanes built a page search; one is left). The
  matching is this lane's (`lib/policyEdit.ts` `searchText` / `matchesSearch`: accents folded, translated labels,
  approver, value), now over every guide part (what, raise, lower, when, example) as the fix round did. The box is the
  fix round's (`PolicySearch`: full width up to 560 px, an `aria-label`, the match count line, "No parameter matches"
  instead of an empty table). It replaces the kit `FilterBar` here: the kit box is at most 420 px, uses its
  placeholder as its label and adds a "Reset filters" row a single search does not need; `PolicySearch` keeps the URL
  `q` with the kit's 300 ms debounce. The fix round's `lib/policyGuide.ts::searchParams` is gone (its test cases moved
  to `lib/policyEdit.test.mjs`).
- **Every API error in the page's language** (`policyUi.errorText`): each code has a message; an unknown code names the
  code instead of the API's English text. `approver_group` names the parameter's real approver (administrator for
  retention), Submit on a passed day has its own text.
- **Retired settings rows.** Settings › Commercial defaults and the proposal preview no longer read
  `booking.settings` `deposit_pct` / `quote_validity_days` (retired by bk-056): quote validity comes from the pricing
  policy (with the festive value and the allowed range, link to Pricing › Policy), the deposit from the agency payment
  terms (the default terms for finance, else a pointer). `lib/bookingConfig.ts` (the constants and the hard-coded
  "7–30" range) is gone.
- **Agency payment terms.** Agency billing › Settings › Payment terms adds and edits an agency's own terms (agency
  picker from the active B2B partners, `PUT /booking/billing-terms/agencies/{tenant}`, which existed with no caller)
  and shows every field in force for each agency. The deposit keeps the typed text (no float noise), each day count
  shows its allowed range (the API's `BillingTermsIn` bounds) and an empty or out-of-range field is refused under it
  (`lib/billingTermsForm.ts`).
- **Past effective days for rules, FX rates and cancellation schedules.** Create refuses a day before today (422
  `effective_in_past`), approval refuses a row whose day has passed (409 `effective_date_passed`), as for the policy
  parameters. The FX "as of" day is the day the rate takes effect, so the page calls it "In force from".
- **Pricing rules & FX in Vietnamese.** Same language switch as Pricing › Policy (`rules/_parts/messages.ts`); the
  early-booking helper messages are translated by their English text, so `ui/booking/earlyBooking.ts` stays as is.

### Changed

- The bk-021 integration test that needs a backdated, approved cancellation schedule now writes it directly (the API
  refuses it on purpose now).
- `PolicyView.tsx` was split (ChangeDrawer.tsx, policyUi.ts, small cell components) to stay under the complexity
  ratchet; the code-health baseline shrank (5 entries gone).

### Tradeoffs

- Discarding reuses the `rejected` step instead of a new step value: no migration, and the history already shows
  "rejected by <name>: <reason>". A new "discarded" step would need a CHECK change (contract migration).
- The terms form mirrors the API bounds in `lib/billingTermsForm.ts`; they are validation bounds of the endpoint, not
  policy values (the policy values stay on Pricing › Policy).

### Should know

- Reject / withdraw of a pending pricing rule, FX rate or cancellation schedule (and freeing its day) needs a table
  for the decision (the rows are append-only, the day is a unique key): not in this branch; see the bk-058 section
  (migration, merged first) and branch `fix/s280-policy-row-reject-withdraw` (code).
