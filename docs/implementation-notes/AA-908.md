# AA-908 — signed-in traveller → verified Booking customer (Booking slice S3)

Root ADR 0006 Phase 4. TripPlanner travellers sign in on the Cognito EXTERNAL pool. A signed-in hand-off
(`inquiry.submitted` v1.4) carries the verified identity, and Booking links it to one customer. Two PRs (lesson
S249: a Booking code PR that needs a new migration merges only after the apply):

1. **Migration-only PR:** `migrations/024_customer_identities.sql` (bk-024) plus its schema test. `migrations/` and
   `backend/tests/` are outside the deploy paths, so merging it deploys nothing.
2. **Code PR:** contract v1.4, intake, `REQUIRED_SCHEMA_VERSIONS += bk-024`. It is stacked on the migration PR and
   merged after the DB Migrate apply.

## Decisions

- **Key bk-024, not the plan's bk-023.** SCHEDULE §1 gave bk-023 to AA-835 (`023_supply_outbox_media.sql`, merged as
  #84).
- **`customer_identities` primary key is `(iss, sub)`.** One identity belongs to one customer, and a customer may
  hold several (a later Google sign-in, another pool). It is keyed on iss AND sub, never sub alone (ADR 0006 d9). The
  shape CHECK matches `staff_users.cognito_*` (bk-016) and the contract: iss https and ≤ 300 characters, sub 1–128.
- **ON DELETE CASCADE.** The identity follows its customer (DM-7 row: kept while the customer is kept). Customers
  are archived (`deleted_at`), not deleted, so the cascade only matters for a future erasure step.
- **Archived customer:** intake re-points the identity to a new customer (UPDATE of `customer_id`). That is the only
  column role `booking` may update. `iss` / `sub` are never rewritten and rows are never deleted by the app.
- **`customers_source_chk` gains `traveller_signin`.** It is swapped in place in this migration, before the code that
  writes the value is deployed (lesson AA-847: a CHECK value must exist before its writer).
- **No phone or address import for a signed-in customer.** Only the name and the token's email. ADR 0006 Phase 4:
  no unverified field is imported into a verified customer.

## Tradeoffs

- **One table, not identity columns on `customers`.** Columns would allow only one identity per customer and would
  need a pair CHECK like bk-016. A table keeps the customer row unchanged and allows a second identity later.
- **The intake rule (b) attaches an identity to an existing verified customer with the same email.** This is safe
  only because the token's `email_verified` is true: the EXTERNAL pre-sign-up trigger refuses `email_verified` on
  SignUp, and the address was confirmed by an email code. A guest's typed email never takes this path (verified is
  false without an identity, enforced by the v1.4 schema).
