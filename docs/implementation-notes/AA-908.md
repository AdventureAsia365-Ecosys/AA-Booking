# AA-908 — signed-in traveller → verified Booking customer (Booking slice S3)

Root ADR 0006 Phase 4. TripPlanner travellers sign in on the Cognito EXTERNAL pool. A signed-in hand-off
(`inquiry.submitted` v1.4) carries the verified identity, and Booking links it to one customer. Two PRs (lesson
S249: a Booking code PR that needs a new migration merges only after the apply):

1. **Migration-only PR:** `migrations/024_customer_identities.sql` (bk-024) plus its schema test. `migrations/` and
   `backend/tests/` are outside the deploy paths, so merging it deploys nothing.
2. **Code PR:** contract v1.4, intake, `REQUIRED_SCHEMA_VERSIONS += bk-024`. It is stacked on the migration PR and
   merged after the DB Migrate apply.

## Decisions

- **Key bk-024, not the plan's bk-023.** SCHEDULE §1 gave bk-023 to AA-835 (`023_supply_outbox_media.sql`, merged as
  #84).
- **`customer_identities` primary key is `(iss, sub)`.** One identity belongs to one customer, and a customer may
  hold several (a later Google sign-in, another pool). It is keyed on iss AND sub, never sub alone (ADR 0006 d9). The
  shape CHECK matches `staff_users.cognito_*` (bk-016) and the contract: iss https and ≤ 300 characters, sub 1–128.
- **ON DELETE CASCADE.** The identity follows its customer (DM-7 row: kept while the customer is kept). Customers
  are archived (`deleted_at`), not deleted, so the cascade only matters for a future erasure step.
- **Archived customer:** intake re-points the identity to a new customer (UPDATE of `customer_id`). That is the only
  column role `booking` may update. `iss` / `sub` are never rewritten and rows are never deleted by the app.
- **`customers_source_chk` gains `traveller_signin`.** It is swapped in place in this migration, before the code that
  writes the value is deployed (lesson AA-847: a CHECK value must exist before its writer).
- **No phone or address import for a signed-in customer.** Only the name and the token's email. ADR 0006 Phase 4:
  no unverified field is imported into a verified customer.

- **Code PR: consumer of v1.4.** `contract.py` accepts 1.4, against the byte copy of root `docs/contracts/inquiry.submitted.v1.4.json`
  (root #237; its SHA-256 is pinned in the unit test). `Contact.identity` is read only from a v1.4 payload. The
  customer object of v1–v1.3 is closed, so it cannot carry an identity. The trip-case snapshot never holds the
  identity: it lives in `customer_identities`.
- **Code PR: when the signed-in path applies.** `Contact.signed_in` = identity AND verified AND email. Every other
  contact (a v1.4 guest send, or v1–v1.3) takes the unchanged lead path, including the old v1.1 rule "verified contact
  with a verified-customer email → link".
- **Code PR: lead flagging.** It runs on every signed-in send, not only on (c), because a guest may have sent from the same
  address since the last sign-in. It touches only unverified live `tripplanner_lead` / `manual` rows with
  `merge_candidate_id IS NULL`, so an earlier staff decision or another candidate is never overwritten.
- **Code PR: staff visibility.** The notification says "Signed-in traveller (verified email)." and counts the flagged
  leads. The summary and audit row carry `signed_in` (identity | email | created) and
  `leads_flagged_for_review`. No log line carries the sub, iss or email (DM-6.4). The optional
  "Signed-in traveller" badge on the staff customer page is not built. The customer detail page already shows
  `verified` and `source`.
- **Code PR, review round 1: the issuer is checked and pinned.** The v1.4 schema checks `identity.iss` only with
  `format: uri`, and `Draft202012Validator` runs without a FormatChecker, so `http://evil` or `not a uri` passed. Such
  a payload then hit the bk-024 `customer_identities_shape_chk` inside `resolve_signed_in`: a CheckViolation, not a
  ContractError, so the inbox row stayed `received` and the job retried it forever (a poison message).
  - `contract.validate()` now also requires an `https://` issuer of at most 300 characters with no whitespace, for
    any v1.4 identity. The reason text never quotes the value (it is stored on the inbox row and logged).
  - `contract.parse(payload, traveller_issuers=...)` refuses any other issuer (root ADR 0006: each route class pins its
    issuer). The intake passes `{Settings.cognito_external_issuer}` (`COGNITO_EXTERNAL_ISSUER`, default
    `identity_config.DEV_EXTERNAL_ISSUER`, the Dev EXTERNAL pool read from `cognito-idp list-user-pools` on
    24/10/2026) through `intake.build_handlers(settings)`, which `main.py` now uses. `intake.HANDLERS` and
    `process()` default to the Dev issuer, so tests need no settings. A wrong issuer is a contract error: the row is
    `failed` once with the reason.
  - Test samples use the Dev issuer (`samples.ISS`), plus `samples.FOREIGN_ISS` for the refusals.
  - Follow-up for the root contract (next minor or text fix): add `"pattern": "^https://"` to `identity.iss` in
    `docs/contracts/inquiry.submitted.v1.4.json`, so the schema states what the DB CHECK needs. Not done here: the
    vendored copy is a byte copy with a pinned SHA-256, so it changes only after the root file does.
- **Code PR, review round 1: concurrent sends of one new identity.** `resolve_signed_in` first takes
  `pg_advisory_xact_lock(hashtextextended(iss || ' ' || sub, 908))`. A second hand-off of the same identity waits for
  the first transaction, then finds its identity (a), instead of failing on the key and waiting for a job retry. Two
  different identities with the same new email can still collide on `customers_email_verified_uq`; the retry then takes
  (b). That case needs two Cognito accounts with one verified email, which the pool does not allow.
- **Code PR, review round 1: blocked customers.** (a) and (b) can resolve to a customer with `is_blocked = true`. The
  case is still opened (staff decide), the notification adds "Customer is blocked." and the summary carries
  `customer_blocked`.
- **Code PR: `REQUIRED_SCHEMA_VERSIONS += bk-024`.** bk-023 is still left to AA-835 S4, which reads its shapes.
  Both lines sit at the end of the tuple, so whichever merges second takes a one-line rebase.

## Tradeoffs

- **One table, not identity columns on `customers`.** Columns would allow only one identity per customer and would
  need a pair CHECK like bk-016. A table keeps the customer row unchanged and allows a second identity later.
- **The intake rule (b) attaches an identity to an existing verified customer with the same email.** This is safe
  only because the token's `email_verified` is true: the EXTERNAL pre-sign-up trigger refuses `email_verified` on
  SignUp, and the address was confirmed by an email code. A guest's typed email never takes this path (verified is
  false without an identity, enforced by the v1.4 schema).
