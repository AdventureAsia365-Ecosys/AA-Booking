# AA-683: staff admin frontend scaffold (Wave 1 base)

Scope: the Next.js app in `frontend/` that every Wave 1 page lane builds on. Sources: S236 UI spec
(`ui-spec.md` §1–§5, §8), shell module spec `01-shell.md`, the S236 design system draft
(`aa-design-system.md`), root ADR 0004 and the CIS kit at AA-CIS-App commit `039bb250`.
Stacked on `feat/aa-681-staff-auth-trip-case-versions` so the typed client matches the bk-003/bk-005 API.

## Decisions

- **Kit copy, not a rewrite.** `ui/` holds byte copies of the CIS kit files (tokens.ts, brand.ts, primitives,
  DataTable, Modal, Drawer, Toast, theme/sidebar stores, Providers). Each file starts with a two-line header
  naming the CIS commit. Only imports and the two localStorage keys changed (`bk_theme`, `bk_sidebar`, spec §1.1).
  `ui/tokens.css` is a byte copy of the `--aa-*` blocks (CIS `globals.css` lines 30–246).
- **Shell components are adapted copies.** `AdminShell`, `Sidebar`, `Topbar`, `BottomNav` and `CommandPalette`
  follow the CIS structure and CSS class names (so the copied shell CSS works unchanged) but read the Booking nav
  model (`ui/nav.tsx`) and the Booking staff profile instead of CIS `adminNav` / `useAdminIdentity`.
- **Styling (spec Q2 recommendation).** Copied kit components stay inline-style on `K`. Booking-only
  components (`ui/booking/*`) and page layout use Tailwind v4 utilities generated from the same `--aa-*`
  variables (`@theme inline` in `app/globals.css`), never raw hex. One colour source, two ways to read it.
- **Visual (Nghiệp S236 decision 1).** adventure.asia tokens identical to the CIS kit: Poppins UI, Fahkwang
  titles and KPI numbers, gold `#DB9628` / deep `#9E6E16`. Light gold `#E3BD7F` is not in the kit; it is added
  as the Booking-local `--bk-accent-line` (design system §2.1 "divider gold"). Satisfy is loaded for the login
  splash line only (design system: never in admin UI, never under 32 px).
- **Buttons stay kit pills.** The design system proposes radius 8 for admin buttons, but decision 1 says
  "identical to the CIS kit", so `BTN_RADIUS` stays 999. Changing it is one value in `ui/brand.ts`, made in CIS first.
- **Login (decision 2, spec §4.1, Q4 recommendation a).** `/login` posts to the BFF `POST /api/auth/login`, which
  calls CIS `POST /auth/admin-login`, then `POST /auth/booking-token` with the CIS token as Bearer. Two httpOnly
  cookies: `bk_cis_session` (the 24 h CIS staff token, used only to mint) and `bk_access` (the 15 min Booking JWT).
  The browser never sees a token. Error copy never says which field was wrong.
- **Token refresh in one place.** `lib/session.ts` decides refresh (Booking token missing or under 2 min left) by
  reading the JWT `exp` without verifying it; verification is the Booking API's job (JWKS, `aud=booking`). The
  proxy (`proxy.ts`, Next 16's name for middleware) refreshes on page requests and forwards the fresh cookie to the
  server render; the BFF proxy refreshes on API calls and retries once on a 401.
- **Route protection.** `proxy.ts` sends every request without a CIS session to `/login?next=…`; a failed mint
  (CIS 401: session expired, user deactivated in CIS) clears both cookies. The `(staff)` layout then calls
  `GET /booking/staff/me` server-side: 401 → `/login`, 403 `staff_inactive` → "pending activation" screen,
  network/5xx/404 → "Booking API unavailable" screen. Page access by role is checked in the shell
  (`lib/rbac.ts`, spec §3 roles); the Booking API enforces its own permission matrix on every call.
- **Google sign-in (decision 2).** One public env var, `NEXT_PUBLIC_GOOGLE_SIGNIN_URL`. Unset (default) → the
  button is not rendered. Set → "Continue with Google" links to it. The flow itself is AA-703.
- **Waves (decision 3).** Every spec §3 route has a page file. W1 pages have real headers and regions; W2/W3 pages
  render the Figma layout frame (header, KPI labels, filter bar, column headers, tabs) around an EmptyState
  "Coming in wave 2/3". No fake rows anywhere. Nav items of a later wave stay hidden (spec §2.2) until
  `SHIPPED_WAVE` in `ui/nav.tsx` is raised.
- **Statuses (decision 4).** The 13 DB statuses keep their own labels and tones (spec §1.3); the case stepper
  groups the 12 non-cancelled ones into 4 phases (Inquiry, Proposal, Booking, Travel); `cancelled` is a red banner.
- **Deposit 30 % and quote validity 14 days are config.** They come from `GET /booking/settings` (bk-005 seed rows
  `deposit_pct`, `quote_validity_days`); `lib/bookingConfig.ts` holds the same values as the fallback when the
  settings call fails, so a page never invents a different number.
- **Hotels / activities (decision 5).** Not touched beyond their W2 frames.
- **Dev API base URL.** `BOOKING_API_URL` defaults to the Dev execute-api stage
  `https://9z3xnalp59.execute-api.us-west-1.amazonaws.com/dev` (spec §6, ADR 0004 O2) until
  `api-booking.lumiguides.it.com` has its certificate. `CIS_API_URL` defaults to `https://api-cis.lumiguides.it.com`.

## Changed vs the brief

- **`proxy.ts`, not `middleware.ts`.** Next 16 renamed the middleware file convention to `proxy` (the old name is
  deprecated). Behaviour is the same; the build lists it as "Proxy (Middleware)".
- **W1 pages read the real API** instead of being bare skeletons: dashboard (summary + recent cases), cases list,
  new case form, case workspace (Overview / Proposals / Activity, read-only), builder and preview (read-only),
  proposals, customers + detail, staff + detail, notifications, settings. Every list has its real empty state.
  Write actions that need modals (change status, assign, edit details, convert / decline, send, approve, item
  editing, staff role / activation, customer edit / block / archive) are left to the page lanes; the API calls
  are already typed in `lib/api/client.ts`.
- **Pricing calculator** shows its layout and an empty state naming the dependency: `POST
  /booking/pricing/quote-preview` is on the unmerged bk-004 branch (AA-810), whose auth stub returns 401 (D1).
- **Case "Billing" and "Checks" tabs** are visible but disabled ("Coming in wave 3"); they are query tabs of
  `/cases/[code]`, not routes.
- **Trip style and countries** are not on the new-case form (spec Q13 / Q16 have no source yet).

## Tradeoffs

- **Kit-copy vs rewrite (spec Q2).** Copying keeps CIS and Booking byte-comparable (a CI diff is possible later,
  Q3) at the cost of two styling idioms in one repo. The eslint rule keeps page code off raw hex either way.
- **The kit `Tabs` (segmented pills) is kept, but list / detail pages use underline tabs** (design system §4:
  "gold text with a 2 px gold underline", which is the Figma). The copied kit file is not edited; the underline
  tab lives in `app/(staff)/_parts/SavedTabs.tsx` and the detail pages.
- **Role gating in the shell, not in `proxy.ts`.** The role lives in `booking.staff_users`, so knowing it in the
  proxy would cost an API call per navigation. The shell already has it (one `staff/me` per server render) and the
  API enforces permissions on every call, so a mistyped URL shows "no access" instead of data.
- **Session refresh reads `exp` without verifying.** Verifying RS256 in the proxy would need the JWKS and a JOSE
  dependency, and would duplicate the API's check. A forged cookie only causes a refresh or a 401 from the API.
- **No unit-test runner in the frontend yet.** The required checks for this slice are lint + typecheck + build
  (ADR 0004 decision 3). Pure helpers worth testing first: `lib/rbac.ts` (`canSeePage`), `lib/session.ts`
  (`needsRefresh`), `ui/booking/Stepper.tsx` (`stepState`).

## Page lane fe-cases (trip cases list, create, workspace)

### Decisions
- **List (`/cases`).** Saved tabs All / Inquiries / Mine / Unassigned / Active / Closed set the `status` / `assignee`
  query; an explicit Status (multi) or Sales rep filter overrides the tab preset. All filters and paging live in
  the URL. Tab counts come from `GET /booking/trip-cases/summary`; Mine / Unassigned show no count (the summary
  has no exact number for them).
- **Create (`/cases/new`).** Existing customer (debounced search on `GET /booking/customers`, blocked customers
  disabled) or "+ New lead" inline (`new_customer`, name + e-mail or phone, consent). Sales rep defaults to the
  signed-in user when they are sales. Initial status New inquiry or Discovery (CaseCreate `initial_status`).
- **Workspace (`/cases/[code]`).** Status actions only offer `allowed_transitions` from the API. New inquiry →
  "Convert to discovery" (optional rep change + note) and "Decline" (reason select + notes). Later statuses →
  "Change status" menu + "Cancel case…" (reason required). Cancelled → "Reopen" (reason required, back to
  New inquiry). `confirmed` shows disabled with "approve a sent proposal version" (the API answers
  `approve_version_first`).
- **Edit details** sends only changed CasePatch fields (start date, adults/children, currency, countries, notes);
  the customer is locked. Internal notes are also editable inline on the Overview (same PATCH `notes`).
- **History** is the Activity tab (`GET /trip-cases/{code}/activity`, cursor `before`), which merges status
  history with audit rows.
- **States.** Skeleton while loading, kit ErrorState with Retry, 403 → "You do not have access" empty state,
  404 → "Trip case not found". Create page without `trip_case.write` shows the permission-denied state.

### Changed
- `ui/booking/FilterBar.tsx` gained an additive `extraKeys` prop so a child control (the status multi-select)
  counts as an active filter and is cleared by "Reset filters".
- The Proposals tab moved to `ProposalsTab.tsx` unchanged so the builder lane can own its actions.

### Tradeoffs
- Decline / cancel reasons are a fixed front-end list (stored as "Reason: notes" in the status note, ≤ 2000 chars)
  rather than a settings table: there is no reason catalog in bk-005.
- Currency select offers USD/EUR/GBP/AUD/SGD; the API accepts any 3-letter code, and a case already in another
  currency keeps it in the edit drawer.

### Should know
- Endpoints used: `GET/POST /booking/trip-cases`, `GET /booking/trip-cases/summary`, `GET/PATCH
  /booking/trip-cases/{ref}`, `GET /booking/trip-cases/{ref}/activity`, `POST /booking/trip-cases/{ref}/status`,
  `POST /booking/trip-cases/{ref}/assign`, `GET /booking/customers`, `GET /booking/staff/directory`,
  `GET /booking/countries`. All are on the bk-003/bk-005 backend; none is live on Dev yet.
- Not verified in a browser against real data (Dev API not deployed); lint, typecheck and build pass.

## Builder lane (fe-builder): proposals, preview, send, calculator, /proposals

Routes: `/cases/[code]/proposals/[n]`, `/cases/[code]/proposals/[n]/preview`, `/pricing/calculator`, `/proposals`.
New files: `lib/api/proposals.ts` (typed version + pricing calls, kept out of `client.ts` so lanes do not collide),
`lib/proposalDraft.ts` (pure builder state: grouping by day, reorder, validation, quote request),
`ui/booking/PricePanel.tsx` (cost lines, price settings, quote result, `useQuotePreview`),
`ui/booking/PageState.tsx` (page skeleton; 403 / 404 / error views), `proposals/_parts/SendProposalModal.tsx`,
`[n]/ItemDrawer.tsx`.

### Decisions

- **Every price number comes from the API.** The panel calls `POST /booking/pricing/quote-preview` (bk-004,
  `feat/aa-810-pricing-engine`), debounced 500 ms, and renders its lines, totals, margin and `below_floor`. The
  frontend never computes a margin or a sum (review finding 10 removed the per-item subtotal).
- **Net cost lines are saved with the items** (review fix, see below): `PUT …/items` carries `costs[]` per item and
  "Apply price" calls `POST …/versions/{n}/price`. (Superseded: they were page state only in the first cut.)
- **Below-floor override reason** is sent with Apply price (`override_reason`) and is required by the API there.
- **Send** uses `POST …/versions/{n}/send`: subject, message and valid-until (default today + `quote_validity_days`
  from settings, range from `bookingConfig`). Copy says "marked as sent and locked. No e-mail was sent."
  Send stays disabled while the version has no `total_price` (the backend rejects it the same way).
- **Item saves** use `PUT …/items` with ids (D2 upsert); order is "by start day, then staff order inside the day".
  Drag-and-drop plus up / down buttons (the buttons are the keyboard and phone path).
- **`/proposals` "Duplicate" is "New version".** `POST …/versions` always copies the case's *latest* version;
  the API has no "copy version N". The row action is labelled and confirmed that way, never "duplicate this row".
- **"+ New proposal"** opens a case picker (`GET /booking/trip-cases?q=`, 8 results). Picking a case opens its
  latest version, or creates V1 (prefilled from the case legs by the API) when it has none. Closed cases are disabled.
- **Pricing access** in the builder uses the role list admin / sales / contracting, matching bk-004's
  `pricing.read`; this backend's permission matrix does not have `pricing.read` yet, so `useCan` cannot be used.

### Should know

- Preview shows what Booking stores (items, notes, day dates from the case start date). CIS day text, photos and
  the map need `GET /booking/catalog/tours/{id}` (spec §6.2); the page says so. Download PDF is W2.
- Quote errors are mapped: 404 → "pricing engine not on this API yet", 422 missing FX / rule → "price in USD or
  have the row added" (no link: Pricing rules & FX is a wave 2 page), 503 → data unavailable, 403 → no access.

## Review fixes (S236 review of the W1 branches)

Backend fixes are on `feat/aa-681-staff-auth-trip-case-versions` (findings 2, 4, 6, 13) and
`feat/aa-810-pricing-engine` (3, 7; see AA-681-w1.md and AA-810.md). Frontend, this branch:

- **1 Open redirect (major).** `lib/safeNext.ts`: refuses control characters (tab / CR / LF are stripped by
  browsers, so `/\t/evil.com` became `//evil.com`) and backslashes, then resolves against a placeholder origin and
  keeps only a same-origin path (never `/login`). Used by the login page and again in `LoginForm` right before
  `router.replace`.
- **3 Price and costs (major).** The builder now loads each item's `costs[]`, saves them with the items, and has
  "Apply price to this version" (`POST …/versions/{n}/price`), enabled only when the draft is saved, every item has
  a cost line (0 allowed), the live quote is fresh and, below floor, a reason is given. The saved total (and the
  FX rate for non-USD) shows under the panel; Send / preview copy says "apply a price" instead of "not deployed".
  A Save that changes items or costs clears the price on the server; the toast says so. With this the W1 sales
  flow (costs → price → send → approve → confirmed) is reachable in the UI once bk-810 is deployed.
- **5 FX on Dev.** `FxNotice` on the calculator and the builder: non-USD needs a rate and Booking cannot enter
  rates before wave 2. The missing-FX error no longer links to the wave 2 page.
- **8 Login / logout CSRF.** `lib/sameOrigin.ts` is shared by the BFF (unchanged behaviour) and both auth routes,
  which are strict: `Origin` (or `Sec-Fetch-Site: same-origin`) must match, and login also needs a JSON
  content type (a cross-site form can post text/plain that parses as JSON).
- **9 Session end mid-page.** `ui/booking/QueryProvider.tsx` replaces the mounted CIS `Providers` (that file stays
  byte-comparable with CIS, unmounted): a 401 from any query or mutation goes to `/login?reason=expired&next=…`,
  and 4xx answers are never retried (`retryUnlessClientError`, also used by the pages that had their own retry).
- **10 Money.** No client-side sum per item (per-line amounts only); `formatMoney` always shows the currency's
  minor units (`1,845.00 USD`, `17,780,000 VND`).
- **11 DataTable a11y.** aria-labels on the page-size select and previous / next buttons, marked as a local
  deviation in the copied CIS file: upstream the same three attributes to CIS `app/_kit/DataTable.tsx`.
- **12 "Lead" chip** on the dashboard, case list and case header is now "Unverified" (it marks an unverified
  customer; customer status lead / active / past stays on `/customers`).
- **13** needs no UI change: the status menu lists `allowed_transitions`, so a confirmed case now offers Cancel.
- **15** Cost lines accept 0 (message "An amount of 0 or more"); the override total stays strictly positive.
- **14** (rebase onto `origin/main` 57dafdc, which squash-merged bk-003 as #2): all three branches were rebased
  `--onto origin/main 139825d`.

## S237 wave 1 close-out (dashboard hint, card fee row, per-entry nav flag, /audit-log, ui-spec.md)

Frontend and docs only: no migration, no backend change, so no Booking API deploy. Sources: the S236 UI verify
follow-ups (Linear AA-683 comment), the S237 lane plan (booking item 1) and UI spec §1.3, §3, §4.2, §5, §6.2.

### Decisions

- **Dashboard tile vs hint.** The "In progress" tile counts `discovery` + `building`, but its hint said
  "`open` open · ±delta vs last month" (`open` = every non-terminal status, delta = cases created this month vs
  last). With only TC-000001 in `new_inquiry`, the tile read "0" over "1 open". The tile and its label stay (Nghiệp
  S236 role rule); the hint now says what the number is ("In discovery or building"). The open total and the
  month-over-month delta, which spec §4.2 puts on an "Open trip cases" tile, moved to the header of the
  "Pipeline by phase" card, the one place that already shows every phase. No number was dropped.
- **Card fee row.** The quote summary gets a "Card fee (included in the price)" row showing
  `rule.card_fee_pct` from the quote-preview response (3% today). It is a rate, not an amount: the engine builds the
  fee into the selling price (`net / (1 - margin - card_fee)`, ADR 0005) and the API returns no fee amount, so the
  frontend still computes nothing. 1000 USD net still prices to 1,495.00 USD (the response is unchanged).
- **Per-entry nav flag.** `SHIPPED_WAVE` is gone. Every `NavEntry` has `shipped: boolean` (and keeps `wave` as
  information). `isVisible` = `shipped && canSeePage(role, href)`. All wave 1 entries are `shipped: true`; of the
  wave 2/3 entries only `/audit-log` is. The next page (AA-810 `/pricing/rules`) flips its own flag.
- **/audit-log over the existing API.** `page.tsx` stays a server file (keeps the `<title>`) and renders the client
  `AuditLogView`. Filters map 1:1 to `GET /booking/audit-logs`: record type (`entity_type`), staff member (`actor`,
  options from `GET /booking/staff`, the page is admin-only anyway), date range (`from` / `to`, `to` inclusive) and
  `entity_id` (set by "Only this record" on a row or by a link `/audit-log?entity_id=<uuid>`, shown as a removable
  chip; a value that is not a UUID is ignored and the chip says so, instead of a 422). Keyset pages with
  "Show older"; the footer counts loaded rows because a cursor page has no total (same as notifications).
- **Row anatomy (spec §5 AuditTimeline).** Action badge (upper-case verb, spec §1.3 tones: created / provisioned /
  opened → success, status_changed / sent / approved → warning, archived / blocked / deleted → danger, the rest →
  info), record type, record label linked to its page (`TC-000123` → case, `TC-000123 V2` → builder, customer and
  staff by id), the stored `summary`, the actor (linked to the staff page; "System" for intake rows) and a
  "Show changes" field grid of the stored `before` / `after`. Nothing is re-derived from today's rows.
- **Shared helpers.** `ui/booking/audit.ts` holds the tone / label / entity-link / before-after helpers. The staff
  detail Activity tab now uses the same tone map (it had its own, which coloured updates neutral and sent / approved
  green); its label text is unchanged.
- **`docs/ui-spec.md`.** The S236 consolidated spec is copied into the repo because AA-683's output is defined as
  this file. Changes vs the archived copy: a status / provenance header, the stale migration keys (wave 2 starts at
  bk-007 = AA-810 approvals in a separate `policy_approvals` table, bk-008 = suppliers + contracts; wave 3 keys are
  numbered when built), the module-spec paths (now under AA-Ecosys `docs/audits/2026-10-14-S236-design-review/`),
  the `/audit-log` route marked shipped, and one "as built" note for wave 1 (Vercel project name, Q11 `source_id`
  not in bk-005, dashboard tiles, card fee row).

- No server-side CSV export (`?format=csv` is a spec §6.3 endpoint that does not exist). "Export CSV" downloads the

## S239 table width fix (/pricing/rules, /proposals)

Folded into AA-683 by the 15/10 comment (S237 UI verify defect #2): at 1440 px the `/pricing/rules` table rendered
1207 px wide in a 1084 px wrapper, Note got 82 px and the seed note wrapped one word per line (rows 164 px); the
Actions column was empty when nothing was pending; `/proposals` used the same `tableMinWidth={1100}`.

### Decisions

- **Measured before fixing** (lesson "Tràn ngang: đo phần tử gây tràn rồi mới sửa"): a local `next dev` against a
  fixture mock of the Booking API (scratch only, not committed) reproduced the exact numbers of the comment (table
  1207 / wrapper 1084 / Note 82 / 164 px rows) and `/proposals` at 1447 px (the nowrap `truncate` title set the
  Proposal column to 613 px). The column widths are set by the nowrap kit headers, so lowering `tableMinWidth` alone
  could not make either table fit.
- **`tableMinWidth` removed** on both pricing tables and on `/proposals`. Below the tables' min-content width the kit
  wrapper (`overflow: auto`) still scrolls inside the card, which is the kit's documented behaviour (AA-601).
- **Pricing rules**: "Target margin" + "Floor margin" become one column "Target / floor" (`30% / 20%`, sorts by
  target). The Approve action moves under the status pill of a pending row (or "Needs a second person" / "Waiting"),
  so there is no Actions column at all; same for FX rates. Note is the flexible column: `md:line-clamp-2` and
  `md:min-w-[130px]` with the full text in a `title` tooltip; phone cards (< 768 px) show the full note.
- **Pending pill label "Pending"** (was "Pending approval", ~140 px, the widest cell once Approve moved in). The help
  tooltip still says "Pending approval: waiting for a second person…"; the maker-checker banner says *Pending*.
- **Proposals**: Version (V{n}) leads the proposal title and Dates (`3 Dec 2026 · 13 days`) sits under the first leg
  in the Trip cell; both cells are flexible (`FlexCell`, min 200 / 160 px on desktop) with one clamped line per row and
  the full text in the tooltip.
- **Clamp, not `truncate`**: a `truncate` (nowrap) line's min-content is the whole text, so it sets the column width
  in an auto-layout table. A `line-clamp-1` line can wrap, so its min-content is one word and its max-content (the
  full text) still lets the auto layout hand the spare width to that column. Clamping is `md:`-only, which matches the
  kit DataTable's phone card cut (767 px).
- **No kit change**: `ui/DataTable.tsx` stays byte-comparable with CIS; everything is in the two page files.

### Changed vs the brief

- The comment asked to "collapse or hide Actions when no row is pending"; Actions is gone in every case (Approve is in
  the Status cell), because with a pending row the extra column would push the table over 1084 px again.
- `/proposals` loses its separate Version and Dates columns (their data is in the Proposal and Trip cells). ui-spec
  §4.11 carries an "as built" note.

### Tradeoffs

- At 1440 the rules table with a pending row fits with ~2 px to spare (1082 / 1084 at the narrowest content); with
  the sidebar collapsed there is more room. Between 768 and ~1360 px the rules and proposals tables scroll inside
  their card (kit behaviour), the page itself never scrolls sideways (`scrollWidth == innerWidth` at 1024 / 1280 /
  1440 / 390, light and dark).
- Native `title` tooltips (no kit tooltip exists) are mouse-only; phone cards show the full text instead.
