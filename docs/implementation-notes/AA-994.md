# AA-994 — no internal issue IDs in user-visible text (rule R2)

## Decisions
- Guards parse the source instead of grepping it, so comments (and Python docstrings) may keep issue IDs:
  - frontend: `frontend/ui/booking/noIssueIds.test.mjs` (TypeScript compiler API over `app/`, `ui/`, `lib/`,
    `proxy.ts`; string literals, template parts, JSX text; import specifiers skipped). Runs in `npm run test:unit`.
  - backend: `backend/tests/unit/test_no_issue_ids.py` (`ast` over `app/`; every string constant except docstrings).
    Error details, OpenAPI descriptions and CLI help all reach a reader outside the code.
- The vendored CIS copy `app/auth/identity_verifier.py` is skipped by the backend guard (never edited here).

## Changed
- `PricePanel.tsx` 404 message: dropped "(bk-004, AA-810)"; the reference moved to a comment.
- `GET /booking/catalog/trip-plans` `orphaned` query description: dropped "AA-986:" (and in `docs/api/openapi.json`).
- `leg_keys` CLI help: dropped "(AA-830)".

## Tradeoffs
- Any string literal counts, even ones never rendered (log keys, CLI help). Simpler and stricter than deciding which
  strings reach the screen; the cost is moving a reference into a comment when it trips.

## Should know
- The regex is case sensitive (`\bAA-\d+\b`); migration keys like `bk-004` are not checked.
- Review (S255): the frontend guard also checks files served byte for byte (`public/`, non-code files under `app/`:
  svg, txt, json, xml, webmanifest, html), comments included, since those reach the browser unchanged.
- Not a leak: `booking.settings.description` seed rows carry issue IDs, but the Settings page shows its own help text
  (not the stored description), and `GET /booking/settings` is read by the staff app only.
