# AA-993 — slice V2: Booking post-deploy verify workflow

Design: AA-Ecosys root `docs/audits/2026-10-26-S252-aa993-delivery-pipeline/design.md` (ADR 0016 draft, D3; slice
plan Phase A → V2) and the critic notes next to it (points 12, 13, 20). Same shape as the AA-CIS-App V1 slice
(`post-deploy-verify.yml`, `.github/scripts/post_deploy_verify.sh`, `.github/verify/cis.rows`, a `result` job).

## Decisions

- **One script for Booking and Partner.** `.github/scripts/post_deploy_verify.sh <app>` is byte-identical in
  AA-Booking (`booking`) and AA-Partner (`crm`); the app argument picks `.github/verify/<app>.rows` and the summary
  title. Everything app-specific (paths, schema prefix, service name) lives in the rows file and the workflow. The CIS
  script stays separate (it also checks the worker service and the job-runner worker rows). The root canonical copy +
  byte check (design D3, `tools/verify/`) is not part of this slice.
- **Concurrency** as in V1: dispatched runs share the job-level group `post-deploy-verify-booking`; the call from
  Deploy Dev gets `post-deploy-verify-booking-deploy-<run id>-<attempt>` (input `from_deploy`, `workflow_call` only),
  so a dispatch can never cancel the pending verify of a Deploy Dev run. Neither group is `deploy-dev`.
- **Required schema comes from the deployed commit**: the newest key of `REQUIRED_SCHEMA_VERSIONS` in
  `backend/app/db.py` at `expected_sha` (a one-line `required_schema()` function in the workflow; a unit test runs it
  against the real `db.py` and compares with an AST read). The version comes from that commit's
  `.release-please-manifest.json`.
- **Expected image** = `<registry>/<ECR_REPOSITORY>:<sha>`, the exact string the build pushes. The registry comes
  from `aws-actions/amazon-ecr-login` in the verify job (the same output the build uses), so no account ID is written
  anywhere; the summary prints the tag only.
- **Rows format** `name|auth|METHOD path|expected HTTP|jq assertion`, the CIS V1 format. Booking has no admin secret
  and its one machine route (`/booking/ops/deploy-gate`) takes an OIDC token minted for `deploy-dev.yml` only, so
  `auth` must be `public` here (any other value is a red row).
- **No secrets.** The verify reads the same `dev` environment variables as Deploy Dev (`AWS_ROLE_ARN`, `AWS_REGION`,
  `ECR_REPOSITORY`, `ECS_CLUSTER`, `ECS_SERVICE`, `BOOKING_API_BASE_URL`) and assumes the deploy role (only
  `ecs:DescribeServices`, `ecs:DescribeTaskDefinition`, `ecr:GetAuthorizationToken` are used; all already granted).
  No Terraform/IAM change.

## Changed (vs. the brief and the design)

- **`config` fails instead of skipping.** It used to output `enabled=false` when `AWS_ROLE_ARN` is unset, which
  skipped every job and left the run green. Now it exits 1 with an `::error::`; `preflight`/`deploy` lose their
  `if:` (a failed `config` skips them), and `result` is red. This holds on every event, not only `push`.
- **Desired count 0 is red** (Q6: no automatic scale-up). The old smoke exited 0 with a warning at desired 0
  (`deploy-dev.yml` ~:205-208). The verify reports "desired count 0 (scaling Dev up is a separate approved step)".
  Consequence: while the service is scaled to 0, every Deploy Dev run is red. That is intended.
- **A missing base URL is red** (it skipped green before).
- **Schema check is `>=`, not `==`**: `/booking/health/ready` returns 200 only when every key the running code
  needs is registered; the row also requires `schema_version` = `bk-NNN` and its number >= the newest key of the
  deployed commit. The DB is often ahead of the code (MIG-4 applies migrations first), so an equality would go red
  on a healthy deploy. Readiness does not expose `git_sha` or the required key on 200, so the sha proof is `/health`.
- **ECS rollout checks are new**: service ACTIVE, running = desired, exactly one deployment, PRIMARY
  `rolloutState == COMPLETED` (the service has the deployment circuit breaker, so a rollback shows `FAILED`).
- The D1 "released on shutdown" count is not printed: the endpoint does not exist yet (slice G1).

## Tradeoffs

- One verify job (one OIDC sign-in, one summary table) instead of separate ECS / HTTP jobs.
- PATH-stub tests (fake `curl` and `aws` reading fixture JSON): the script under test is exactly what CI runs.
- The workflow structure is tested as text (the repo has no YAML parser in its test deps); the `config` and
  `result` shell bodies are extracted and executed with the inputs GitHub would pass.
- 3 tries, 10 s apart per check (`VERIFY_TRIES`, `VERIFY_RETRY_DELAY`) after an initial 10 s: a real failure costs
  ~30 s, a slow first request after the roll does not turn the deploy red.
- `result` is red for any non-`success` need on every event (the design asks this for `push`); no job in Deploy Dev
  is conditional any more, so a skip always means something did not run.

## Should know

- Read the **Deploy Dev result** job: `verify` is skipped when `deploy` fails, and GitHub shows a skipped job grey.
- `test_release_version.py` asserted the version check inside `deploy-dev.yml`; it now reads the verify workflow and
  `booking.rows`.
- Pushes that change only the verify files (`post-deploy-verify.yml`, the script, `booking.rows`) do not trigger
  Deploy Dev (push paths unchanged); dispatch `Post-deploy verify` to exercise them. This PR changes `deploy-dev.yml`,
  so its merge runs a full Deploy Dev + verify.
- Review fixes (public logs): AWS error text in a row is scrubbed (`arn:aws…` -> `<arn>`, 12-digit numbers ->
  `<acct>`); an invalid `expected_sha` is never echoed (script, workflow, summary print `invalid`); the verify's
  `configure-aws-credentials` sets `mask-aws-account-id: true`; the deploy job prints task definitions as
  `family:revision` only. Tests: a describe-services error carrying an ARN/account stays out of stdout and the
  summary; `EXPECTED_SHA=not-a-sha-SENTINEL` is red and `SENTINEL` is printed nowhere.
- actionlint 1.7.12 and shellcheck (`-S warning`) pass on the new/changed workflow files and the script.
- Live proof (orchestrator): (1) the push-triggered Deploy Dev after merge shows `Post-deploy verify` green with the
  table (ecs-rollout, ecs-image, health, health-ready) and `Deploy Dev result` green; (2) a `Post-deploy verify`
  dispatch with `expected_sha=<previous main sha>` goes red on `health` and `ecs-image`; (3) the dispatch does not
  cancel or replace a pending Deploy Dev run.

## Slice V5: public smoke of the staff admin after each production deploy

Branch `ci/aa-993-admin-public-smoke`.

### Decisions

- **Target = the public production custom domain `booking.lumiguides.it.com`** (workflow env `PRODUCTION_HOST`), not
  the per-deployment URL. The deployment URL sits behind Vercel Deployment Protection; the custom domain is what
  staff open, it is public, and `vercel deploy --prod` points it at the new deployment. No bypass secret is needed,
  so the smoke job uses no secret at all.
- **Expected header values come from `next.config.ts`**: the spec imports the config and calls `headers()`
  (`VERCEL_ENV` unset, so the production set). Every configured header must come back with the same value. A pinned
  list of the six AA-879 headers is also checked against the config, so dropping one from `next.config.ts` fails
  the smoke too, not only a deployment that loses one. `X-Powered-By` must be absent.
- **Render check includes "Sign in with company email"**: on the production host the button only appears when the
  production build has the `booking-staff` client secret (`lib/cognito.ts`). Without it staff would fall back to the
  legacy form, which is a broken production for AA-680.
- **"No failed same-origin request"** = no `requestfailed` and no response >= 400 whose origin is the admin host,
  while `/login` loads to `networkidle`. Cross-origin (the CIS link) is ignored.
- **`webServer` is off when `SMOKE_BASE_URL` is set**. The config's `webServer` (stub API + `next start`) is
  config-wide in Playwright; starting it would need `next build`. The npm script `test:smoke-public` defaults
  `SMOKE_BASE_URL` to the production host.
- **Retries 2 on CI for this project only** (`layout-mock` keeps 0): a live host can blip, and the custom domain may
  take a few seconds to move to the new deployment.
- **Job `result` gates production only.** Production = `push` to main, or `workflow_dispatch` with
  `target=production` and no `alias_only_url`. Then deploy and smoke must both be `success`; skipped, failed,
  cancelled or missing is red. Previews, alias-only dispatches and no-op label runs exit 0 in `result` (the deploy
  job's own status stands), so preview behaviour is unchanged. The production target is derived from the event,
  not from deploy outputs, because a deploy that fails in `plan` sets no outputs.

### Changed

- `.github/workflows/vercel-deploy.yml`: env `PRODUCTION_HOST`; job `smoke` (needs deploy; production + deploy
  success only; checks out the deployed SHA; `npm ci`, Chromium, `npm run test:smoke-public`; uploads
  `frontend/e2e/smoke-public/results/` as artifact `booking-admin-smoke-public`, always); job `result`.
- `frontend/playwright.config.ts`: project `smoke-public`; `webServer` only without `SMOKE_BASE_URL`.
- `frontend/e2e/smoke-public/login.spec.ts`: the smoke. `frontend/package.json`: script `test:smoke-public`.
- `frontend/.gitignore`: `/e2e/smoke-public/results/`.
- `backend/tests/unit/test_vercel_deploy_smoke.py`: pins the wiring and runs the `result` step with simulated
  `needs` JSON (26 cases).
- `CONTEXT.md`, `README.md`, `frontend/e2e/SIGNED-IN-SMOKE.md`: one paragraph each.

### Tradeoffs

- The smoke does not prove the production host serves **this** commit: the admin has no version endpoint. The
  existing "Check the security headers" step still reads the exact deployment URL. A follow-up could add a public
  `/api/version` (git SHA) to the admin and compare it, like V4 does for TripPlanner.
- `npm ci` + Chromium on every production deploy costs about 1-2 min of runner time; production deploys are rare
  (only pushes to main that touch `frontend/**`).
- The `result` step is inline (like V2's `deploy-dev.yml`), not a script file; the test extracts it from the YAML.

### Should know

## Slice H1: pre-push hooks (local only) — 27/10/2026

Design: root `docs/audits/2026-10-26-S252-aa993-delivery-pipeline/design.md`, D5 and Phase B → H1. Files:
`scripts/pre-push.sh`, `scripts/install-hooks.sh`, `.githooks/pre-push`, a paragraph in `README.md` (Local
development). No workflow file changes (H2 makes CI call the script).

### Decisions

- **Commands come from the current workflows**, each failure printed with its CI job/step and the exact command:
  `ci.yml` Lint (`ruff check .`, `ruff format --check .`; the ruff version must equal the `requirements-dev.txt`
  pin, 0.16.9), Security Audit (`check_resource_ids.py` always; `pip-audit==2.10.1` on both requirement files when
  one of them changed), Unit Tests, Docker Build Check's `check_trivyignore.py` (when `.trivyignore` changed),
  Frontend Build's `npm run lint` + `npm run typecheck` (when `frontend/` changed; never `npm run build`), and
  `docs-lint.yml` (front-matter, ADR index, single-line AWS CLI, lychee offline; the tools' unit tests when
  `tools/docs/` changed).
- **Fast mode** (default) plans from `git -c core.quotePath=false diff --name-only -z origin/main...HEAD`
  (`AA_PREPUSH_BASE` overrides; no base ref, or a diff git cannot compute such as no merge base → every check).
  Unit tests: the changed test files, `tests/unit/test_<stem>.py` / `test_<stem>_*.py` of a changed module, the
  tests that import it, the tests whose text names a changed file (by basename, `__init__.py` excepted: workflows,
  `.github/scripts`, `.github/verify`, release config, `backend/Dockerfile`, scripts loaded with
  `spec_from_file_location`), `test_openapi_export.py` when any `backend/app/*` file changed (a stale
  `docs/api/openapi.json` fails CI Unit), the migration guard when `migrations/` changed, plus the unit test files
  in pytest's `lastfailed` cache that still exist. One serial `ENVIRONMENT=test` run, no coverage. A change to
  `requirements*.txt`, `pyproject.toml`, `tests/conftest.py` or `tests/unit/conftest.py` / `fakes.py` does **not**
  run the whole suite in fast mode (~3 min in CI, over the 90 s target): it runs the targeted selection and prints a
  warning naming `AA_PREPUSH=full`.
- A change to the hook files plans `hook-self-test` (`bash scripts/pre-push.sh --self-test`, 0.1 s). A diff that
  deletes or renames a file plans `docs-links` even without a Markdown change (a moved link target breaks lychee).
- **`--full` / `AA_PREPUSH=full`** runs every local check, the unit step being the exact CI command
  (`ENVIRONMENT=test COVERAGE_CORE=sysmon pytest tests/unit -n 4 --tb=short --cov=app --cov-report=term-missing
  --cov-fail-under=90`). **`--ci`** (reserved for H2) is `--full` that never looks at the diff and treats a missing
  lychee as a failure (locally lychee is optional: a warning; CI checks links).
- **`--self-test`** runs the planner on 20 fixture diffs (plus the unit_all warning), the unit-test selection on a
  fixture tree (9 cases) and the diff reader on a scratch git repo (non-ASCII and spaced names, a failing diff,
  deletes/renames); no CI tool is invoked. `--plan` prints the checks a push would run.
- **docs-links** passes the tracked pages (`git ls-files -z '*.md' | xargs -0 -r lychee --config
  tools/docs/lychee.toml`) instead of `'./**/*.md'`, which locally also walks `frontend/node_modules` and
  `backend/.venv`. A missing lychee prints the install hint: lychee v0.24.2 (the default of lychee-action v2.9.0),
  a release binary or `cargo install lychee --version 0.24.2`.
- **Tool lookup:** `AA_PREPUSH_VENV`, then `backend/.venv`, then the main checkout's `backend/.venv` (found through
  `git rev-parse --git-common-dir`, so worktrees reuse it), then `python3`. Tools are called as `python -m ruff`,
  `-m pytest`, `-m pip_audit`, which survives a venv copied from another path (stale shebangs). A missing env, a
  wrong ruff version, a wrong pip-audit version (exact match on `2.10.1`), missing pytest-xdist / pytest-cov for
  `unit-full`, a Python without jsonschema + PyYAML for the front-matter check or the docs tools' tests, or a missing
  `frontend/node_modules` fails that check with the install command: the hook blocks rather than passing silently.
- `scripts/install-hooks.sh` prints the previous `core.hooksPath` when it was set to something else, and lists the
  non-`.sample` hooks in `<git-common-dir>/hooks` that stop running once `core.hooksPath` is set.
- Every check runs even after one fails (like docs-lint); the summary then lists each failure.

### Changed (vs. the design)

- Not run locally (CI only): Integration Tests (PostgreSQL), Docker Build Check / Trivy / SBOM, Vendored CIS copies
  and OpenAPI breaking (network, pinned binaries), gitleaks, PR title.
- The hook checks `HEAD` and the working tree, so it **refuses** (exit 1) a push whose pushed commit is not `HEAD`
  (for example pushing another branch than the one checked out): `pre-push: checks run on HEAD (<sha>), not the
  pushed <ref>; check out that branch and push again, or git push --no-verify`. Chosen over a warning because a
  warning would let an unchecked commit through with a green hook. An annotated tag is compared through its commit;
  a delete-only push is skipped. It prints a note when the tree is dirty (the push sends commits, the checks read
  files).
- The aa-ship note (install, bypass) belongs to the root repo and is not in this change.

### Tradeoffs

- Name + import matching can miss a test that reaches a module indirectly; `--full` and CI still run everything.
  Over-selecting is cheap (154 tests for a change to `app/db.py`).

- Install once per clone: `scripts/install-hooks.sh`. Undo: `git config --unset core.hooksPath`. Skip once: push
  with `--no-verify`.
- Checks (27/10/2026, after the review fixes): shellcheck 0.11.0 `-S warning` clean and `bash -n` on the three
  files; `--self-test` 33/33 in 0.1 s. `--plan` on a bad base (`HEAD^{tree}`) prints `cannot diff`, switches to
  full mode. The hook fed a push line for another branch exits 1 with the message above; a delete-only line exits 0.
- Not for H1, noted for H2: `--ci` also plans `fe-lint` / `fe-typecheck` (needs `frontend/node_modules`) and the docs
  checks (needs lychee and the tools/docs requirements). The CI Lint and Unit jobs have neither, so H2 needs

## Slice G4 proof kind + G5: `bk_noop_sleep` and the deploy gate — 28/10/2026

Design: root `docs/audits/2026-10-26-S252-aa993-delivery-pipeline/design.md` (ADR 0016 draft D1.3-D1.4, Phase C → G4,
G5; Q3, Q4) and critic points 15, 21, 22. G4 part 1 (uvicorn `--timeout-graceful-shutdown 5`, #112) is merged.

### Decisions

- **`bk_noop_sleep`** (`app/jobs/noop_sleep.py`): the port of CIS `noop_sleep`. Registered only when `JOB_TEST_KINDS`
  is truthy, read into `Settings.job_test_kinds` (1/true/yes/on; any other value is off, never a start-up error, as
  in CIS). Payload `seconds` 1..3600 (bool / string / out of range → `PermanentError`). Sleeps in 5 s steps and
  writes `progress.slept_seconds` + `total_seconds` after each step (the worker heartbeats the lease itself), resumes
  from `progress.slept_seconds` after a release. Shutdown cancellation is never caught (the worker releases the row).
  A cancel request (`cancel_requested`, SQL only: Booking has no cancel route) is read back by each progress write;
  the handler then ends its own row `cancelled` (guarded by `status = 'running' AND cancel_requested`), since the
  Booking worker has no cancel path for a running job. `EXPECTED_SECONDS` 3660; in `DEPLOY_GATE_EXEMPT` (mirror of
  the CIS `deploy_gate_exempt`) and in a new `TEST_KINDS` set (the lifespan test expects it only with the flag).
- **`DEPLOY_BLOCKING_KINDS`** = the two retention kinds (design G4 bullet 3, Q3), equal to `retention.NOT_RELEASED`
  (a unit test pins it). `bk_notify_email` is an accepted duplicate (critic 22: at-least-once staff mail).
- **Gate** (`app/routers/ops.py`): `safe_to_deploy = no RUNNING row and no due QUEUED row of DEPLOY_BLOCKING_KINDS`
  (`queue.blocking_count`). New fields `blocking_kinds`, `blocking_running`, `blocking_due`, `blocked_by`; `active` / `by_status` / `by_kind` / `exempt_kinds`
  unchanged (information; no field removed, so the AA-899 breaking-change check stays green). No CIS wave read (Q4).
- **Preflight script**: messages only. Safe → says how many queued/running rows the new task re-claims; blocked → names
  `blocked_by` plus the by-kind counts; an older API with no `blocked_by` still blocks with a generic reason. The
  task-count checks (no task / a pending task) are unchanged: without a running task the gate cannot answer.

- **Due queued rows of a blocking kind block too** (review follow-up; the first commit counted RUNNING only, as the
  design words it). The preflight runs before the image build + push, and the old task keeps claiming until its
  SIGTERM minutes later: a due queued `bk_retention_job` (a manual live run with an approved `max_rows`) that passed
  the gate would be claimed by the old task and failed on shutdown (`NOT_RELEASED`), losing the approved run. So a
  queued row due within `kinds.DEPLOY_BLOCKING_HORIZON_SECONDS` = 900 s (covers build + push + roll) counts as
  `blocking_due`; one due later waits for whichever task is live. The retention kinds are enqueued due at once (daily
  schedule, manual run) with `MAX_ATTEMPTS` 1, so a row due later than that is rare. Same rule in CIS and Partner.
- **`JOB_TEST_KINDS` stays on the Dev task** (review follow-up; settles the earlier "remove after the proof"): the
  kind is test-only, deploy-gate exempt and never blocking, the CIS api/worker keep the same env on Dev since G1, and a
  later drain proof (G4b) can reuse it without a Terraform round trip. Production gets `"0"` (AA-CIS-Infra
  `booking.tf`).

### Changed (vs. the design)

- **Order.** The design says the gate relaxation ships "only after G1–G4 are live". Here the relaxed gate ships in
  the same PR as `bk_noop_sleep`, which the G4 drain proof needs, so the gate stops blocking ordinary running jobs
  before the Booking drain + release is proven live. Kept as one PR (the old gate would let the proof deploy through
  anyway, `bk_noop_sleep` being exempt), on one condition for the orchestrator: run the G4 drain proof right after the
  deploy that carries this PR and before relying on the new gate for any other deploy; if the proof fails, revert
  `app/routers/ops.py` to the old count until it passes. The PR body says so.
- The design put `DEPLOY_BLOCKING_KINDS` in G4; it ships here with the gate that reads it (G4 part 1 shipped only the
  uvicorn flag).
- `docs/api/openapi.json` regenerated (four new `DeployGate` fields).

### Tradeoffs

- While `bk_noop_sleep` sleeps, the serial worker runs no other Booking job (pull, notify) — acceptable for a
  one-off Dev proof of ≤ 5 min.
- Due-queued horizon 15 min, not "until the old task is gone": a retention row due later than that but before a slow
  roll finishes could still be claimed by the old task. Accepted (enqueued due at once, no retry backoff).
- A handler that ends its own row makes the worker log "succeeded" (with `cancelled: true` in the result) because
  `complete` then matches no row; adding a cancel path to the worker for one test kind was not worth it.

### Should know

- Tests: `tests/unit/test_noop_sleep.py` (steps + progress, resume, cancel request, lost row, shutdown cancel
  propagates, bad payloads), `test_settings.py` (flag values), `test_lifespan_worker.py` (registered only with the
  flag), `test_deploy_gate.py` (`blocking_count`; queued/running ordinary jobs → safe; running retention → unsafe;
  due queued retention → unsafe; retention queued past the horizon → safe; blocking set = `NOT_RELEASED`),
