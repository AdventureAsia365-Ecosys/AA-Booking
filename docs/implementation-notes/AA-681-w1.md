# AA-681 / AA-680 / AA-810 Wave 1: staff admin backend (bk-005)

Scope (S236 lane bk-681, UI spec `ui-spec.md` §4, §6.1–6.2, §8 Wave 1, §9, §10): fix the integration defects D2,
D3 and D4, and add the Wave 1 endpoints the staff admin pages need. Schema additions are in a new migration
`005_w1_extras.sql`. `003` is already copied to AA-CIS-Infra and is unchanged; `004` belongs to the pricing branch
(AA-810), and `005` references none of its objects.

## Decisions

- **005 is independent of 004.** It applies before or after `bk-004` (checked locally in both orders). It uses
  per-table grants, not `GRANT ... ON ALL TABLES IN SCHEMA booking`. After `bk-004`, that blanket grant would
  re-open UPDATE/DELETE on the append-only `pricing_rules` / `fx_rates`. Readiness needs every entry of
  `REQUIRED_SCHEMA_VERSIONS` (`bk-001`, `bk-002`, `bk-003`, `bk-005`; the pricing branch adds `bk-004`).
- **D2: items keep their ids.** `PUT …/items` takes an optional `id` per item. The service:
  1. checks that every id belongs to this version and that no id repeats;
  2. deletes only the items that were left out;
  3. moves the kept items to `position + 1000`, so the bk-003 unique `(version, position)` does not collide
     mid-save (the constraint is not deferrable and `ALTER CONSTRAINT` cannot change a unique constraint);
  4. updates the kept items in list order and inserts the new ones.

  Rows that reference an item (bk-004 `version_item_costs`, `ON DELETE CASCADE`) therefore survive a save. The
  integration test uses a stand-in table with the same FK.
- **D3: transitions are seed rows in bk-005.** The new edges are `proposal_sent → confirmed` and
  `cancelled → new_inquiry`.
  - `confirmed` is reachable only through `POST …/versions/{n}/approve`. A bare status move returns 409
    `approve_version_first`, so the record always says which version was approved (`approved_by`,
    `approval_note`, history note `V{n} approved`).
  - Reopen needs a reason, the same as cancel (`reason_required(from, to)`).
- **D4: directory.** `GET /booking/staff/directory?role=` returns `{cis_user_id, name, role}` for active staff
  only (no e-mail). Permission `staff.directory` = admin, sales, contracting.
- **Send** (`POST …/versions/{n}/send`):
  - allowed from `discovery`, `building` or `proposal_sent`. From `discovery` it walks
    `discovery → building → proposal_sent`, one history row per edge, each with the note `V{n} sent`;
  - requires at least one item, plus `total_price` and `currency` (`price_missing` otherwise);
  - `to` is optional and must equal the customer's e-mail (Q14);
  - `valid_until` defaults to today + `settings.quote_validity_days` (14) and must fall 7–30 days from today;
  - writes a **customer** notification row `proposal.sent` (subject, message and data) and an audit row with the
    subject and message. No e-mail is sent, and the response says `email_sent: false`.
- **Sent = locked in the database** (bk-005 triggers). Once a version is sent, its commercial fields
  (title, notes, total, currency, validity, channel, FX, deleted_at, number) and its items cannot change; only the
  approval columns can. The API also returns 409 `version_sent`. The bk-003 approval lock is unchanged.
- **Approve** requires a sent version that is not superseded, on a case in `proposal_sent`. It writes a staff
  notification `proposal.approved` to the shared queue.
- **Version badge** is derived in SQL (`app/trip_cases/sql.py`):
  - `approved`;
  - `superseded`: a later version was sent, or another version is approved;
  - `sent`;
  - `draft`.
- **Delete version** is a soft delete (`deleted_at`) of an unsent, unapproved draft. Version numbers are never
  reused.
- **Case create** (`POST /booking/trip-cases`):
  - fields: `customer_id` xor `new_customer`, pax or the adults / children split, currency (default USD),
    `trip_style` (free text until Q16), `countries` (ISO-2), `assignee`, `initial_status`
    (`new_inquiry` | `discovery`);
  - the source is `manual`;
  - a sales creator becomes the sales owner by default;
  - a blocked customer cannot get a new case (409).
- **Manual leads** follow the intake rule (O6). They are created `verified=false`, `source='manual'` and never
  merged. If the e-mail or phone matches a live customer, the lead gets `needs_merge_review` and
  `merge_candidate_id`. E-mails are stored lowercase.
- **Customer status** comes from the view `booking.v_customer_summary`:
  - `active`: a live case in an open status past `new_inquiry`;
  - `past`: no active case, at least one `completed` case;
  - `lead`: anything else.

  Blocked is a chip and a filter (`status=blocked`), not a status value. UI labels: New Lead / Active /
  Past Client.
- **Customer code** `CUS-000123` comes from `booking.customer_code_seq`. Existing rows are back-filled by the
  volatile column default.
- **Customer edit**: the e-mail of a verified customer is locked (409 `email_locked`). Block / unblock is admin only
  (403 from the service). Archive (`DELETE`) is admin only and returns 409 `customer_has_cases` when any case is
  past `new_inquiry`. Otherwise it cancels the open `new_inquiry` cases with the reason `customer archived` and sets
  `deleted_at`.
- **Notifications.**
  - Staff see the shared queue (`recipient_ref IS NULL`) plus rows addressed to them (new column
    `recipient_ref` = CIS user id). `recipient_id` stays a UUID, but CIS ids are text.
  - Read state is per person in `booking.notification_reads`. bk-002 `read_at` is not used for staff rows.
  - New rows are written for `trip_case.assigned` (to the assignee, unless they assigned themself),
    `trip_case.status_changed` (to the open sales owner, unless they made the change) and `proposal.approved`
    (queue).
  - Marking read is audited once per call (`notification.read`).
- **Preferences** live in `staff_users.preferences` jsonb as `{notify: {type: bool}}`. Only known staff types
  are accepted, and the default is on. They are stored only: nothing filters on them yet.
- **Settings** are rows in `booking.settings` (`deposit_pct` 30, `quote_validity_days` 14), read-only for role
  `booking`. A change goes through a reviewed migration until a settings admin exists.
- **Countries** come from `booking.countries`, an ISO-2 code plus English short name for 16 AA destinations. It is
  reference data, not content: country text and photos stay in CIS (O7, Q18). Cases link to it through
  `trip_case_countries`.
- **Status history order.** `trip_case_status_history.seq` is an identity column, because rows written in one
  transaction share `changed_at = now()`. Case detail orders by `(changed_at, seq)`.
- **Feeds use keyset paging.** Audit log, notifications and case activity page with an opaque cursor
  `"<iso ts>|<uuid>"` (`next_before`) over `(created_at, id)`. A timestamp alone would skip rows that share
  `now()`.
- **Audit rows** now carry `entity_label` (e.g. `TC-000001 V2`) and a short `summary`, written at write time.
  `GET /booking/audit-logs` is admin only (`audit.read`).
- **Trip title.** `trip_title` / `leg_titles` / `duration_days` are derived from the inquiry snapshot day names
  (the same rule as V1 prefill). The CIS catalog title (`catalog.v_tour`) is not read yet (CIS migration 225
  grant, Q11).

## Changed vs the issue / spec

- The spec puts bk-005 work in "bk-005". The file is `005_w1_extras.sql` (key `bk-005`), as briefed.
- The notification type for new inquiries stays `trip_case.new_inquiry`, which is what bk-002 intake writes. The
  spec vocabulary says `inquiry.new` (open question).
- `GET /booking/trip-cases/summary` `mom_delta` compares cases **created** this calendar month (UTC) with last
  month. The open count has no history to diff, so it is not compared.
- `proposals_awaiting` = cases in `proposal_sent`.
- Not built here: `POST …/versions/{n}/price`, cost lines in the PUT body (`costs[]`), and the FX lock values.
  They depend on bk-004 / the pricing engine on the AA-810 branch. The FX columns exist and stay NULL. Also not
  built: `GET /booking/catalog/tours*` and the `catalog.v_tour` join, which wait on the CIS migration 225 grant.
- The migration guard's "contiguous numbers" test now allows the gap `004`, listed in
  `RESERVED_ON_OTHER_BRANCHES`. Remove the entry when AA-810 merges.

## Tradeoffs

- Hard-coded validity bounds (7–30 days) plus a settings row for the default, instead of a settings admin UI.
- `send` requires a price. Without the pricing branch, a W1 smoke test needs bk-004 merged first (or a price set
  by hand on Dev). A proposal with no price was judged worse than a blocked send.
- The activity feed orders `(at, id)`. Two history rows from the same transaction can appear in either order in
  the feed (detail `status_history` uses `seq`). Kept, so the feed has one simple cursor.

## Review fixes (S236 review of the W1 branches)

- **Finding 2 (price copied to Vn).** `create_version` no longer copies `total_price`; V2+ start unpriced (currency
  and channel are still copied). `replace_items` clears `total_price` when the saved list differs from the stored
  one (ids, order or any field); saving the identical list keeps it. The audit row says `price cleared`.
  Integration test `test_new_version_and_item_changes_clear_the_price`.
- **Finding 4 (readiness with a gap).** Readiness now lists `booking.v_schema_versions` and fails while any entry of
  `REQUIRED_SCHEMA_VERSIONS` is missing (body adds `missing_schema_versions`). Only checking `max(version)` was green
  with bk-005 applied and bk-004 missing.
- **Finding 6 (hard delete of a sent version).** bk-005 revokes DELETE/TRUNCATE on `trip_case_versions` from role
  `booking` (the API only soft-deletes drafts) and the sent-lock trigger now also fires `BEFORE DELETE`, so a sent
  version cannot be removed by any role (the item lock cannot see the version during a cascade). bk-005 is not on Dev
  yet (no AA-CIS-Infra copy), so the file was edited in place instead of adding bk-006.
- **Finding 13 (confirmed is a dead end).** bk-005 seeds `confirmed → cancelled` (reason required like every cancel)
  until AA-682 adds the post-sale chain.
