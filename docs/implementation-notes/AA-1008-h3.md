# AA-1008 H3 — the Visual check ready to be a required check; the post-deploy not-found fix (AA-Booking)

Lane `aa1008-h3-visual-merge-group` (S270). Companion PRs: AA-CIS-App (`visual.yml` + `kit-consumers.yml`) and
AA-Partner (`visual.yml`). The branch-protection step itself is the tech lead's (ADR 0011); this PR only makes the
check safe to require, and makes the post-deploy visual run green again.

## Decisions

- **Step-level skip, not a scope job.** `visual.yml` job `pr` gets a `Scope` step right after the checkout (with
  `working-directory: .`: the job's default is `frontend/`). It diffs the PR (`origin/<base_ref>...HEAD`) or the queue
  group (`merge_group.base_sha...HEAD`) and matches the old pull_request `paths:` list (`frontend/**`, the workflow
  itself). No match: `run=false`, "no frontend change" in the step summary, every later step skipped by
  `if: steps.scope.outputs.run == 'true'`, the job green. A separate scope job with a job-level `if`/`needs` would
  report "skipped", which GitHub counts as passed even when the scope job failed.
- **The required name stays**: `Visual (next start, mocked API + kit gallery)` (pinned by the TL script, verify-h3.sh
  and the new test).
- **Scope fails toward running**: an empty base or a failing `git diff` runs the full check with a warning, never a
  silent skip. `--no-renames` so a file moved out of `frontend/` still counts by its old name.
- **merge_group**: `Changed pages` diffs `$MERGE_BASE_SHA...HEAD` (`github.base_ref` is empty there); the PR comment
  stays pull_request-only; the `deployed` job says `github.event_name != 'merge_group'` explicitly (it was already
  excluded by `github.ref == 'refs/heads/main'`). Concurrency already fell back to `github.run_id` for merge_group
  (checked; a test pins it).
- **Post-deploy not-found (Vercel Deploy 42013253500, 4 x "Expected: 404")**: signed out, the deployed `proxy.ts`
  sends every path but `/login` to `/login?next=<path>` (307), and `page.goto` returns the LAST response, so 404 can
  never be the deployed answer. `pages.ts` gets an optional `deployed` expectation (final status + final path + why)
  and a pure `expectedOutcome(page, onHost)`; on a host the not-found page must land on `/login` with 200 (the spec
  now checks the final path as well, so changing only the status would not pass a wrong landing page). The mocked
  `next start` run sets a session cookie, so it still reaches the 404 page and keeps the 404 assertion. Chosen over
  excluding the page on a host: the redirect of a signed-out unknown path is itself worth checking after a deploy.
- `summary.mjs` reads the expected status / path from the report (written by the spec) instead of hardcoding 404 for
  not-found, so the deployed table does not show a false "HTTP 200".

## Tradeoffs

- Every PR now starts the job (checkout with full history + one diff, ~30 s) even without a frontend change.
- A frontend PR's queue group runs the full visual again (~3–6 min) on the combined commit.
