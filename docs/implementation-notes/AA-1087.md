# AA-1087 — Dev-only write-capable E2E staff identities (Booking half)

S278 system audit gap B2: no test identity could write on the staff side (the A10a E2E user is read-only, every POST is
403 including dry runs). The tech lead chose to build write identities before the synthetic pilot rehearsal. Root ADR
0006a A10e records the decision; the CIS half is A10b-3 (AA-CIS-App), the Cognito trigger and mailbox are AA-CIS-Infra.

## Decisions

- **Three new addresses, not a wider A10a.** A10a (`e2e-booking@`, `booking-admin`) has its codes in the CI-readable
  mailbox prefix `inbound/`; making it write-capable would hand a Booking admin write to every CI reader. The new
  identities' codes land in `inbound-admin/` (MFA admin role only), like A10b / A10c / A10d.
  - `e2e-booking-staff@` — `booking-sales`; writes: POST `/booking/supplier-bookings/{booking_id}/request`, `/confirm`.
    Sales holds `ops.write` and `b2b_desk.write` (an on-request B2B line's confirm needs both); contracting would also
    carry pricing and bill approval.
  - `e2e-booking-maker@` — `booking-finance`; writes: POST `/booking/agency-invoices/{ref}/payments`.
  - `e2e-booking-checker@` — `booking-finance`; writes: POST `/booking/agency-payments/{payment_id}/approve`, `/reject`.
  Both finance users hold the same role, so the allow-lists (not the role) make the maker never approve and the
  checker never record; the DB CHECK `agency_payment_maker_checker_chk` still refuses an approve by the recorder.
- **Synthetic = CIS's rule, read from the contract view.** `catalog.v_tenant_account_v1.is_synthetic` (CIS 401:
  `is_canary IS TRUE AND NOT is_pilot`, the A10b-1 rule). Booking has no synthetic mark of its own and must not read
  `shared.tenants`. Record -> agency: supplier booking -> trip case `party_tenant_id`; invoice `party_tenant_id`;
  payment -> invoice. A B2C case, a departure-owned supplier booking or an unknown id has no agency: refused.
- **One check point, before the route.** `app/auth/e2e_staff.py`, called from `current_staff` (the dependency of every
  staff route): environment, exact groups and the allow-list before any DB access; the synthetic check after the pool
  is open and before the staff row is synced or the route runs. The route template comes from `scope["route"].path`
  (Starlette sets it before dependencies run). No route was changed.
- **Environment from the process, exactly `dev`.** `Settings.environment` defaults to `dev` when unset, so the guard
  reads `os.environ["ENVIRONMENT"]` and requires exactly `dev` (CI's `test` and an unset value refuse).
- **Users are created by the Infra tool, not Terraform** (`tools/identity/crm_dev_identity.py e2e-booking-writers`),
  as A10a / A10c were: ADR 0006 section 3 keeps WORKFORCE users out of Terraform; Terraform holds the trigger map,
  its Dev flag and the mailbox recipients.

## Tradeoffs

- Reads are not limited to synthetic agencies: a `sales` / `finance` session reads what its role reads on Dev, the
  pilot agency included. Limiting every read route was out of scope; A10a already reads everything as admin from a
  more widely readable mailbox, so this adds no new reader of Dev data.
- The synthetic check is one SQL per allowed write (a fresh pool read, no cache): a flag cleared in CIS stops the
  identity at once.
- The smoke writes through the BFF from the signed-in page (`fetch`, same origin) instead of clicking through the
  admin UI: it proves the browser session and the server-side refusal without depending on page markup.

## Threat note (for the independent review)

- **Asset at risk:** Booking writes on Dev. **Who can get a session:** whoever reads a sign-in code under
  `inbound-admin/` (the MFA admin role, already full AWS admin) or controls mail for `e2e-mail.lumiguides.it.com`
  (A10's domain dependency: losing it removes every E2E address at once).
- **What a session can do:** reads of its role on Dev; at most these writes, and only on a synthetic agency's records:
  send / confirm a supplier booking, record an agency payment, approve / reject one. No retention run, no staff,
  pricing, B2B partner, billing config or customer write; no delete.
- **Bypass attempts covered by tests:** another identity's write (403 `e2e_read_only`), extra or other groups (403
  `e2e_scope`), look-alike or non-ASCII address (no match: an ordinary staff check then applies and the address is
  outside the staff domain, so the trigger never issues it a token), outside Dev (403 `e2e_not_allowed_here`, reads
  too), a real / pilot / NULL-canary agency, a B2C case, an unknown id, a non-UUID path value, a missing view column or
  a DB error (403 `e2e_synthetic_only`, fail closed).
- **Residual risks:** (1) someone with CIS admin on Dev can set `is_canary` on a real tenant and so widen the scope:
  the same trust as A10b-1 (CIS admin is already a higher privilege than these writes). (2) A record's agency can
  change between the check and the route (no lock): Booking never moves a supplier booking, invoice or payment to
  another agency, so the window has nothing to race. (3) The identities exist in the shared WORKFORCE pool on Dev
  only: the trigger map is consulted only while `E2E_DEV_ONLY_STAFF_ENABLED` is exactly `"true"`, which Terraform
  sets for dev only (precondition elsewhere).
- **Audit:** every allowed write is the unchanged route, so `booking.audit_logs` names the identity's staff key
  (`cog:<sub>`) as `actor_ref`; refusals are logged `booking_e2e_writer_refused identity=… reason=…`, allowed writes
  `booking_e2e_write_allowed`.
- **Removal (AA-1054, with the A10 family):** delete the three Cognito users, drop the trigger entries and the
  mailbox recipients (AA-CIS-Infra), drop `app/auth/e2e_staff.py` and its two calls, deactivate the three
  `booking.staff_users` rows; CIS 401's column may stay (a later `_v2` view drops it).
