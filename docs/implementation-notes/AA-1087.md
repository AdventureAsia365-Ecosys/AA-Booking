# AA-1087 — Dev-only write-capable E2E staff identities (Booking half)

S278 system audit gap B2: no test identity could write on the staff side (the A10a E2E user is read-only, every POST is
403 including dry runs). The tech lead chose to build write identities before the synthetic pilot rehearsal. Root ADR
0006a A10e records the decision; the CIS half is A10b-3 (AA-CIS-App), the Cognito trigger and mailbox are AA-CIS-Infra.

## Decisions

- **Three new addresses, not a wider A10a.** A10a (`e2e-booking@`, `booking-admin`) has its codes in the CI-readable
  mailbox prefix `inbound/`; making it write-capable would hand a Booking admin write to every CI reader. The new
  identities' codes land in `inbound-admin/` (MFA admin role only), like A10b / A10c / A10d.
  - `e2e-booking-staff@` — `booking-sales`; writes: POST `/booking/supplier-bookings/{booking_id}/request`, `/confirm`.
    Sales holds `ops.write` and `b2b_desk.write` (an on-request B2B line's confirm needs both); contracting would also
    carry pricing and bill approval.
  - `e2e-booking-maker@` — `booking-finance`; writes: POST `/booking/agency-invoices/{ref}/payments`.
  - `e2e-booking-checker@` — `booking-finance`; writes: POST `/booking/agency-payments/{payment_id}/approve`, `/reject`.
  Both finance users hold the same role, so the allow-lists (not the role) make the maker never approve and the
  checker never record; the DB CHECK `agency_payment_maker_checker_chk` still refuses an approve by the recorder.
- **Synthetic = CIS's rule, read from the contract view.** `catalog.v_tenant_account_v1.is_synthetic` (CIS 401:
  `is_canary IS TRUE AND NOT is_pilot`, the A10b-1 rule). Booking has no synthetic mark of its own and must not read
  `shared.tenants`. Record -> agency: supplier booking -> trip case `party_tenant_id`; invoice `party_tenant_id`;
  payment -> invoice. A B2C case, a departure-owned supplier booking or an unknown id has no agency: refused.
- **One check point, before the route.** `app/auth/e2e_staff.py`, called from `current_staff` (the dependency of every
  staff route): environment, exact groups and the allow-list before any DB access; the synthetic check after the pool
  is open and before the staff row is synced or the route runs. The route template comes from `scope["route"].path`
  (Starlette sets it before dependencies run). No route was changed.
- **Environment from the process, exactly `dev`.** `Settings.environment` defaults to `dev` when unset, so the guard
  reads `os.environ["ENVIRONMENT"]` and requires exactly `dev` (CI's `test` and an unset value refuse).
- **Users are created by the Infra tool, not Terraform** (`tools/identity/crm_dev_identity.py e2e-booking-writers`),
  as A10a / A10c were: ADR 0006 section 3 keeps WORKFORCE users out of Terraform; Terraform holds the trigger map,
  its Dev flag and the mailbox recipients.

## Changed

- `backend/app/auth/e2e_staff.py` (new), `backend/app/auth/staff.py` (two calls in `current_staff` + docstring).
- Tests: `backend/tests/unit/test_aa1087_e2e_writers.py` (real app, scripted pool), `backend/tests/integration/
  test_aa1087_e2e_writers.py` (the SQL on PostgreSQL as role `booking`, with and without CIS 401's column).
- `frontend/e2e/e2e-writers/writes.spec.ts` + Playwright project `e2e-writers` (agent-only; opt-in and dry-run
  switches; a unit test keeps every workflow from setting the switch).
- `CONTEXT.md` (Operations: the identities and their checks).

## Tradeoffs

- Reads are not limited to synthetic agencies: a `sales` / `finance` session reads what its role reads on Dev, the
  pilot agency included. Limiting every read route was out of scope; A10a already reads everything as admin from a
  more widely readable mailbox, so this adds no new reader of Dev data.
- The synthetic check is one SQL per allowed write (a fresh pool read, no cache): a flag cleared in CIS stops the
  identity at once.
- The smoke writes through the BFF from the signed-in page (`fetch`, same origin) instead of clicking through the
  admin UI: it proves the browser session and the server-side refusal without depending on page markup.

## Threat note (for the independent review)

- **Asset at risk:** Booking writes on Dev. **Who can get a session:** whoever reads a sign-in code under
  `inbound-admin/` (the MFA admin role, already full AWS admin) or controls mail for `e2e-mail.lumiguides.it.com`
  (A10's domain dependency: losing it removes every E2E address at once).
- **What a session can do:** reads of its role on Dev; at most these writes, and only on a synthetic agency's records:
  send / confirm a supplier booking, record an agency payment, approve / reject one. No retention run, no staff,
  pricing, B2B partner, billing config or customer write; no delete.
- **Bypass attempts covered by tests:** another identity's write (403 `e2e_read_only`), extra or other groups (403
  `e2e_scope`), look-alike or non-ASCII address (no match: an ordinary staff check then applies and the address is
  outside the staff domain, so the trigger never issues it a token), outside Dev (403 `e2e_not_allowed_here`, reads
  too), a real / pilot / NULL-canary agency, a B2C case, an unknown id, a non-UUID path value, a missing view column or
  a DB error (403 `e2e_synthetic_only`, fail closed).
- **Residual risks:** (1) someone with CIS admin on Dev can set `is_canary` on a real tenant and so widen the scope:
  the same trust as A10b-1 (CIS admin is already a higher privilege than these writes). (2) A record's agency can
  change between the check and the route (no lock): Booking never moves a supplier booking, invoice or payment to
  another agency, so the window has nothing to race. (3) The identities exist in the shared WORKFORCE pool on Dev
  only: the trigger map is consulted only while `E2E_DEV_ONLY_STAFF_ENABLED` is exactly `"true"`, which Terraform
  sets for dev only (precondition elsewhere).
- **Audit:** every allowed write is the unchanged route, so `booking.audit_logs` names the identity's staff key
  (`cog:<sub>`) as `actor_ref`; refusals are logged `booking_e2e_writer_refused identity=… reason=…`, allowed writes
  `booking_e2e_write_allowed`.
- **Removal (AA-1054, with the A10 family):** delete the three Cognito users, drop the trigger entries and the
  mailbox recipients (AA-CIS-Infra), drop `app/auth/e2e_staff.py` and its two calls, deactivate the three
  `booking.staff_users` rows; CIS 401's column may stay (a later `_v2` view drops it).

## S278 lane l18: fixtures, departure cancel (A10e-1), the full write run

The S278 live verify proved every refusal but no allowed write: Dev had no record the identities may act on, the CRM
E2E agency was not synthetic for the guard, and no identity could cancel a departure (crm-13).

### Decisions

- **Fixtures through the services, not hand rows** (`backend/app/e2e_fixtures.py`, CLI, DRY RUN by default, Dev
  only). Per run: a departure of a tour a synthetic agency booked before (`departures.create_departure`), that
  agency's booking on it (`desk_bookings.enter`: quote, hold, confirm at its own price, agency reference
  `E2E-<run>`), a pending supplier booking on the case (`supplier_bookings.create`), an issued settlement invoice
  (draft + adjustment line + `invoices.issue`). Written as the A10e staff identity (its staff row from its first
  sign-in) so the audit log names it. Idempotent per run key. A CLI in the API image (precedent
  `app.inquiry.leg_keys`), run through ECS Exec, not an admin route: no identity the orchestrator can sign in with
  may create records, and adding one would widen auth further than the fixtures need.
- **Departure cancel = A10e-1.** Departure status needs `trip_plan.write` (admin, contracting). Options weighed: a
  fourth identity in `booking-contracting` (an Infra trigger, a Cognito user, the CIS reconcile list and Terraform for
  one write), moving the staff identity to contracting (it would also get pricing and bill approval), or a
  route-scoped grant. Chosen: the staff identity's allow-list gets PATCH `/booking/catalog/departures/{departure_id}`
  with a fixed body (exactly `{"status": "cancelled"}`, `BODY_RULES`, checked before any DB access), and only after
  every check passed does that one request hold `trip_plan.write` (`E2EWriter.grants` -> `Staff.e2e_grants`, never
  stored; a unit test pins the only grant).
- **Synthetic departure rule** (`DEPARTURE_SYNTHETIC_SQL`, tightened in the review fix pass): the A10e staff
  identity created it (`departures.created_by` is that identity's staff key: only the seeder makes such departures),
  at least one agency hold line is on it, and every agency tied to it in any departure-scoped table is synthetic in
  CIS: hold lines (any hold status), `departure_allotments` (any state: the cancel's `END_ALLOTMENTS_SQL` ends every
  open one, pending included) and `departure_fees` (any status). A catalogue departure staff made (even one only
  synthetic agencies booked), an empty departure, one a real agency has a hold, allotment or fee on, an unknown id, a
  missing column or a DB error are real (fail closed). The feed event of a cancel reaches hold-line partners only;
  with every tied agency synthetic, no real agency loses anything silently.
- **Default target = the CRM E2E agency** (`CRM_E2E_AGENCY_TENANT`, the sen-vang UUIDv5 the CRM seed and CIS's
  synthetic registration share): the departure.cancelled event then reaches a CRM that can open its
  `aa_cancel_case`. `--agency-tenant` picks another synthetic agency, `--any-synthetic` the latest booked one.
- **The CRM side of crm-13** is checked by AA-Partner `e2e/tests/aa-cancel.spec.ts` (prepare: a draft builder
  version of a CRM trip with the seeded tour as an AA item on the seeded departure, before the cancel; verify: the
  trip's `aa_cancel` card and the pipeline `issue=aa_cancelled` filter, after it). A staff desk booking creates no CRM
  trip, so the CRM needs its own trip on the departure for a case to open.
- **Payment = the open amount**: the maker records the invoice's whole open amount (total - paid - waiting) unless
  `PAYMENT_AMOUNT` is set, so a run leaves no balance that could turn the agency past_due (G4 credit stop).
- **Audit actor check** uses the A10a read-only admin (`booking-admin` reads `/audit-logs`; codes in `inbound/`):
  the write identities have no `audit.read`, and none is widened for it.

### Changed

- `app/auth/e2e_staff.py` (DEPARTURE_CANCEL, BODY_RULES, grants, departure SQL + `SYNTHETIC_SQL_ARGS`),
  `app/auth/staff.py` (`Staff.e2e_grants`, body check + grant in `current_staff`), `app/e2e_fixtures.py`, the spec
  (fixtures file, test 4 departure cancel, test 5 audit actor: `items[].actor.id` + `action`, the shape of
  `GET /booking/audit-logs`), CONTEXT.md.
- Tests: unit `test_aa1087_e2e_writers.py` (+ departure cancel), `test_aa1087_e2e_fixtures.py` (CLI shell);
  integration `test_aa1087_e2e_fixtures.py` (seeder end to end on PostgreSQL, the departure rule: a staff-made
  catalogue departure, an empty one, a mixed one, a seeded one with a real agency's pending allotment or fee).

### Tradeoffs

- The seeder copies a tour a synthetic agency already booked (a known-priceable line) instead of taking a tour
  argument: no pricing guesswork on Dev; the first synthetic booking must exist (the CRM agency has several).
- Each run leaves a confirmed synthetic booking, a supplier booking and a small issued invoice on Dev (marked "E2E
  fixture (synthetic) run <run>"); the run cancels the departure and the maker / checker pay the invoice in full (its
  open amount, so it ends `paid`). A dry run, or a run stopped before the checker approves, leaves the invoice open:
  approve or reject the recorded payment, or record the rest, before its due date. Nothing is deleted.
