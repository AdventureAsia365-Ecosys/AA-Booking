# AA-1158 part 1 — approval rules for a three-person team (S288)

Scope: part 1 only (bk-064 + Booking code). Part 2 (KMS key, supplier profile fields, supplier bank accounts) is S289.

## Decisions

- **bk-064 stays compatible with the running code (MIG-4).** CI runs the whole integration suite on the
  migration-only PR with the old code, and the migration preflight refuses a readiness raise to a contract key in
  the same PR. So every DB rule in bk-064 had to keep the old code's flows working, except where the old code's
  flow is exactly what R3 / R4 / R5 forbid (those old test expectations are updated in the migration PR). Two strict
  rules that the old code would break are deferred to the part 2 migration (S289):
  - `suppliers`: refusing any INSERT but `pending` with a creator, and the column default `pending` (the old code
    inserts `active` for a holder of `supplier.activate`; older schema tests insert as role booking without a
    creator; fixtures rely on the default). The code PR inserts `pending` with its creator only.
  - `billing_entity_guard` (payment_instructions / is_default change only in the approving transaction): the old code
    edits them directly. The code PR routes them through `billing_entity_change`; part 2 adds the DB guard together
    with the same guard for supplier bank accounts.
- **Activation guard fills the activator from `updated_by`.** When an activation statement names no activator (the
  old code), the trigger sets `activated_by := updated_by`, `activated_at := now()`, flag false; it always requires
  `activated_by = updated_by`. So the DB refuses a creator activating their own supplier from the old code too.
- **Owner connections are exempt from the shape guards only.** `suppliers_activation_guard` skips members of
  `bk_owner` (migrations, DB Migrate run-script, test fixtures); they own the table and could drop the trigger anyway.
  A post-check makes sure role `booking` is never a member. The CHECKs and the owner self-approval trigger bind
  everyone.
- **One business-owner reader:** `custom_roles.is_business_owner(conn, cognito_sub)` next to `is_owner` (lane
  contract rule 1): uncached, fail closed. `app/auth/self_approval.py` builds the per-request decision on it (preview,
  E2E writer and E2E test sessions never self-approve).
- **Payout rule (critique 9):** the bill creator and facts editor never pay (bk-030 rule kept for everyone, the owner
  included). The approver pays only flagged `same_approver_payer`, and only as the business owner. Widening it to
  "the owner may pay a bill she entered" needs an explicit tech-lead yes (open question below).
- **Contract writers:** backfill on drafts only, before the trigger exists; published / expired contracts keep
  `writers = '{}'` (the bk-008 lock refuses any UPDATE of them). The append happens only while a draft; the reason is
  that the lock fixes published contracts anyway (the plan's restrictions.py rationale was wrong: `_touch_contract`
  only ever succeeds on drafts).
- **Generic owner guard re-checks only on a change** of the approver column or the flag (critique 3), so a flagged
  row stays editable after the marker moves or the owner leaves.
- **The migration guard allows one read of schema `shared`:** `tests/migration_guard.py` refused any `shared.*` name
  but `schema_versions`; it now also allows `shared.v_staff_booking_grant` after FROM / JOIN only (the trigger
  function's read), with a unit test for both sides.
- **The page flag is its own route** `GET /staff/me/self-approval`, not a field of `/staff/me`: a sign-in then never
  reads the CIS view (the AA-1155 sign-in tests count those reads), and AA-1157 keeps `/staff/me` to itself.
- **Price versions write the flag as `owner_self_approved = ($2 = created_by)`**: the API has already refused any other
  maker; the DB owner trigger checks the marker. Kept `price_versions.py` within its file-size baseline.
- **Fixture shortcuts:** `tests/integration/conftest.py` `activate_supplier` / `make_sellable` run as the owner
  connection (exempt from the shape guard, like DB Migrate run-script) for fixtures that need an active supplier or a
  sellable plan; the rules themselves are tested in `test_bk064_schema.py`, `test_aa1158_approval_rules_api.py` and
  the API tests that now go through the second person (bk008 suppliers, aa1037 billing entity, aa1091 workbench).
- **Season approvals:** self-approval for `season` ranges, holiday events, the calendar default and the trip plan
  calendar (`decide_plan_calendar`); the last two have no decided_by column, so only the audit row carries the flag.
  Stop-sale ranges, every range / event end, rejections and withdrawals stay two-person.

- **Review fixes (S288, after the agent review):**
  - *Supplier writers (R5 gap like R4 / bk-045).* `suppliers.writers` (bk-064, trigger `suppliers_writers`): INSERT
    = `[created_by]`; an UPDATE that changes the supplier's data while it is pending appends `updated_by` (the status
    move, the activation and bookkeeping columns are not data; an edit in the activating statement counts, so the
    activator becomes a writer and is refused). The CHECKs read `created_by` OR `writers`, so existing rows keep
    `'{}'` and no live row is touched (no backfill). The API passes `supplier_makers()` (writers + creator) to
    `self_approval.check`, `actions.activate`, `approvable=me` and the My work queue. Chosen over "only the creator
    may PATCH a pending supplier": it keeps the content + ops maker / reviewer flow (anyone with `supply.write` fixes
    a typo) and gives a DB backstop now, not in part 2. Edits while `inactive` add no writer (that data was approved
    once; a re-activation is the ordinary rule: not the creator, not a pending-data writer).
  - *Workbook sellable gate vs recompute budget.* `sellable_gate.recompute_queue(plans, MAX_RECOMPUTE)` puts the plans going sellable first,
    then the others in workbook order, capped at `MAX_RECOMPUTE`; the apply recomputes exactly that list, and the dry
    run (`sellable_gate.check_import(recomputed=...)`) accepts a `priced` prediction only for a plan in it. Beyond the
    budget the dry run reports `no_approved_price` with "import it in a smaller workbook".
  - *Erasure of billing_entity_change reasons (DM-6.7).* The guard lets one update set `reason` and / or
    `reject_reason` to `[redacted]` with every other column unchanged, on any row (owner run-script; role booking has
    no UPDATE grant on `reason`), like bk-048 / bk-054 / bk-057. Root DM-7.1 row reworded to match.
  - *E2E pricing checker activate.* Behavioural tests: the checker's activate of the maker's synthetic supplier
    reaches the route; on a real supplier 403 `e2e_synthetic_only` after a single guard query, before the staff sync;
    the maker stays `e2e_read_only`.

## Changed

- `custom_roles.is_business_owner(conn, cognito_sub)` (lane contract rule 1) and `app/auth/self_approval.py`
  (`check`, `may_self_approve`, `switch_on`, `flag`).
- New capability `billing_config.approve` (admin, finance; approve class by its suffix, so never in a custom role).
- `app/agency_billing/entity_changes.py`, `app/ops/bill_approvals.py`, `app/catalog/sellable_gate.py` (split out to
  keep the files within the code-health baseline).
- My work: `suppliers_to_activate`, `billing_changes_to_approve`, `owner_self_approvals` (every `audit.read` holder);
  the bill and agency payment approval tiles include the business owner's own items.
- Frontend: pending badge / filter / Reject on suppliers, Activate follows `actions.activate`, publish follows the
  writer list, bill drawer owner notices, billing entity pending-change panel (approve / reject / withdraw) and
  "Change payment details", audit log tab "Business-owner self-approvals", own-row approve for the business owner on
  price versions, seasons, agency payments and price adjustments (`lib/useSelfApproval.ts`), workbench reason
  `no_approved_price`.
- Tests that assumed the old rules: suppliers active on create, a creator publishing after a checker edit, the
  workbook selling a tour before its rates, entities with payment details on create (now approved by FIN_B).
- Replays of bk-048 / bk-054 / bk-055 in integration tests re-apply bk-064 (they REVOKE ALL and re-grant columns).

- Supplier `pending` status: every new supplier starts pending, whoever creates it; `set_status` refuses `pending`
  as a target; `pending -> inactive` is a reject (`supplier.rejected` audit action).
- `contract.publish` checks the writer list, not `coalesce(updated_by, created_by)`.

## Tradeoffs

- The sellable gate reads matrix rows only (readiness `priced` / `hand_priced`), not the readiness probe of a plan the
  cost sheet would price but has not stored yet (`pending_recompute`): the gate is a write, the probe is costly, and
  the `bk_price_recompute` job stores the rows. The workbook import also accepts a tour its own recompute will price.
- Open question for the tech lead (critique 9): may the business owner pay a bill she ENTERED (not only approved)?
  Today no (bk-030 rule kept); she approves the payout path only for bills someone else entered.

- Deferring the two strict DB rules keeps CI green and the MIG-4 order, at the cost of the DB not refusing an
  INSERT of an active supplier or a direct bank-detail edit until part 2. The API refuses both from this PR on.
