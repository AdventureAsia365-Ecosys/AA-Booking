# AA-1060 — Booking admin deploy keeps the WordPress test site sidecar

## Decisions
- AA-CIS-Infra adds a second, non-essential container `test-wp` (a WordPress test site for the CIS publish checks) to
  the Booking admin task definition family (`modules/environment/test_wp.tf`, tech lead approved in S274, $0 Fargate:
  the task size does not change). `deploy-admin-dev.yml` refused any revision with more than one container.
- The guard now asks for exactly one container named `booking-admin` that is essential; every other container is
  copied as it is (the image swap already targeted `booking-admin` by name). The step prints the container names.

## Changed
- `.github/workflows/deploy-admin-dev.yml`: the one-container guard; nothing else (build, push, wait, image check of
  the running tasks, verify, smoke unchanged: they name `booking-admin`).
- `CONTEXT.md`: the Frontend on ECS paragraph says the copy keeps other containers.

## Tradeoffs
- The deploy does not validate the sidecar (its image, its secret): Terraform owns it and its own guards live in
  AA-CIS-Infra (`tools/terraform/tests/test_aa1060_test_wp.py`).

## Should know
- Merge this before the first Booking admin deploy after the AA-CIS-Infra apply that adds the container, or that deploy
  fails at the guard (nothing is changed on the service when it fails).
- A Booking admin deploy is also how the running service first gets the sidecar (the service ignores the task
  definition Terraform registers); the AA-CIS-Infra step 2 apply (`test_wp_service_attached`) follows it.
