# AA-811 — Staff "new inquiry" e-mail through SES (Booking half)

Scope (S238): the first real consumer of the SES channel that AA-CIS-Infra #113 created (identity
`lumiguides.it.com`, configuration set `aa-email-dev-transactional`, `ses:SendEmail` for the Booking task role with
`ses:FromAddress = no-reply@lumiguides.it.com`). Booking sends one e-mail to the staff inbox for each new inquiry.
Infra adds the task environment in `accounts/aa365/booking.tf` (separate PR); TripPlanner `notify.py` stops
pretending to e-mail the advisor (separate PR).

## Decisions

- **Booking sends the advisor / staff e-mail, not TripPlanner** (Nghiep, S238). ADR 0004 boundary: TripPlanner is
  the front door, Booking owns customers, trip cases and notifications. The issue text (scope 4, "wire TripPlanner
  `notify.py`") is superseded by this decision.
- **Own job kind `bk_notify_email`**, queued by `bk_inquiry_process` in the same transaction as the
  `trip_case.new_inquiry` notification row. SES is never called inside the intake transaction or a request path,
  so an SES outage cannot fail or slow the intake.
- **Dedupe = the job idempotency key** `bk_notify_email:<notification_id>` (the existing `booking.job` unique index).
  The intake transaction runs once per inbox row (a settled row is a no-op), so there is one notification and one
  job. Delivery is at least once: a worker that dies between SES accepting the message and `complete()` re-sends
  it when the reaper re-queues the job. Acceptable for a staff alert; SES v2 has no idempotency token.
- **No migration.** The SES `MessageId`, the recipient and the case code are kept in `booking.job.result`.
- **Content is read at send time**, not copied into the job payload: notification → trip case → lead customer →
  legs, plus a live, soft read of `catalog.v_tour` (title, country) per leg `source_tour_id` (contract: CIS
  `tour_id`). An unreadable catalog falls back to the snapshot day name / "AA tour <id>" (same rule as
  `trip_cases.sql.leg_title`), the e-mail still goes out.
- **Templates in code** (`render()`): plain text + a simple inline-styled HTML twin, all values HTML-escaped. Subject
  `[Dev] New inquiry TC-000123: <customer name>` (no prefix on `prod`). Contains the customer's name, e-mail and
  phone (it goes to staff only), countries, tours requested with their day ranges, trip length, travel dates and
  travellers ("not given yet": TripPlanner's `inquiry.submitted` carries neither), the merge-review warning when
  the lead matches a customer, and the link `<STAFF_ADMIN_URL>/cases/<code>`.
- **Settings, all optional** (`STAFF_NOTIFY_EMAIL`, `SES_FROM_ADDRESS`, `SES_CONFIGURATION_SET`, `SES_REGION`,
  `STAFF_ADMIN_URL`). Without the recipient or the sender the job succeeds as `skipped` with the reason and a log
  line: local runs, tests and an environment without SES never fail jobs. `SES_FROM_ADDRESS` has no code default on
  purpose: it must equal the Infra `ses_from_address` (IAM condition), so it comes from the task definition.
  `STAFF_ADMIN_URL` defaults to the Dev Vercel alias, like the other Dev defaults (CIS JWKS / issuer).
- **Error policy.** SES error codes that a retry cannot fix (`MessageRejected`, `MailFromDomainNotVerifiedException`,
  `AccountSuspendedException`, `SendingPausedException`, `BadRequestException`, `NotFoundException`,
  `AccessDeniedException`) → `PermanentError` (job failed at once, reason in `booking.job.error`); everything else
  (throttling, 5xx, network) is retried by the runner (30 s, 60 s, ... up to 5 attempts).
- **boto3** pinned to the AA-CIS-App version (1.43.49), imported lazily in `app/mailer.py`; the blocking call runs in
  `asyncio.to_thread` because the worker shares the event loop with the API. One client per handler, created on the
  first send; credentials come from the ECS task role.

## Changed vs. the issue

- Issue scope 4 said TripPlanner `notify.py` would send the advisor e-mail; per S238 Booking sends it.
- Scope 3 "suppression on bounce/complaint" in app tables is **not** built: the SES configuration set already has
  account-level suppression (`BOUNCE`, `COMPLAINT`) and the feedback SNS topic has no subscriber yet. A Booking-side
  suppression table is a follow-up when customer e-mail (quotes, OTP) lands.

- `.github/workflows/deploy-dev.yml`: base revision = latest of the family (see "Should know"); needed for the new
  task environment to reach the running task at all.

## Tradeoffs

- One staff inbox (a setting) instead of per-staff recipients: there is no assignment at intake time and the staff
  directory has no e-mail preferences yet. Per-staff routing is a later change in the same handler.
- Reading content at send time means a case edited before the job runs shows the edited values; the job normally
  runs seconds after the intake, and the newest data is what staff want.

## Should know

- The live chain is: TripPlanner "Send to an advisor" → `tripplanner.outbox` → `bk_inquiry_pull` (~60–90 s) →
  `bk_inquiry_process` → `bk_notify_email` (next worker tick) → SES `MessageId` in the job result → inbox.
- Re-sending by hand needs a new idempotency key (the unique index covers finished jobs too), e.g. enqueue with key
  `bk_notify_email:<notification_id>:resend-1`.
- The environment variables are declared in AA-CIS-Infra `accounts/aa365/booking.tf`. Order: Infra apply (new task
  definition revision with the env) **before** the app deploy of this PR; until then the job logs `skipped`.
- `deploy-dev.yml` now bases the new revision on the **latest ACTIVE revision of the family** (`ECS_TASK_FAMILY`,
  default `aa-booking-dev-api`) instead of the revision the service runs. Before, a Terraform change to the task
  definition never reached the running task: the service ignores `task_definition` changes (booking.tf
  `ignore_changes`) and the deploy copied the service's own revision, so the new env would have been lost. Same rule
  as the CIS deploy. Only the image is swapped, as before.
