## Decisions

- **Booking keys staff by the Cognito identity; the CIS directory is not read.** Source of truth for staff identity is
  the Cognito WORKFORCE pool (ADR 0006a). A WORKFORCE token is matched on `(cognito_iss, cognito_sub)`. No row →
  Booking creates one from the token claims with `cis_user_id = 'cog:' || sub`. `cis_user_id` stays the primary key
  (about 30 FKs: versions, suppliers, pricing rules, FX, assignments, notification reads …) and is documented as "the
  Booking staff key, legacy name" (column comment in bk-016). The rejected alternatives (a CIS contract view, a CIS
  HTTP lookup, a Cognito custom attribute) are listed in the S243 plan; the main session chose this design.
- **Identity columns are a pair `(cognito_iss, cognito_sub)`**, the same shape and check as CIS
  `shared.admin_users` (`admin_users_cognito_pair_chk`, migration 247): both NULL or both set, issuer `https://…`, sub
  1–128 chars, UNIQUE `(cognito_iss, cognito_sub)`. The issuer is kept (not only the sub) because ADR 0006 §8 keys
  every principal by `(iss, sub)`, and a second pool (prod, or a re-created Dev pool) must never collide.
- **`staff_users_cognito_key_chk`**: a `cog:` key always carries its own sub (`cognito_sub = substr(cis_user_id, 5)`,
  sub NOT NULL). A row created by a Cognito sign-in can therefore never be re-linked to another identity, and an
  operator who reads `cog:<x>` in an FK knows which Cognito user it is.
- **bk-016 is migration-only and not in `REQUIRED_SCHEMA_VERSIONS` in its own PR** (CONTEXT rule: apply first, then
  require). The code PR adds it.
- **Re-runnable DDL**: `ADD COLUMN IF NOT EXISTS`, `CREATE UNIQUE INDEX IF NOT EXISTS`, and each CHECK dropped if
  present then added (the Integration Tests replay every file; `ADD CONSTRAINT` has no `IF NOT EXISTS`). The table
  has a handful of rows, so the CHECK validation scan is instant; `lock_timeout` 5 s as in bk-012/013.
- **Verifier = byte copy of CIS `api/core/identity_verifier.py`** (AA-CIS-App main `13911f5`, #808) at
  `backend/app/auth/identity_verifier.py`, excluded from ruff (CIS style, like the job template copies) and
  drift-checked by the non-required CI job, renamed "Job template copy" → **"Vendored CIS copies"**
  (`scripts/check_job_template_copy.py` → `scripts/check_vendored_copies.py`, now keyed by path under `backend/`). The
  CIS unit tests are copied up to their CIS-only `identity_config` / `api.main` part with only the import path changed
  (`tests/unit/test_identity_verifier.py`); the Booking issuer config has its own `test_identity_config.py`.
- **Accepted clients: WORKFORCE x {booking-staff, breakglass}** + the bridge. `cis-admin` is left out until a CIS
  screen calls the Booking API (least privilege; ADR 0006 §8 rule 6 lists it, deliberate deviation).
- **Issuer and client ids are code constants with optional env overrides read by `Settings`**
  (`COGNITO_WORKFORCE_ISSUER`, `COGNITO_BOOKING_STAFF_CLIENT_ID`, `COGNITO_BREAKGLASS_CLIENT_ID`, the CIS names). No
  task-definition change; none of them is set on Dev. Validated in `Settings` (https issuer without trailing slash,
  alphanumeric client ids).
- **Which rules apply is chosen by the `IssuerConfig.name`** (`workforce` / `bridge`) of the verified `iss`
  (`identity_config.issuer_kind`). `BRIDGE_ENABLED` is a module constant so PR-4 starts by flipping one line.
- **Role from groups on every request; no group = 403 `no_booking_role` before any DB call** (nothing written, so a
  grant removed in CIS takes effect on the next token, at most the 15-minute access-token life).
- **`active` stays a Booking switch for linked rows**: an inactive linked row is refused (403 `staff_inactive`), as the
  main-session design says ("active=false rows refused"). So `PATCH /booking/staff/{id}` still accepts `active` for a
  linked row (suspend / re-enable) and refuses only a **role** change (409 `managed_in_directory`). The plan's S2(f)
  refused both; refusing `active` too would leave an inactive linked row with no way back. Group removal does **not**
  flip `active` (the plan's S2(e) did): it refuses at the token, so re-granting in CIS works without a Booking admin.
- **New `cog:` rows are active** (the group is the grant). Their `name` is the e-mail local part: Cognito access
  tokens carry no name and Booking does not read the CIS directory; the backfill fills real names for linked rows.
- **Write only when something changed**: one SELECT by identity per request; an UPDATE (after `SELECT … FOR UPDATE`)
  only when role / e-mail / cis_role changed or `last_seen_at` is older than 5 minutes (the bridge's throttle). The
  role-change audit row compares under the lock, so concurrent requests write it once.
- **First sign-in race**: `INSERT … ON CONFLICT DO NOTHING` then re-read by identity (the conflicting insert waited for
  the other commit). Still nothing → the `cog:` key is held by another issuer → 403 `identity_conflict`, logged, never
  rebound. The integration test runs 4 concurrent first sign-ins → one row, one audit row.
- **Bridge path unchanged** except: the bridge `name` claim is read from the already verified token (the vendored
  `Principal` has no `name`); a bridge token without `cis_role` is now 403 `unknown_cis_role` (was 401); a bridge
  `sub` starting with `cog:` is 401 (a CIS id is never one).
- **`app/auth/tokens.py` keeps only the single-issuer cache + decoder for the deploy gate** (`app/auth/ci.py`).
  `StaffTokenVerifier` / `StaffClaims` are deleted now (dead once the app uses the multi-issuer verifier; the plan had
  them in PR-4). `BridgeClaims` in `staff.py` replaces `StaffClaims` for `provision()`.
- **`REQUIRED_SCHEMA_VERSIONS` += `bk-016`** (bk-014 / bk-015 are not added: no shape this code reads).

## Changed (vs. the plan / issue)

- The plan's S2 resolved unknown identities through a CIS view `catalog.v_staff_identity` with an email fallback.
  Replaced (main-session decision) by: create `cog:` rows on first sign-in + a one-time Infra backfill that links the
  bridge-era rows from `shared.admin_users.cognito_sub`. No CIS migration, no cross-schema read at request time.
- No email fallback link (dropped with the CIS view).
- `PATCH` refuses role only, not `active` (see Decisions).
- `StaffTokenVerifier` / `StaffClaims` removed now instead of in PR-4.

## Tradeoffs

- **A bridge-era person whose CIS row is not linked to Cognito when the backfill runs gets a second (`cog:`) row on
  their first Cognito sign-in**; their bridge-era history (assignments, versions, rules) stays on the old row. The
  backfill DRY RUN lists every bridge-era row it cannot link, so this is visible before the code ships; the backfill
  is idempotent and can be re-run, but it never merges a `cog:` row into a bridge row (that would mean re-pointing
  ~30 FKs). Accepted for Dev (7 CIS staff, a few Booking rows).
- **Group removal does not deactivate the Booking row.** The person is refused at once on WORKFORCE (no group →
  403), but during the dual-issuer window they can still use the bridge (CIS password login) until PR-4, because the
  bridge never reads groups. Keep the window short; a Booking admin can also set `active = false`.
- **Role overwrite**: bridge-era rows whose role was set by a Booking admin take the group role on the first Cognito
  sign-in. Set each person's Booking role in CIS → Platform → Staff before they sign in with Cognito.
- **Bridge-era inactive rows stay inactive after linking** (e.g. a CIS reviewer provisioned as inactive `sales` and
  never activated): with a `booking-*` group they get 403 `staff_inactive` until a Booking admin activates them on
  `/staff`. The backfill DRY RUN prints `active` per row so this is visible before the code ships.
- The vendored verifier drift check is non-required: a CIS change to `identity_verifier.py` shows a red, non-blocking
  check here until the file is copied again.
