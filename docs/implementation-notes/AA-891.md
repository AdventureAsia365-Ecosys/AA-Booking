# AA-891 — release-please and the release version on /booking/health (Booking)

Linear AA-891 (release versioning for the three public app repos), with AA-901 (the `aa-ecosys-ci-bot` GitHub App).
This file covers AA-Booking; AA-CIS-App and AA-TripPlanner-Web have their own notes.

## Decisions

- **release-please in manifest mode, one package at the repo root.** `release-please-config.json` +
  `.release-please-manifest.json`, `release-type: simple`, `bump-minor-pre-major: true`, `include-v-in-tag: true`,
  `include-component-in-tag: false` (tags are `v0.2.0`, not `aa-booking-v0.2.0`), changelog `CHANGELOG.md` at the root.
  One version covers the whole repo (API image + staff admin); the two are always deployed from the same `main`.
- **Release PR title = the release-please default, `chore(main): release x.y.z`**, the same as AA-CIS-App and
  AA-TripPlanner-Web (no `pull-request-title-pattern`). `pr-title.yml` allows an optional scope, so the title, and the
  squash commit on `main`, pass the `PR title` check.
- **Workflow `.github/workflows/release-please.yml`:** push to `main` + `workflow_dispatch`, job in environment
  `release` (deployment branches: `main` only) and an `if: github.ref == 'refs/heads/main'` guard, so a dispatch from
  another branch is skipped instead of failing on the environment rule. `GITHUB_TOKEN` is `contents: read` only.
  The writes (release branch, PR, labels, tag, GitHub release) use an installation token of `aa-ecosys-ci-bot`, minted
  by `actions/create-github-app-token@v3` from `vars.AA_CI_BOT_APP_ID` + `secrets.AA_CI_BOT_PRIVATE_KEY`, narrowed to
  `contents`, `pull-requests` and `issues` write. A PR opened with the App token triggers the required CI checks; one
  opened with `GITHUB_TOKEN` would not (GitHub does not start workflows from `GITHUB_TOKEN` events).
  Actions pinned to their current released majors as AA-891 asks: `create-github-app-token@v3` (v3.3.0 at the time)
  and `release-please-action@v5` (v5.0.0), both Node 24. `app-id` is deprecated in v3 in favour of `client-id` but
  still supported (a deprecation warning in the log); kept, because the variable holds the numeric App ID.
- **First release v0.2.0 without `release-as`.** The manifest holds `0.1.0` (the version before the first release, the
  same as `backend/pyproject.toml`). There is no tag yet, so release-please reads every commit on `main`; the history
  has `feat:` commits and, pre-1.0 with `bump-minor-pre-major`, even a breaking change only bumps the minor:
  `0.1.0 → 0.2.0` exactly. Nothing to remove afterwards. (Had another number been needed, `"release-as": "x.y.z"` in the
  `"."` package config is the way; it must then be deleted in the first PR after that release, or every later release PR
  proposes the same number again.)
- **Version baked like `GIT_SHA`.** Deploy Dev reads the version from `.release-please-manifest.json` at build time
  (`jq -r '."."'`) and passes `--build-arg APP_VERSION=…`; the Dockerfile turns it into `ENV APP_VERSION`,
  `Settings.app_version` reads it (default `unknown`), and `GET /booking/health` returns
  `{"status", "service", "version", "git_sha"}`. The deploy smoke test and CI's Docker Build Check assert the
  `version` field equals the manifest.
- **Version files:** `backend/pyproject.toml` `[project].version` is the only other place; it is a release-please
  `extra-files` entry (`type: toml`, `$.project.version`), so the release PR bumps it with the manifest. A unit test
  keeps the two equal.

## Changed

- New: `release-please-config.json`, `.release-please-manifest.json`, `.github/workflows/release-please.yml`,
  `backend/tests/unit/test_release_version.py`. `CHANGELOG.md` is created by the first release PR, not here.
- `backend/app/settings.py` (`APP_VERSION` → `app_version`), `backend/app/routers/health.py` (`version` field),
  `backend/Dockerfile` (`ARG`/`ENV APP_VERSION`), `backend/tests/unit/test_health.py`.
- `deploy-dev.yml`: `!backend/pyproject.toml` added to the push paths, build arg `APP_VERSION`, smoke checks `version`.
- `ci.yml` Docker Build Check: same build arg, and the container's `/booking/health` must carry the manifest version.
- `CONTEXT.md`: workflow list, `APP_VERSION` in the process environment, a "Releases" paragraph.

## Tradeoffs

- **A release commit does not redeploy** (AA-891: no deploy on a commit that only changes `CHANGELOG.md` / the manifest
  / version files). Deploy Dev already only watches `backend/**`; `backend/pyproject.toml` is now excluded too (the
  image copies only `requirements.txt` and `app/`, so pyproject never changes the image). Vercel Deploy only watches
  `frontend/**`. Consequence: right after the release PR merges, the running task still reports the previous version
  (its code is the same as the release; only the number differs) until the next backend change deploys, or someone runs
  Deploy Dev by `workflow_dispatch` on `main`, which builds a new image for the release commit with the new version.
  Accepted: Dev has no users, and deploying an unchanged image to rename it is a needless restart of the worker.
- **The staff admin's `frontend/package.json` version is not bumped.** Listing it as an extra file would make every
  release commit touch `frontend/**` and trigger a Vercel production deploy (Hobby cap), and its `package-lock.json`
  holds the same number twice more. The package is private; nothing reads its version. The release version of the repo
  is the manifest (and the tag), and the frontend shows no version today.
- **Sentry `release` stays `GIT_SHA`.** Switching it to the release version would group several deploys under one
  release between two releases; left for a separate change if wanted.

## Should know

- Needs, before the workflow can open its first PR: the `release` environment in this repo with variable
  `AA_CI_BOT_APP_ID` and secret `AA_CI_BOT_PRIVATE_KEY` (environment or repo/org level), and `aa-ecosys-ci-bot`
  installed on this repo. Until then the token step fails red on each push to `main` (visible, nothing else breaks).
- The first release PR lists all of the repo's history (37 `feat`, 4 `fix`); `ci`, `docs`, `chore`, `test` commits are
  hidden by release-please's default changelog sections.
- Merging the release PR creates tag `v0.2.0` and a GitHub release; no workflow listens on tags.
- **Rollback past AA-891.** Deploy Dev now reads `.release-please-manifest.json` in its build step (`set -e`), so it
  fails on any checked-out commit from before AA-891 (no manifest there). Roll back with a `git revert` on `main`: the
  revert commit still has the manifest and deploys as usual. A dispatch cannot rebuild a pre-AA-891 commit with this
  workflow.
