# AA-830 — Catalog tour key on trip case legs (Booking half)

Scope (S238, data standards X3, S237 decision E7): TripPlanner sends `inquiry.submitted` v1.2, where every leg also
carries the catalog tour key `(source_system, source_id)` of contract `catalog.tour.v1`. Booking stores the key on
`booking.trip_case_legs` (migration `bk-011`), resolves it for v1 / v1.1 payloads, back-fills existing legs, and the
nightly schema dump in AA-CIS-Infra reports legs whose key is not in `catalog.v_tour` (DM-4.2). Root contract and
registry: AA-Ecosys `docs/contracts/inquiry.submitted.v1.2.json`; TripPlanner producer: `backend/assembly/handoff.py`.
Ecosystem notes: AA-Ecosys `docs/implementation-notes/AA-830.md`.

## Decisions

- **Columns nullable, both or neither, `cis` only.** Legs opened before bk-011 have no key, and a leg whose tour left
  the catalog cannot get one. The CHECK wraps the second branch in `coalesce(…, false)`: a CHECK passes on NULL, so a
  plain `source_system = 'cis' AND length(btrim(source_id)) …` would have let `('cis', NULL)` through (caught by the
  integration test).
- **No FK, no `REFERENCES`** across schemas (DM-2.3; role `booking` has SELECT on the catalog views only). The orphan
  rate is measured by the nightly dump instead.
- **`source_tour_id` unchanged** (still NOT NULL, as sent). It keeps v1 / v1.1 compatibility and the existing readers
  (versions pre-fill, leg titles from the snapshot) working; new code keys on `source_id`.
- **The v1.2 payload's key is stored as sent**, without a catalog read: TripPlanner resolved it in the hand-off
  transaction. Only a leg without a key (v1 / v1.1, or v1.2 with both fields null) is resolved here, by the same rule
  as TripPlanner: `source_tour_id` matched as `catalog.v_tour.source_id` or as `tour_id` (a source_id match wins).
- **Soft catalog read inside a savepoint** (`leg_keys.resolve`, same `CATALOG_ERRORS` as the destination reads): an
  unreadable catalog leaves the keys null and the trip case still opens. A customer's inquiry is never refused over
  the tour key. The process result gains `legs_without_tour_key` so the job log shows it.
- **Back-fill is a module, not a job kind**: `python -m app.inquiry.leg_keys [--apply]`, shipped in the image (only
  `app/` is copied), run once by ECS exec in the Booking task with its own `DATABASE_URL` (role `booking`: UPDATE on
  the table since bk-002, SELECT on `catalog.v_tour` and `tripplanner.v_inquiry_outbox`). DRY RUN by default; `--apply`
  writes only rows still null, so a re-run never overwrites a key. It prints one JSON report: legs without a key,
  matched, written, every unmatched leg (trip case code, position, source_tour_id), and the TripPlanner outbox legs
  (read-only, see below).
- **The TripPlanner outbox is reported, never rewritten.** Its rows are published events Booking already consumed
  (Booking keeps its own copy in `inbox_events`); TripPlanner drafts hold no tour key (the itinerary is projected from
  the components at read time; S238 check: 0 keys in 87 draft entries), so there is nothing to back-fill there.
- **Staff e-mail looks the tour up by `source_id` first** (`staff_email.tour_key`), else `source_tour_id`, matching
  either key kind (it matched `tour_id` only, so a v1.2 leg keyed by a source_id would have lost its title).
- **Trip case detail / list legs** expose `source_system` and `source_id` (additive JSON fields).
- **`bk-011` is required for readiness** (`REQUIRED_SCHEMA_VERSIONS`): intake now writes the new columns.

## Changed vs. the issue

- The issue says "nullable, then backfilled" for the migration. The migration does not back-fill: it runs as
  `aa_cis_admin` through DB Migrate and a catalog read there would tie the migration to CIS 225 being applied; the
  back-fill is the separate re-runnable DRY-RUN-first module above.

## Tradeoffs

- A superseded version `tour_id` is not in `catalog.v_tour` (live tours only) and Booking may not read
  `silver_aa_internal.raw_tours` (ADR 0002), so such a leg stays unmatched and is listed for a person. Dev today
  (S238 read-only check): 8 legs, all keyed by a version `tour_id`, all 8 present in `catalog.v_tour` → the back-fill
  should match 8/8 if run before the next re-upload of that tour.
- The resolve query compares `tour_id::text` (no index use) over ~900 live tours: 8 ms on Dev, once per inquiry.
